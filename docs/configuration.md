## 配置

全在 `/data/adb/soc_freqcap/socfreq.conf` 里，每项都有注释。常用的几项：

| 项 | 默认 | 说明 |
|---|---|---|
| `CPU_PCT_BIG` | 65 | 最强核的封顶百分比 |
| `CPU_PCT_MID2` | 64 | 次强核（只有 4 簇以上机型用得上） |
| `CPU_PCT_MID` | 66 | 中间档 |
| `CPU_PCT_LITTLE` | 65 | 最弱核 |
| `CPU_MIN_PCT_BIG/MID2/MID/LITTLE` | 0 | 进阶最低频：把对应簇 `scaling_min_freq` 抬到硬件上限的百分比，0 = 跟随系统；目标夹在硬件最低与当前封顶之间；设过的簇 `CPU_MIN_LOCK` 让位 |
| `GPU_PCT` | 45 | GPU 封顶百分比 |
| `STRATEGY` | cap | `cap` 固定百分比封顶；`smart` 六态智能调度，`CPU_PCT_*` 只当天花板 |
| `APP_SWITCH_TIER` | 0 | **遗留项，默认关**：ASB/Kin 没有「切前台预热」这套逻辑。0=关，1/2/3=轻/中/重载；开了才会在每次切前台强行抬档 |
| `CAMERA_HOLD` / `CAMERA_HOLD_PCT` | 1 / 80 | 相机前台时封顶软钳到本机峰值×N%（够 4K60 不冲满） |
| `CAMERA_HOLD_PKGS` | 空 | 追加相机包名（逗号分隔），空 = 只用内置表 |
| `FSM_JOINT` | 1 | zTT：热受限 GAMING 且 GPU≥90% 时削大核 8% |
| `GAME_CPUSET_FIX` | 1 | 游戏态 top-app cpuset 被收窄时写回全核（1s 节流） |
| `GAME_DND` | 0 | 游戏态自动免打扰：进 GAMING 切「仅优先」，离开还原（默认关，改系统行为） |
| `WIFI_PS` | auto | WiFi 省电：`auto` 不动、`on`/`off` 写 `wlan_pm`（记账，停守护还原） |
| `PROBE_CADENCE` | 1 | 多窗口扫描节流：重载/高负载 8s、中等 25s、安静 120s（省 fork） |
| `QUIET_NIGHT` / `QUIET_NIGHT_S` | 1 / 300 | 夜间静默：学到的夜间窗口里息屏，巡检拉长到 N 秒 |
| `IDLE_UCLAMP` | 18 | 息屏把 background 组 uclamp.max 收到 N%（只压不抬，亮屏还原） |
| `APP_PROFILE` | 1 | 画像自动匹配：未显式配置的应用落到「其他」档（tool） |
| `FSM_LEARN` | 1 | 智能模式会话学习：按 ASB 的方向信号漂移 alpha（热/掉电/重载/热否决↑，干净凉快↓） |
| `FSM_LEARN_RATE` | 100 | 学习率（千分比）：100 = 每次会话只走信号的 10% |
| `CAP_MIN_FOLLOW` | 1 | 限频模式跟随下限（Scene 式）：上限不变，下限随负载在硬件最低与封顶×N% 之间移动 |
| `CAP_MIN_LO` / `CAP_MIN_HI` | 30 / 70 | 跟随下限的负载阈值（%，带回差） |
| `CAP_MIN_PCT_LO` / `CAP_MIN_PCT_HI` | 45 / 75 | 中载/高载时下限占当前封顶的百分比 |
| `FSM_BOUNDS` | 1 | 智能模式封顶模型：1 = ASB/Kin 频阶曲线（包络+级别+本机缩放），0 = 旧的百分比查表 |
| `FSM_ALPHA` | 0 | 包络混合 0~1000：0 均衡、1000 省电 |
| `FSM_CUR_HEAVY` / `FSM_CUR_MOD` | 150 / 120 | 放电电流闸门（mA），充电或读不到时旁路 |
| `FSM_GAME_HINT` | 1 | 前台命中游戏名单时直接判 GAMING（Kin/ASB 的 `pkg_agrees`），不再等 GPU 连续 6 拍；分类命中的视频/社交/阅读优先，0 = 只看负载 |
| `GPU_BOOST_OFF` | 1 | 1 = 禁止 GPU Boost：同时把下限压回最低档、关掉抬频源头（`dcvs_boost` / `touch_wake` / `force_no_nap` / `devfreq_boost` / 天玑 OPP boost 档），并把高通 KGSL `idle_timer` 从 80ms 收到 48ms（只降不升）；交权态自动还原。旧键 `GPU_MIN_LOCK` 已并入本开关 |
| `BG_LIGHT` | 1 | 后台分组常驻轻压制（与动态封顶无关）：`background` / `system-background` 的 `uclamp.max` 收到 50/60，`background` cpuset 收窄到最低频簇（与现有掩码取交集，只收窄）；交权态自动还原。默认开，页面不提供开关 |
| `BIG_MIN` | 0 | 1 = 超大核压到最低可用频点（不关核）；游戏/满血/熄屏交还仍放开 |
| `BIG_OFFLINE` | 0 | 1 = 常态把最高频簇写 `online=0` 真离线；游戏、满血应用、开机满血窗口会先拉回在线（最多等 2.5 秒）再交还，熄屏保持离线。开机完成且满血窗口结束后才执行 |
| `CPU_MIN_LOCK` | 0 | 1 = 常态把各簇下限压到 `cpuinfo_min`；30s 节流；被平台下限（PPM / powerhint）夹回时按簇退避 60→180→300→600s 重探，插拔电/亮屏立刻重探 |
| `MIN_WINDOW_STEPS` | 3 | 窗口守护（隐藏项）：下限至少比封顶低几个频点，0 = 关。`min == max` 时整簇钉死在一点，空载也不降（CPU 空转），温控/自适应想压封顶也压不动；冲突时让下限让到「封顶往下 N 档」，不足 N 档直接落硬件最低 |
| `CPU_FLOOR_M` | 0 | M 簇封顶下限（Hz，0=不设）：只作用于最低频档（2 簇机型的 LITTLE/M 簇）；动态封顶、智能、温控、电量偏移都不会把它的 `scaling_max_freq` 压到该值以下。Find N5 设 `1785600` |
| `CAP_BACKEND` | auto | CPU 封顶第二道锁：`auto` = 有 MTK PPM 节点就叠加厂商硬限，否则只用 sysfs；`sysfs` = 只写 sysfs；`ppm` / `msm` = 强制（`msm` 为实验性）。隐藏项，页面不摆开关；改后重启守护生效 |
| `INTERVAL` | 5 | 巡检间隔（秒） |
| `GAME_GRACE_SEC` | 30 | 退出游戏后继续保持解锁的秒数 |
| `SCREEN_POLICY` | cap | 熄屏保持封顶（默认开）：`cap` = 保持封顶 + 轻巡检；页面一个「熄屏保持封顶」开关，关掉写 `uncap`（交还系统）；高级用户手工写 `keep` 仍生效 |
| `SOFF_INTERVAL` | 15 | 熄屏轻巡检周期（秒，5~300） |
| `SCREEN_STATE_PATH` | 空 | 亮屏信号文件；空 = 自动挑选 |
| `SCREEN_UNCAP` | 0 | 旧键兼容：只在手工设成 `keep` 时给旧的熄屏解锁分支用 |
| `IDLE_CURRENT_MA` / `IDLE_HOLD_CYCLE` | 250 / 2 | 熄屏电流低于多少 mA、连续几轮后进深度空闲 |
| `IDLE_INTERVAL` / `WAKE_DELTA_MA` | 30 / 150 | 深度空闲周期；电流比熄屏基线高多少 mA 才触发一次亮屏复核 |
| `BATT_CURRENT_PATH` / `BATT_CURRENT_UNIT` | battery/current_now / auto | 电流节点与单位；auto 按量级识别，ua / ma 可强制；符号统一取绝对值，明显是 µA 的超大读数也会自动纠正 |
| `BOOT_FULL_S` | 60 | 开机后满血窗口秒数（0 = 关掉这个功能） |
| `CPU_GOVERNOR` | 空（不干预） | 留空 = 不碰调速器；荣耀 / 华为机型一律不改写（切 conservative 会硬重启） |
| `CHG_UNCAP` / `CHG_PCT` | 1 / 100 | 插电时把常态 CPU/GPU 封顶至少抬到多少（专属 GPU 档不抬） |
| `TH_CAP` / `TH_HIGH` / `TH_LOW` | 0 / 75 / 68 | 温控闭环默认**关**（发热交给内核热管理）；打开后超 TH_HIGH 逐档压、回 TH_LOW 逐档还 |
| `TH_STEP` / `TH_MAX` / `TH_BACK` | 5 / 25 / 20 | 每档压多少个百分点、最多压多少、每多少秒还一档 |
| `PSI_ADAPT` / `PSI_GAIN` / `PSI_STEP` | 1 / 5 / 5 | PSI 护栏开关与最多借出（默认最多一档 +5）、每档多少个百分点 |
| `PSI_HOLD` / `PSI_BACK` | 30 / 15 | 判到卡后额度至少借住多久、不卡了每多少秒收回一档 |
| `ADAPT_UP_MAX` / `ADAPT_DOWN_MAX` | 15 / 30 | 合计偏移的总闸（百分点）；0 = 那一侧封死 |
| `BATT_STEP` | 0 | 电量阶梯开关（默认关）；打开后低电量才额外收紧 |
| `BATT_LOW` / `BATT_LOW_CUT` | 20 / 5 | 低于多少电量（%）压第一刀、压几个点 |
| `BATT_CRIT` / `BATT_CRIT_CUT` | 10 / 10 | 更低的第二档与第二刀（必须低于 BATT_LOW） |

改错了不会生效 —— 数值会被夹回合法范围，调速器名只认白名单里的词。

> 旧版本的 `govs.saved` 可能把模块最后写入的调速器当成原值。升级后如果选「不干预」仍是老调速器，
> 说明原厂值已被旧快照覆盖：按机型手动选一次原厂 governor，再切「不干预」即可。
> 修复后的版本启动时会先按快照恢复、再取基准，不会再覆盖。

**只对全新安装生效**。升级安装一律不碰用户配置——用户刻意填的 65 可能刚好等于
旧默认值，用"值等于默认就覆盖"的启发式会把它改掉。
覆盖安装的人想用新预设，去「CPU / GPU 封顶」页点**省电**或**均衡**：后端按当前 SoC
重新匹配 `adapt/*.conf`，把对应档位的值填进控件；没有匹配的芯片时显示「无」，两个按钮都置灰。
两种预设都只填入控件，点「保存并生效」才写盘。

两档的定位：

| 档位 | 目标 | 性能保留 | 适用场景 |
|---|---|---|---|
| **省电** | 日常调度能触碰到的最低实用频率 | 45%~55% | 刷视频、社交、浏览、出差保电 |
| **均衡** | 日常无感的上限，只砍顶档浪费 | 60%~70% | 默认日常、混合使用、多任务 |

两档都会随落四条策略（写进控件，随保存生效）：
插电不封顶（`CHG_UNCAP=1` / `CHG_PCT=100`）、发热不主动降（`TH_CAP=0`，发热交给
内核热管理）、PSI 不放宽（`PSI_ADAPT=0`，连默认的少借一档也不借）、
调度回限频（`STRATEGY=cap`；智能模式仍可在页面手动切）。
芯片默认值就是**均衡档**，和你打开配置看到的值是同一份，不存在守护 fallback 里的第二套。

省电/均衡的具体落档值在 `adapt/*.conf` 的 `preset_sav_*` / `preset_bal_*`；`default_*` 等于
均衡档。省电档不是能效最优点，而是“省电量最大的、性能还能忍”的工程取舍点。

应用分类默认值按芯片的三场景参数表（视频 / 社交 / 阅读）落档，写在 `adapt/*.conf`
的 `cat_*` 键里；没有表数据的芯片继续用省电预设偏移兜底。分类按场景覆盖当前封顶，
不再只压不抬，但熄屏、游戏、满血和专属应用档不覆盖。全新安装、仍是旧固定值
44/55/50、或仍是旧公式生成且未改过时重写；用户改过的 CPU/GPU 保留。
应用分类滑条只改页面草稿，点「保存分类参数」二次确认后才写入；三个分类的未保存
修改可以一起保存，也可以一键撤销。

8E / 8E5 / 8G5 都是 m=2 双簇，`CPU_PCT_MID` / `MID2` 在这类机器上不生效，适配文件只给
BIG/LITTLE；SM8975 是 m=3 三簇，中间簇映射到 `CPU_PCT_MID`，`MID2` 不生效。

**Find N5（SM8750 7 核，2+5）**单独走 `adapt/sm8750_7core.conf`：`#match brand=OPPO` +
`#match soc=SM8750` + `#match cores=7`，8 核的 SM8750 仍走 `sm8750.conf`。
默认均衡 62/78、GPU 46；省电 46/51、GPU 37。M 簇另设
`CPU_FLOOR_M=1785600`（1.7856GHz）——7 核的 M 簇只剩 5 颗，再往下压会让调度
把任务甩给两颗 L 核，同频 L 核每瓦性能更差，又慢又费电。这个下限对动态封顶、
智能、温控、电量偏移都生效。**暂时不写 `cpuset_*`**——7 核的 CPU 编号和禁用核
位置还没实测，照抄 8 核的 `0-7` 可能把不存在的核写进分区。拿到这台机的
`socfreqd probe` 后再补 cpuset 和细调百分比。
天玑 9400（1+3+4）、9500（1+3+4）、9600 Pro（2+3+3）也是三簇，同样用 BIG/MID/LITTLE。
SM8650 是四个频率域（两个 A720 簇峰值相同），`CPU_PCT_MID` 与 `CPU_PCT_MID2` 都写 66%；
如果内核把两个同频簇去重成一档，MID2 不生效，结果仍然是 66%。
天玑那三套的百分比是按"向下吸附后仍能落在目标 MHz 上"取的，不是纯算术占比：
例如 9500 的 Ultra 3000MHz 若写 71%，71%×4210=2989 会吸到 3000 以下一档；
写 72% 算出 3031，才能吸住 3000。GPU 同理（9400 写 34% 只有 548，写 35% 才够 550）。
百分比最终会向下吸附到频点表；换机型先用
`cat /sys/devices/system/cpu/cpufreq/policy6/cpuinfo_max_freq` 确认硬件顶点，
再看吸到的实际频率。候选值发布前仍按真机温度/续航曲线复测。

**升级时怎么处理**：一个 `default_*` 都不套，用户配置逐字节保留。
不靠"值等于默认就覆盖"的启发式——用户刻意填的 65 可能刚好等于旧默认值，
那样会被静默改掉。升级只追加配置里不存在的新键。`SCREEN_POLICY` 例外：
熄屏轻巡检改为常开后，存量配置在升级时统一改成 `cap`（只强制一次，写
`.screen_cap_default` 标记；之后手工改 `keep`/`uncap` 不会被再次打回）。

### 这台机上没有的那一档，不摆控件

骁龙 8 Elite 这类两档/三档芯片，`MID2`、`MID` 可能天生落空。
守护把这种情况报成 `coretier_CPU_PCT_MID2=`（空），页面对应的行**只留名字和
（未检测到）**：滑杆摘掉、百分比不显示、保存时也不写进 conf。
摆一个"调了也没用"的滑杆在那里，只会让人以为是自己设了没生效、保存出了问题。

反过来，**"检测失败"（守护版本旧或读不到）时滑杆照旧保留** ——
那种情况下我们并不知道这台机有没有这一档，不该替用户把控件藏掉。

## CPU 封顶后端（CAP_BACKEND）

默认 `auto`。主路径始终是 `scaling_max_freq`；检测到厂商自己的硬限节点时，
再叠加一层“第二道锁”，让 perf / 热控不容易把上限顶回去：

| 值 | 行为 |
|---|---|
| `auto` | MTK 有 `/proc/ppm/policy/hard_userlimit_max_cpu_freq`、`/proc/ppm/enabled` 为 enabled、且簇数对得上，就叠加 PPM；否则只用 sysfs |
| `sysfs` | 只写 `scaling_max_freq`，最保守；出问题时用它一键回退 |
| `ppm` | 强制 MTK PPM；节点不可用/写失败自动回退 sysfs |
| `msm` | 强制高通 msm_performance；**实验性**：不同内核/厂商对“清除某个 CPU 限制”的语义不一致，恢复可能不完整，只建议测试用；节点不可用/写失败自动回退 sysfs |

约束：

- 第二道锁只在 sysfs 写成功后跟着写；不会单独抢在 sysfs 前面改频。
- 游戏、熄屏解除、停用、卸载、崩溃重启都会按账本还原；厂商已经改过的值不动。
- PPM cluster 号默认按 policy 顺序映射。`socfreqd probe` 会打印 `ppm_map=...`；
  如果簇数对不上，`auto` 会直接回退 sysfs，不会冒险压错簇。
- 这是隐藏键，页面不摆开关。改完要重启守护（或重启手机）才生效。
- 想看现场：`socfreqd probe | grep -E 'capbe|ppm_|msm_'`。

## 智能调度（STRATEGY）

`STRATEGY=cap` 是原来的固定百分比封顶；`STRATEGY=smart` 打开六态状态机：

| 状态 | 目标 |
|---|---|
| 深度空闲 | 天花板 ×45% |
| 浅空闲 | 天花板 ×65% |
| 中载 | 天花板 ×85% |
| 重载 | 天花板 ×100% |
| 持续高载 | 天花板 ×80% |
| 游戏 | 天花板 ×100% |

双簇机型（m=2，如 SM8750 / SM8850）单独一套：主簇 55/75/90/100/85/100、
超大核 40/60/80/100/70/100。没有中核缓冲，主簇压太狠会把轻中载线程推到漏电
更高的超大核，反而更费电；主簇上浮让 90% 的日常负载留在主簇里消化。
m=1/3/4 保持通用比例。

每 2 秒读一次 `/proc/stat` 和 GPU 占用；CPU 用全核平均，GPU 走 KGSL/MTK 节点。
升档 2 拍确认（4s）、降档 5 拍确认（10s），中载↔重载/持续高载多要 1 拍确认；
重载驻留 4 拍（8s）、游戏 13 拍（26s）、持续高载 12 拍（24s）。
CPU 80/60%、GPU 90/80/65% 带迟滞；前台是视频/社交/阅读时，GPU 单指标不再进游戏态。
每状态 GPU 上限 40/45/60/85/80/100%，只和全局/分类/应用 GPU 取更低；电池电流/功率只写状态，不参与选档。
「高级阈值」只开放 `FSM_TEMP_IN` / `FSM_TEMP_OUT`（压频起始 / 松手，默认 54/48℃）；
CPU/GPU 80/60、升降窗口、驻留等按内置参数固定，不再暴露英文内部键。
页面「六态参数」可逐状态调 BIG/其他核 CPU 上限、下限和 GPU；下限 0 = 不设，非 0 会覆盖 `CPU_MIN_PCT`。阈值、升降窗口和驻留也在同一页。
温度超过 `TH_HIGH` 且处于重载时进持续高载，回到 `TH_LOW` 以下才退出；亮屏/切前台后 45 秒内不吃热降档。
PSI 争用、皮肤/外壳温也参与选档；ADPF 从 `/data/adb/soc_freqcap/adpf` 读 0-100，30 秒内新鲜才生效，没有 companion 写入时自动忽略。
状态里的 `src` / `gsrc` 报 CPU/GPU 当前来源，`fsmrs` / `fsmw` 报切换原因和还差几拍，`hr` / `hrv` / `hrs` / `hrh` 报厂商上限余量、是否可信、软钳/硬钳。
### 日志精简（`LOG_VERBOSE`，默认 0）

默认只打"变化"：同一簇的「档位/意图/生效/封顶」值没变就不再打、同一批 cpuset 节点
不重复报"已还原"、`→ 常态封顶` 只在从游戏/满血/熄屏回到常态时打一次、平台下限夹回
同一簇 60 秒最多一条、`下限原值顶住封顶` 每簇只报一次、预热和状态切换不再各打一行。

排查"为什么是这个值"时把 `LOG_VERBOSE` 改成 1（隐藏项），恢复每拍明细。

### 前台检测（1:1 Kin `getTopAppFast`）

- 主路径：读 `/dev/cpuset/top-app/cgroup.procs`（优先）→ `/dev/cpuset/top-app/tasks`
  → `/proc/<pid>/cmdline`，剥掉 `:xxx` 后缀；**300ms 缓存**，空结果也缓存，
  不 fork、不 dumpsys；
- 黑名单：桌面（各种 `*launcher*`、`com.miui.home`）、输入法、systemui、phone ——
  命中时按"没有前台应用"处理，**不再回退 dumpsys**；
- 取不到时用 **2 秒内的 last_good**，并要求它仍出现在 top-app（小窗盖住游戏时游戏仍在）；
- 以上都拿不到才走原来的 dumpsys 解析（手动/兜底路径）。

### 下限只有一个写入口（floor arbiter）

以前 `scaling_min_freq` 有 5 个写手（下限锁、跟随下限、包络下限、压制静置、交权还原），
互相能顶住。现在改成**请求 + 仲裁 + 唯一写**：

| 优先级（高→低） | 来源 |
|---|---|
| 1 | 用户 `CPU_MIN_PCT_*` |
| 2 | 智能状态包络下限（ASB clampFloor） |
| 3 | 跟随下限（限频模式，`CAP_MIN_FOLLOW`） |
| 4 | 动态压制静置下限 |
| 5 | 硬件最低 |

`floor_pick()` 取最高有效请求 → 过窗口守护（至少比封顶低 N 档）→ `floor_commit()` 唯一写入
（记账、1 拍后复核、平台夹回退避都在这里）。任何新功能要动下限，只提交请求，不再直接写节点。

### 热源决策 / 相机保持 / zTT / 游戏 cpuset

- **热源决策**（移植 Kin `ThermalDecision`）：皮肤 5–70℃ 时按 `皮肤+(60−47)` 对齐结温刻度，
  结温 ≥100℃ 强制到 veto；**两源打架**（结温到硬顶、皮肤侧仍认为没到）时，负载驱动的状态迁移
  多要一拍确认，热降 SUSTAINED 不受影响。
- **相机保持**：相机在前台 → 封顶软钳到 `hwmax × CAMERA_HOLD_PCT%`（默认 80），不冲满。
- **zTT 联合决策**：GAMING 且 GPU≥90、同时热受限（CPU 温度 ≥ 压频起始或 ADPF ≥85）→ 大核再削 8%。
- **游戏 cpuset 矫正**：游戏态发现 `top-app/cpus` 被收窄 → 写回全核（`/dev/cpuset/cpus`、
  `top-app`、`foreground`），1 秒节流防乒乓。

### 游戏免打扰 / WiFi 省电

- **`GAME_DND=1`**：进 GAMING 前读 `settings get global zen_mode` 记住原值，切到 1（仅优先）；
  离开游戏/交还系统/守护退出时还原。读不到（无 settings、命令失败）就完全不动作；
  本来就是「仅优先」时只记在位、不记原值，还原时不写。
- **`WIFI_PS`**：`auto` = 不动；`on`/`off` 写 `/sys/module/wlan/parameters/wlan_pm`，
  写前记账，守护停止时还原。

> 没有做厂商性能限制组件恢复（perfd/thermal-engine 替空还原、emul_temp 清零）——按你的要求撤掉了。

### 探测节流 / 夜间静默 / 空闲 uclamp / 画像

- **探测节流**（`PROBE_CADENCE`）：只有"游戏不是顶层包"时才需要扫多窗口，按活动度分 8s/25s/120s
  三档缓存（ASB V64 同思路），省掉大量 dumpsys fork；关掉就回到每次强制扫描。
- **夜间静默**（`QUIET_NIGHT`）：学到的夜间窗口（或固定 23–6）里息屏，巡检间隔拉长到
  `QUIET_NIGHT_S`（默认 300s），屏幕唤醒检测也随之变慢——夜里没人看屏幕。
- **空闲 uclamp**（`IDLE_UCLAMP=18`）：息屏把 `background` / `system-background` 的
  `uclamp.max` 收到 18%（只压不抬，写进账本，亮屏还原）。对应 ASB V64 的 DEEP_IDLE 背景封顶：
  一个被唤醒的同步任务不能再向调度器要三成峰值算力。
- **画像自动匹配**（`APP_PROFILE`）：前台应用按 `游戏名单 → 视频/社交/阅读 → 其他(tool)` 自动归画像；
  显式 `app_modes.conf` 档位优先。「其他」档的数值用 `app_categories.conf` 的
  `tool_cpu` / `tool_cpu_big` / `tool_gpu` 配（默认 0 = 不覆盖）。切换时会打
  `前台: com.x → 画像档[tool]`。

### 智能模式会学习（`FSM_LEARN`，完整 ASB Smart）

不是简单的"一次会话调一点"，而是 ASB 那套分桶学习：

**分桶**：`bucket = daypart*2 + 是否周末`，共 12 个。
daypart 六段：睡(0-6) / 醒(6-9) / 上午(9-12) / 白天(12-17) / 傍晚(17-21) / 深夜(21-24)。

**一次会话**（亮屏→熄屏）结束后：

1. 信任分级：<60s / <3 拍 / 充电中 = 脏（直接丢弃）；夜间时段 = NOISY(15)；
   凉爽且采样足 = CLEAN(100)；其余 PARTIAL(40)；
2. `obs += 时长权×信任权/100`（时长权 25/50/100/125，按 10/30/90 分钟分档），
   每会话按 97% 滑窗衰减、上限 4000；
3. 方向信号：极热(≥80℃)+80 / 热(≥70℃)+40 / 掉电>14%·h⁻¹ 或均流≥1200mA +30 /
   持续重载 +20 / 热否决(≥60℃)+100 / 干净凉快 −60；
4. `alphaRaw += dt × FSM_LEARN_RATE/1000`，**不钳 0..1000**（证据可继续累积）；
5. 置信度 `conf = obs/800 × 衰减`（7 天内 100%，7→37 天线性到 30%，之后 0），
   桶内 dt 波动大（MAD）还会再压一档；
6. 生效值 `alpha = 500 + (raw−500) × effScale/1000`，effScale 按 conf 分三段
   （<350 → 250；350~650 → 250~600；>650 → 600~1000）。

**回退链**：EXACT → 反周末同时段 → 弱 EXACT → 同时段类（夜/日/傍晚）→ 全局 → 中性 500。

**覆盖层**（只上抬，安全优先）：夜间息屏未充电 → α≥900；低电 ≤20% 未充电 → α≥800；
皮肤锚定温 ≥60℃ → α≥700（45~60℃ 之间线性 +150）。

**探索**：已过门控的桶有 4% 概率给本会话 ±60 的扰动；会话结束按实测均流与该桶基线比，
省电侧真省到奖 +8、没省到罚 −8，性能侧反之。

**覆盖层（第二组，全部按 ASB 语义）**：

- 低电：≤`BATT_LOW` 闩住、≥40% 或充电才解除；危急档（≤`BATT_CRIT`）α≥900，普通低电 800；
- 充电：电池 ≥41.5℃ → α≥800（护温）；息屏 → α≥850（满速充）；亮屏且凉(<39℃，超快充 38℃)
  且没有夜间/低电/热否决 → α≤450（充电不缺电，去掉省电延迟）；
- 热趋势：30 秒窗口算升温斜率（m℃/min），常规 45℃/3000 起、热 App 40℃/2000、边充边玩 38℃/1500，
  满斜率 +120；斜率 ≥6000 时给该前台 App 记一笔「热 App」（16 条表，按天衰减）；
- 内存压力：`/proc/pressure/memory` avg10 ≥20 → +100，≥5 → +50（只亮屏）；
- 厂商软钳：headroom 可信且软钳时 +40，不去硬拼厂商热钳；
- alpha 不再钳 0..1000，频率侧由 `fsm_scale_khz` 钳到 [本机最低, 本机峰值]。

**持久化**：`run/smart_learn.conf`（12 桶的 alpha/obs/last/一致性/基线），重启接着学。
日志：`智能学习：桶7 alpha 512→520（dt=40 lr=80 探索=0 ...）`；
状态里 `alpha` / `acnf` / `abkt` 分别看生效值、置信度、当前桶。

### 限频模式的"跟随下限"（Scene 式，`CAP_MIN_FOLLOW`）

Scene 那种"min/max 都在动"不是锁频，而是在推 cpufreq 的**窗口**：

- `scaling_max_freq` 决定 governor 能升到哪（功耗/温度上限）；
- `scaling_min_freq` 决定能降到哪（响应地板）；
- 两端都动 = 控制实际工作带；只有一个值（min==max）= 关掉 DVFS，空载也跑那个频点。

我们的限频模式默认开了跟随下限，上限仍是 `CPU_PCT_*` 封顶：

| 负载 | `scaling_min_freq` |
|---|---|
| < `CAP_MIN_LO`（30%） | 硬件最低（让 governor 随便降） |
| ≥ 30% | 封顶 × `CAP_MIN_PCT_LO`（45%） |
| ≥ `CAP_MIN_HI`（70%） | 封顶 × `CAP_MIN_PCT_HI`（75%） |

带 30/70 回差防抖，且始终至少比封顶低 `MIN_WINDOW_STEPS` 档（窗口守护），
不会把窗口压成一个点。`CAP_MIN_FOLLOW=0` 回到"下限永远是硬件最低"的老行为。
智能模式不用这套（它的下限来自 FSM 包络）。

### 智能模式的封顶曲线（对齐 ASB / Kin）

`FSM_BOUNDS=1`（默认）时，六态不再按"用户天花板的百分比"查表，而是走
AutoSystemBoost 的频阶模型：

```
状态级别 LEVEL = {0, 0.15, 0.45, 0.72, 0.62, 1.0}   // 深/浅/中/重/持续/游戏
上限 = lerp( battery包络, balanced包络, alpha ) 在该级别上的值
       → 按本机 cpuinfo_max_freq / SM8650 参考峰值缩放（空闲不动，重载才吃满）
下限 = 同一包络的下限，钳到本机 cpuinfo_min_freq
```

- `FSM_ALPHA`（0~1000）：0 = 均衡包络，1000 = 省电包络（整体下移一档）；
- `HEAVY` 与 `SUSTAINED` 的级别差（0.72 vs 0.62）保证热降档不会反而抬频；
- 用户 `CPU_PCT_*` 仍然是**硬天花板**：模型给的再高也不会越过它；
- 用户设了 `CPU_MIN_PCT_*` 时下限用用户的，模型下限让位；
- `FSM_CUR_HEAVY/FSM_CUR_MOD` 是 ASB 的电流闸门（默认 150/120mA）：放电时才生效，
  充电或读不到电流自动旁路；
- 热源默认只用 CPU 温度（进 54℃ / 出 48℃），皮肤温与 ADPF 默认关；
- `FSM_BOUNDS=0` 可退回旧的百分比模型。

### 日志：与 Kin 对齐的「前台」行

智能模式下，**前台变化 / FSM 状态切换 / 亮屏 60 秒心跳**都会打同一行（格式取自
`kin-daemon` 的 `scheduler.hpp`）：

```
前台: com.tencent.tmgp.sgame 类型=0 FSM=GAMING
前台: com.ss.android.ugc.aweme 类型=2 FSM=MODERATE
前台: com.android.launcher 类型=-1 FSM=LIGHT_IDLE
```

- `类型` 用 Android `ApplicationInfo.CATEGORY_*` 枚举：`0`=游戏（命中游戏名单）、
  `2`=视频、`4`=社交、`5`=阅读，`-1`=未知；
- `FSM` 是英文状态名：`DEEP_IDLE / LIGHT_IDLE / MODERATE / HEAVY / SUSTAINED / GAMING`；
- 详细指标仍是原来的 `智能模式：负载 x% / GPU y% → 中载（大核 36% / 其余 45%）` 行，
  两行配合看：一行看"谁在前台、在什么状态"，一行看"为什么切、给了多少"。

**切前台首拍**直接预热到 `APP_SWITCH_TIER`（默认 2 = 中载 85%），冷启动/首屏
不用等负载爬升；只升不降，下一拍起回到正常迟滞。亮屏和 cap→smart 边沿也会
预热一次。连续 2 拍目标空闲、且各簇实际频率都低于当前封顶一半时，直接从
2/3 档回空闲档，不再逐档衰减。
**超大核单独收档**：m≥2 时，最高频簇还会按它自己的占用档向下钳（带迟滞），
主簇忙但超大核闲置时不会把超大核顶到高帽；预热那一拍不钳，避免冷启动被旧低占用抵消。
每簇按自己的 `CPU_PCT_*` 当天花板，m=3/4 机型的中间档也一样；重载就是天花板。
百分比先按硬件最高频算，算完再压回厂商原始上限（`nodes.saved`）；厂商自己压低上限时保留更低值，不再抢写。智能模式不套升降频限速，调频交给 governor 和 FSM 的封顶。
判定周期是 2 秒：滑动、相机启动这类几百毫秒的突发，仍比不上限频模式动态封顶的 1 秒快拍；
智能模式更适合长时间省电。
智能模式不叠 PSI 向上借额度，也不吃实时温控；电量阶梯和插电地板仍保留。插电时充电地板会抬高目标，省电对比请拔电。

游戏、满血、熄屏交还三条路径两种策略完全一样，仍然按原逻辑交还系统；
交还时只撤模块自己写的上限——厂商游戏助手/热控已经把上限压得更低时保留它，
不会在进游戏的一瞬间把帽抬回硬件最高。
交权时连**调速器**一起还原成模块接管前的名字（账本保留），回常态再按你的选择写回去——
不然选过 powersave / conservative 的机器，游戏里仍跑着模块那个调速器，"官方调度"其实没恢复全。
## 分应用档位（app_modes.conf）

`/data/adb/soc_freqcap/app_modes.conf`，一行一条 `包名=值`：

| 值 | 含义 |
|---|---|
| `full` | 这个应用在**前台时**整个交还系统（CPU 和 GPU 都不封顶） |
| `1~100` | CPU 四簇统一按这个百分比封顶；**GPU 仍按全局的 `GPU_PCT`**（老写法，语义不变） |
| `80:40` | CPU 80%、GPU 40%，两段各自吸附到实际频点 |
| `80:` / `:40` | 只设一边，另一边跟随全局 |
| `70/50` | 大核 70%、小核 50%；中间档跟随全局（2 簇机型就是大小核两档） |
| `70/50:40` | 在大/小核之外再给 GPU 单独设 40% |
| `keep` | 熄屏那一刻在这个应用前台时不交还系统，继续按全局百分比巡检 |
| `soff` | 熄屏那一刻在这个应用前台时交还系统，亮屏仍按全局百分比；熄屏轻巡检不查前台，后台下载/后台音乐/闹钟不在前台时仍吃全局 `cap` |

优先级：**游戏名单 > 满血窗口（开机 / 熄屏解除）> 应用专属 > 全局百分比**。
应用专属排在满血窗口之后是有意的——熄屏解除是用户主动开的全局开关，
屏幕都灭了还守着某个相机的 80% 没有意义。`soff` 只影响熄屏那一拍：
要看"熄屏瞬间的前台包"，不是整晚盯着进程，所以它不能替代"后台任务别被限频"
这类全局放行。

典型用法是把相机、录像、地图设成 `full`：这些应用要吃完整性能，
而它们本来也不在"日常待机节流"的目标场景里。想反过来压住某个应用的 GPU 发热
（比如录像、长时间导航），用 `70:40` 给 GPU 单独设一道比全局更低的帽；
GPU 段吃温控、电量阶梯和插电地板，不吃 PSI 借出。

守护按 mtime 热重载，改完就生效，不用重启手机。写的一侧（`api.sh` / WebUI）
有校验：坏包名、越界数字直接被拒；读的一侧（守护）对坏行是**整条忽略**，
不是当成 0%——手改文件写错不该让手机突然变成砖。

WebUI 的入口在「应用 → 分应用档位」（和名单、候选栏在同一页，都是按应用定的事）：
先选一个 CPU 档位（满血 / 90 / 80 / … / 50 / 40 / 30 / 分核 / 自定义）和 GPU 档位（跟随全局 / 90 / … / 自定义），
选「分核」时填大核和小核两个百分比（1~100），例如 `70/50`；
按「＋ 添加应用」展开**已安装应用列表**：默认是第三方应用 + 系统里有桌面入口的那些
（相机、设置、相册、信息…）。列表下面有**「显示系统应用」**开关：勾上连 provider / 服务 /
组件一起列，给"要选某个系统包、但默认列表里没有"的机器用。部分 ROM 把
`cmd package query-activities` 裁掉了，后端会自动回退到全部系统包，不会只剩第三方。
点一下就写入；已经设过的行有两个下拉，CPU 和 GPU 可以分开改，× 删除。

系统应用在 APK 里的名字常是英文（OPPO 相机叫 `Camera`、设置叫 `Settings`），
所以搜索框做了中文别名：搜「相机 / 设置 / 时钟 / 相册 / 文件 / 联系人…」都能找到。
**别名只影响搜索，不改显示名**——名字仍以 APK 里的 `android:label` 为准，不替厂商翻译。
APK label 解析不出来（引用型 label / 资源被裁）的包，用 `scripts/builtin_labels.txt` 的
中文名兜底；只填空白，不覆盖已有英文名。列表先画 80 行，滚到底点「显示更多」再追加；
滑动时暂停批量取图标/名字，停手后再发 root 调用，避免在管理器里滑起来一卡一卡。
深睡页的「永久豁免」默认也只列第三方；同一个「显示系统应用」开关打开后可以选系统包，
厂商短信 / 电话这类不在 `-3` 里的包就能手动加。

**相机类默认满血。** 装机时按 `scripts/builtin_modes.txt` 里各家相机的包名
（`com.android.camera`、`com.oplus.camera`、`com.sec.android.app.camera`、`com.vivo.camera` 等），
只给**本机已安装**的那些追加 `pkg=full  #builtin`。取景、快门、连拍、4K 录像都吃瞬时响应，
相机在前台本来也不在"日常待机节流"的目标里。这份清单**不覆盖你的选择**：

- 已经给这个包设过任何值（哪怕手写 80）→ 不动；
- 删掉那一行 → 以后升级不会塞回来（基准 `builtin_modes.base.txt` 记着上一版清单，
  只有**新版清单里新增**的包才会补）；
- 想换回百分比或 `keep`，直接在「分应用档位」里改即可。

这里不能做"把**当前前台**应用设为满血"：这一页是在管理器里打开的，
那一刻守护抓到的前台**永远是管理器自己**，那个按钮唯一能设的对象就是管理器。
现在首页连"当前前台是哪个"都不显示了（上一段说了原因），
要设档位就在应用列表里自己挑。

命令行同理（走的是同一个 `api.sh`，所以校验也一样）：

```sh
A=/data/adb/modules/soc_freqcap/webroot/api.sh
sh $A modes_list                          # 看现在设了哪些
sh $A modes_set com.android.camera full   # 相机满血
sh $A modes_set com.autonavi.minimap 80   # 地图按 80% 封
sh $A modes_set com.android.camera 70:40  # CPU 70%、GPU 40%
sh $A modes_del com.android.camera        # 删掉
```

直接编辑 `/data/adb/soc_freqcap/app_modes.conf` 也行，但坏行会被守护整条忽略
（不是当成 0%）——手改写错不该让手机突然不动。

**配置为什么不在模块目录里。** 管理器升级模块是「先删 `/data/adb/modules/<id>`
再解包」，配置放模块目录里就会被新包的默认值盖掉，用户调过的东西一次升级就没。
所以装在 `/data/adb/soc_freqcap/`（`customize.sh` 首次安装时搬过去，
`api.sh` 里还有一道兜底）。也没放 `/sdcard`：那里是 FUSE + `media_rw` +
MediaProvider 的一套权限，root 写进去的文件应用侧未必读得到。

**开机满血窗口**（`BOOT_FULL_S`）：`service.sh` 在等到 `boot_completed` 之后、
正式接管之前，往 `/data/adb/soc_freqcap/run/boot_boost_until` 写一个截止秒数
（读 `/proc/uptime`，不用墙钟——开机阶段时间会被 NTP 往前跳）。
守护在主循环里看到没过期就整个交还系统，到期后自己压回常态封顶。
开机动画、首屏加载、桌面重建挤在那几十秒里，封顶会让它明显变慢。

**熄屏轻巡检**（`SCREEN_POLICY`）：默认 `cap`，页面一个「熄屏保持封顶」开关。
开：保持封顶，只压回被厂商顶高的上限；下限压到硬件最低、不吃充电地板；
温控每 4 拍采一次。关：写 `uncap`，熄屏解除封顶、交还系统。
存量配置在升级时统一改成 `cap`（只强制一次），之后用户可以随时关掉。
高级用户仍可手工改成 `keep`（旧的全量巡检）。

| 值 | 熄屏后 | 周期 |
|---|---|---|
| `cap`（默认） | **保持封顶**，只压回被厂商顶高的上限；下限压到硬件最低、不吃充电地板；温控每 4 拍采一次 | `SOFF_INTERVAL` |
| `keep` | 保持封顶，但走亮屏全量路径（读温度/PSI/前台） | `INTERVAL` |
| `uncap` | 解除封顶、交还系统 | `SOFF_INTERVAL`，只读亮屏信号 |

`uncap`/`cap` 共用轻路径：不再 fork `dumpsys window`、不跑 PSI/前台识别，只读一个亮屏信号。
亮屏后立刻恢复常态巡检（`cap` 会把下限还原、充电地板重新生效）；
游戏/满血应用熄屏时保留原交权状态，不会先压一拍再解锁。
`cap` 是"待机也要省电"的默认档：夜里插电不会因为 `CHG_PCT` 被抬到 100%。

亮屏信号的选择：启动时自动挑 `fb0/blank`（0=亮），没有就挑任意
`backlight/*/brightness`（>0=亮）。实测在一加 13 / Android 17 上 `fb0/blank`
不存在，且锁屏亮屏时 `dumpsys window` 仍是 `mSleeping=true`（keyguard token），
所以不拿 `mSleeping` 当判据；亮度节点 0/1127 与 `mWakefulness` 完全一致。
节点读不到时退 `dumpsys power` 兜底；任何判据都失败时按「亮屏」处理——
探测失败的后果是维持封顶，不是悄悄放开。

`SOFF_INTERVAL` 只影响熄屏态的亮屏检测延迟（新装默认 30s）。想要旧的熄屏全量巡检
就手工把配置改成 `SCREEN_POLICY=keep`；页面只提供「保持封顶 / 交还系统」两档。

**深度空闲（P0b）：** 熄屏后电流持续低于 `IDLE_CURRENT_MA`（默认 250mA）达到
`IDLE_HOLD_CYCLE` 轮，巡检周期从 30s 拉到 `IDLE_INTERVAL`（新装默认 60s）。亮屏信号仍每轮读，
电流只做辅助：比熄屏 EMA 基线高出 `WAKE_DELTA_MA`（默认 150mA）时才多问一次
`dumpsys power`，不拿绝对阈值。电流读不到就停在 SCREEN_OFF，永不进深睡。
电流单位默认 `BATT_CURRENT_UNIT=auto`，按量级识别；也可以显式写 `ua`/`ma`。
一加 13 实测是 mA 且充电为负，代码统一取绝对值；明显是 µA 的超大读数会自动纠正。

**分应用 `keep`：** `app_modes.conf` 里写 `包名=keep`，这个包在熄屏那一刻是前台时
**不交还系统**，继续按全局百分比做轻巡检（只读频率节点、被顶回就压回），适合 Termux
编译、挂机下载。它只影响熄屏，亮屏时仍按全局分档。

## 动态封顶（默认关，一个开关 = 完整压制）

仅 `STRATEGY=cap` 生效；智能模式由六态 FSM 独占，动态封顶整体让位。
开关在「Boost 与压制」页。参考能效曲线哲学：预设值是最优解，压制不压低它，
只管"不许无谓地越过它"。打开后下面这组一起生效——全部节点存在才写、值记进
账本，进游戏/满血/熄屏交还时自动还原，卸载按账本恢复：

1. **动态天花板（三档）**：亮屏常态把巡检切成 1s 快拍，天花板在最优解、中间档、风格地板之间收放——持续低载先降到中间档，再连续低载才到地板；持续高载（排除 CPU0 的负载，地板 60 / 中间 75）先放一档，仍高载下一拍才回最优解，换档后先稳 6 秒，低于地板线才继续降，避免单次滑动/切屏或渲染帧毛刺把天花板拉回满频。不再用 `cur_freq` 贴顶判饥饿：静置档 960MHz 本身就是当前频点，按贴顶判会自激振荡。**省电风格的地板是绝对 960MHz**：按该簇真实频点向上取整，不低于硬件最低频，也不越过用户封顶；所有芯片同一套规则，不需要逐颗写表。动态封顶的负载统计排除 CPU0（多核机型），避免小核常驻任务把整机算成"一直很忙"；智能分档仍按全核口径；
2. **静置压下限**：到地板且持续低载 5 拍，把各簇 `scaling_min_freq`
   压到硬件最低（省电风格同样如此，960MHz 上限配硬件最低下限才能让
   调度器真正闲下来），活动立即还原。省电静置档期间「CPU 下限锁到底」的
   亮屏巡检自动让位（两条路都写 min 会互相还原）；均衡档两者目标是同一个值；
   熄屏的 `cpu_min_to_floor` 不受影响；
   超大核和其他簇一样按百分比收（不再无条件钉到最低）；手动开 `BIG_MIN=1`
   时才会把超大核压到硬件最低；
3. **walt 拉频源中和**（高通）：`input_boost_ms` / `sched_per_task_boost` /
   `sched_boost` 写 0——触摸瞬间顶频率的源头（`input_boost_freq` 是频点表，
   数值账本无法原样还原，暂不写）；压制期间每个 1s 快拍补写，防止系统在切前台/
   亮屏时把 `input_boost_ms` 恢复成 100；
   其他 SoC 没有这些节点自动跳过；写入一次不对抗厂商后续行为；
4. **调度下限 uclamp.min**：`/dev/cpuctl/{top-app,system,cpu,foreground,background}/cpu.uclamp.min`
   存在时压到 0，降低前台/系统任务的“最低性能请求”；cgroup 布局不同的机型
   没有这些节点就跳过，不猜路径；
5. **升/降频限速（按簇）**：各簇调速器 `up/down_rate_limit_us` 写入。
   默认值跟随压制风格自动换表：**均衡所有簇升 500 / 降 0µs，省电所有簇升 3000 / 降 500µs**；
   意图是“均衡响应快、掉频也快；省电升得更慢，换频更平滑”。
   `GOV_UP_*` / `GOV_DOWN_*` 是手动基准：某一簇改成别的值后按你的值，
   没改的簇继续跟随风格。旧键 `GOV_UP_US` / `GOV_DOWN_US` 仍兼容：
   某簇没写新键时按旧键统一值。升频 0 会夹到 100µs；降频允许 0，表示不额外限制降频步进。
   walt / interactive / schedutil（含 MTK sugov_ext）通用，按各簇实际
   调速器名找节点；厂商自有调度器（hmbird/scx）不碰；
6. **uclamp.max**：0/1/2 档分别把 `top-app / foreground / dex2oat` 的
   `cpu.uclamp.max` 压到 85/65/45、70/50/30、60/40/20。节点回读
   `max` / 小数 / ≤100 时按百分比写，>100 时按 0–1024 换算；
   其他回读值不猜刻度，直接跳过（避免把 60 当成 5.8%）。原值
   （可能是 `max` 或 `50.00`）单独记在 `uclamp.saved`，还原时原样写回。
   后台两组（`background` / `system-background`）拆成常驻项 `BG_LIGHT`，
   默认开、页面无开关，不再随 SUPPRESS 档位走；
7. **cpuset 前后台分区 + 分级 hispeed**：探测到 policy 后按实际拓扑生成，
   写 `/dev/cpuset/{top-app,foreground,background,system-background,restricted}/cpus`：
   top-app 全核；foreground / restricted 去掉最高频 BIG 簇；system-background
   优先取最低频簇，不足 4 核时用次低档补满；background 同序补到 3 核；有多档时
   两者都不碰 BIG。7 核 8 Elite、Tensor G5/G6、骁龙 8 Gen3、天玑 9600 Pro、
   10 核猎户座 / 玄戒都按实际 policy 生成，不写死 CPU 编号；写入前再按 present 裁剪。`adapt` 里的
   `cpuset_*` 只作为探测不到 policy 时的兜底，`background` 不再由 `BG_LIGHT` 覆盖，
   hispeed 仍只对有适配数据的芯片写，
   并在中间/地板档按 `gov_lv1/lv2_cl<N>_hispeed_ratio / hispeed_load`
   写各簇调速器（0 档不额外改）。`hispeed_ratio` 是千分比
   （对位 JSON 的 `hispeed_freq / 该模式上限`），按我们当前档的封顶
   换算，不会因为绝对值高于我们的百分比封顶而被整簇跳过。`clN` 按
   policy 号升序；SM8650 的两个同频簇用 `clN` 写法，不会被 tier
   去重吃掉。只写 `cpus` 掩码，不搬任务；没有 hispeed 数据的芯片不碰调速器。

`core_ctl` / `migt` / `metis` 这类核心拓扑和厂商调度参数没有跨芯片通用值，
本版不写；`cpuset` 只在探测到 policy 时写 `cpus` 掩码，不移动
`tasks`/`cgroup.procs`。节点不存在或语义不一致时直接跳过，避免把别的
机型的参数套到本机。

**与其它功能的边界**（避免互相拉锯的规则）：

- **插电暂停**：插电时压制自动暂停并交还——"插电不封顶"是既定策略，
  压制的相对阶梯此时会把满频按 80% 压住，与策略矛盾；拔电下一拍恢复。
- **CPU 下限锁到底**：压制开启期间，亮屏的下限巡检由压制的"低载静置
  压下限"接管（`cpu_min_patrol` 让位），两条路都写 min 会互相还原；
  熄屏的 `cpu_min_to_floor` 不受影响。
- **实时偏移（PSI/温控/电量）**：同向叠加、无对抗——偏移改的是生效
  封顶，压制的阶梯以"当前生效封顶"为 100% 跟随；PSI 借出/温控收紧后
  压制地板随之浮动。插电时压制本身暂停，充电地板不与阶梯叠加。
- **内核钳制退避**：目标低于某簇实际下限（如 BIG_MIN 或小封顶机型）
  时记住回读值并退避 600s，不做每秒一次的无效写入。

**压制风格**（`SUP_STYLE`，开关下方可切）：

| 风格 | 中间档 | 地板 | 低载降档 | 高载回升 |
|---|---|---|---|---|
| `bal` 均衡 | 90% | 80% | 连续 3 拍 <20% 逐级降 | 连续高载（地板 60 / 中间 75）先到中间，仍高载回 100% |
| `sav` 省电 | 85% | 960MHz（真实频点向上取，不低过硬件最低） | 连续 2 拍 <20% 逐级降 | 连续高载（地板 60 / 中间 75）先到中间，仍高载回 100% |

「省电 / 均衡」两个预设按钮会一并打开动态封顶并把风格切到对应档；如果随后切到智能模式，动态封顶不生效，但开关仍可切换并保留选择，切回限频后按这个开关恢复；
只想改封顶百分比、不想开压制的，手动把开关关掉即可。`sav` 的地板固定
960MHz，不随芯片档位表变化；Find N5 的 `CPU_FLOOR_M=1785600` 仍优先，
M 簇不会被压到 1.7856GHz 以下。

`sav` 的 0 档附加层也按均衡组走（uclamp 70/50/30，cpuset 五组仍按本机拓扑生成），
1/2 档按省电组；`bal` 的 0 档才用性能组。这样选省电风格时，活跃的 0 档不会仍挂着
性能组的 85/65/45 和前台性能掩码。

附加层与档位对应（0/1/2 档 = 性能/均衡/省电，换档/关闭/交权全部还原）：

| 档位 | uclamp.max（top / fg / dex2oat） | cpuset（按本机拓扑） | hispeed（有数据芯片） |
|---|---|---|---|
| 最优解 0 | 85 / 65 / 45 | top 全核；fg / restricted 去 BIG；sysbg 补足 4、bg 补足 3 | 不改（最优解） |
| 中间档 1 | 70 / 50 / 30 | 与 0 档相同 | 均衡档参数 |
| 地板档 2 | 60 / 40 / 20 | 与 0 档相同 | 省电档参数 |

SM8750 的 hispeed：中间档超大核 1958MHz/大核 1786MHz（load 80），
地板档超大核 1402MHz/大核 1363MHz（load 90）；SM8850 对应
1978/1786MHz（load 80）和 1382/1114MHz（load 90）。0 档不改调速器
（性能档 hispeed 高于日常封顶，写了也是无效工作点）。超大核按百分比
收之后，它的 hispeed 也会按当前封顶换算；低于当前下限或高于封顶时跳过。
**省电风格的 960MHz 地板档会把各簇 `hispeed_freq` 写 0**，否则调速器
一见负载就把频率抬回硬件上限，静置低功耗无从谈起。数值写在
`adapt/<soc>.conf`，还没有数据的机型不写这三层。

压制只在 `STRATEGY=cap` 时生效，叠加在分应用档位之上（以算出的生效封顶为 100%）。智能模式下动态封顶整体让位。
开启后若卡顿明显，把封顶放回预设值或关掉压制。

## 实时偏移（PSI / 温控 / 充电态）

这一节管的是**这一刻该不该让路**。三条各自独立记账，
合成一个偏移加在生效值上：

```
CPU 生效封顶 = 设定值（插电时先抬到 CHG_PCT）+ PSI 借出 − 温控压回 − 电量阶梯（智能模式只保留电量阶梯）
GPU 生效封顶 = 设定值（全局 GPU_PCT 或应用 GPU 档）− 温控压回 − 电量阶梯（智能模式只保留电量阶梯）
```

合计偏移还有一对总闸（`ADAPT_UP_MAX` / `ADAPT_DOWN_MAX`，默认 +15 / −30），
防止每个来源都不越界、叠起来却把 65% 压成 5%。

**只改生效值，从不写配置文件。** 滑杆上显示的就是你设的那个数，背后没有第二个东西在偷偷改它。

**功能页不摆术语。** 三张卡各自只有一个下拉框：「插着电的时候」「机身发热的时候」「CPU 排队偏高的时候」，
选项写的是行为（不封顶 / 早点降 / 少借一点），不是参数名。具体数值收在每张卡的
「自己定」里，**范围一个都没缩** —— 手动改过之后下拉框会自己变成「自己定的值」，
不会继续谎称你还在某一档。页面顶上还有一句按当前值现算的话：
「插电　插着电时不封顶，拔电自动恢复 / 发热　到 75℃ 开始一档档降，最多比设定低 25%…」。
首页那一行同样先给人看的那句（`现在比设定值低 10%　机器发热，正在降速保护`），
`stall / ms/s / 几档` 这些原始读数放在后面一小段淡色文字里，截图反馈问题时用的就是它。

### 充电态（默认开）

`/sys/class/power_supply/battery/status` 是 Charging/Full 时，把常态封顶至少抬到 `CHG_PCT`（默认 100），
拔电自动回落 —— 插着电发热由充电器承担，压它没有意义。三条边界：

- **温控优先**：本拍有收紧（温控/电量）时不抬地板——65% 设定 + 温控 −25 = 40%，
  不会变成 100−25=75%。
- **分应用档位不吃这块地板**：那是你对某个应用的明确选择，插电不该替你改掉。
- **GPU 吃这块地板**：只抬 CPU 不抬 GPU，插电打游戏仍会被 GPU 上限卡在 60 帧；
  例外是分应用里单独设的 GPU 档，那是你给这个应用明确设的上限。

**充电速度不归这个模块管。** 模块不写任何 `power_supply` / 充电器 / 充电电流节点，
只写 CPU/GPU 的频率上限；熄屏充电时不再维持模块的帽（`state=full`，交还系统），
厂商在充电时压低 CPU 上限时模块也跟随（日志写"厂商已压更低"）。
真正影响充电速度的是：电池温度（烫了厂商会主动降功率）、当前电量（80% 以后必然慢）、
充电器/线材、电池老化，以及**边充边玩**——游戏/相机的满血模式会让机身更热，厂商随之降充电功率。

怀疑是模块时做一次 A/B：关于页 →「暂停」（会恢复频率并停掉守护），
用同一个充电器、同样的电量区间、屏幕熄灭各充 10 分钟，比较
`/sys/class/power_supply/battery/current_now` 和电池温度；再「恢复」重复一次。
两组数一样就与模块无关。深睡也不会在充电时压 Doze：除了 `online` 节点，
还会看 `battery/status`（有些 ROM 只有后者）。

### 温控闭环（默认关）

扫 `/sys/class/thermal/thermal_zone*/`，只取 `type` 里带 cpu / gpu / soc 的，拿**最热**那个读数。
超 `TH_HIGH` 每个巡检周期压一档（`TH_STEP`），最多压到 `TH_MAX`；回到 `TH_LOW` 以下每隔 `TH_BACK` 秒还一档；
两者之间是迟滞带，**保持不动**——不然温度在阈值附近晃，封顶就跟着抖。

- 内核的 `temp` 是**毫摄氏度**（43600 = 43.6℃），阈值填℃，代码里换算。这条有断言钉着：
  第一版按 0.1℃ 比较，结果静置 43℃ 就被判成超阈值、白压一档。
- 同一棵目录树下还躺着 `vbat`（4091 其实是 4.091V）、`ibat`、`bcl` 这些**不是温度**的 zone，
  按数值筛会把电压当温度、把恒 0 的当"很凉快"，所以只按 `type` 认。
- 有些内核把 **trip point（阈值）** 也放进 thermal_zone，`type` 叫 `cpu-hw-trip-0/1`，
  `temp` 恒等于阈值（实测 95000 = 95℃）。它不是温度计；混进最大值会让整机永远被判成 95℃，
  温控压满、实时偏移一直不为 0。现在 `type` 里带 `trip` 的一律不收，
  测试里用假 zone（正常 42℃ + trip 95℃）钉住了"最热仍是 42℃、th_steps=0"。
- **zone 路径启动时扫一次并缓存**：PJZ110 上 87 个 thermal_zone 里只有 29 个命中
  cpu/gpu/soc，缓存后每轮只读这 29 个 `temp`，不再每 5 秒 opendir 整棵目录；
  某个缓存路径读失败（驱动重建/热插拔）会自动重扫一次。
- 温控偏移同时作用于 CPU 和 GPU。最热的传感器常常就是 GPU，只压 CPU 等于闭环只做了一半。
- **温度读不到时按"低于恢复线"处理**：thermal zone 热插拔、驱动重建、部分机型熄屏后目录消失，
  这时不能把上一次热到的档位冻住（会变成永久 −25）。已压下的档位按 `TH_BACK` 逐档还回去，
  这段时间温控不再挡 PSI，所以可能出现"温控还在还档、PSI 已经允许借额度"并存，
  最长持续 `TH_BACK × 当前档数` 秒（默认 20×5 = 100 秒）。这是有意的取舍：
  传感器坏了不该同时锁死发热保护和卡顿放宽。
- 默认 `TH_HIGH=75` 是通用值。8 Elite 这类 SoC 到 75℃ 时内核往往已经开始砍频，主动闭环就晚了；
  觉得"热了没效果"时先把 `TH_HIGH` 试到 68~70（`TH_LOW` 要跟着留至少 5℃ 的迟滞带）。
  不同机型散热差异太大，这一项需要按真机温度曲线调，所以默认值没有替所有人拍板。
- 这是主动闭环，比等内核热管控直接砍频平滑。厂商那边同时在压时日志会写"厂商已压更低"，两边不互相盖。

### 电量阶梯（默认关）

出厂不压：低电量时先只管「封到设定值」，不再额外收紧，免得用户觉得"没电就更卡"。
在功能页「电量低的时候」打开后：不充电且容量低于 `BATT_LOW`（默认 20%）时，
再收紧 `BATT_LOW_CUT`（默认 5 个点）；低于 `BATT_CRIT`（默认 10%）
再叠 `BATT_CRIT_CUT`（默认 10 个点）。
它和 PSI/温控共用 `ADAPT_DOWN_MAX` 总闸，不会把 65% 压到 5%：

- **插电时不生效**：低电量正在充电时不该再压，充电态本来就在放宽。
- **分应用档位不吃这一刀**：CPU/GPU 的应用专属档是用户明确设的值，和"专属档不吃充电地板"同一个口径。
- 读不到容量（`capacity` 缺失/越界）就不收紧，不猜。
- 功能页「电量低的时候」有总开关和四档数值；关着（默认）时电量再低也不额外收紧。

### PSI 护栏（默认开，只借不拿）

读 `/proc/pressure/cpu` 的 `total`（累计 stall 微秒），按墙钟差分算出**速率**（ms/s），
和这台机自己最近 10 分钟的基线比：**超出 2 倍、且绝对值再高 30 ms/s** 才借，
一档一档往外借（`PSI_STEP`），总量不超过 `PSI_GAIN`；不卡了先等 `PSI_HOLD` 秒，
之后每隔 `PSI_BACK` 秒收回一档。**它只能往上放宽，永远不低于你设的值**。
基线只在**常态且当前没在借额度**时更新：借出期间 stall 高是放宽本身的结果，
拿它去抬高基线会让护栏在持续高载约 7 分钟后自己失效。游戏/满血/熄屏不更新，
也不推进档位、不攒额度。阈值附近来回抖动导致长期借出、基线长期不学时，
`status` 里 `psifrz` 会给出这一轮连续冻结的秒数。

**它测的是 CPU 排队，不是帧**：看不到 GPU、存储 IO、内存和帧时间；作为
"负载尖峰时别把 CPU 帽压太死"的护栏合理，不能当成"用户真的卡了"的判据。
**温控优先**：只要这一拍还有降温档在生效、而且温度确实读得到，PSI 一档都不借，旧额度清零；
`down_max` 已被电量阶梯占用的部分也不能再借出去。GPU 不吃 PSI（只吃温控/电量），
避免 CPU 排队信号把 GPU 功耗抬上去。
**无效样本只冻结、不学习**：PSI 读不到、熄屏很久回来、内核计数器被清，这一拍不算"不卡了"，
也不会拿 0 去洗基线；`status` 里的 `stall` 这时报 `-1`，页面不显示这一项。
`PSI_GAIN` / `TH_MAX` 填 0 = 整条环路关；非 0 时必须至少能凑出一整档
（`PSI_GAIN >= PSI_STEP`、`TH_MAX >= TH_STEP`），否则后端/守护会按"关"处理。

为什么不用 `avg10` 的绝对值判（"`<1%` 收紧、`>5%` 放宽"那种写法）：一加 13 上量过一轮，

| 状态（各 25 秒） | `some avg10` | stall 速率 | 最热 cpu/gpu |
|---|---|---|---|
| 静置·封顶 62/64/66/68 | 3.6–5.7 | 61.6 ms/s | 42–46 ℃ |
| 8 路满载·有帽 | 4.7→8.5 | 129.0 ms/s | 67→74.5 ℃ |
| 8 路满载·**没帽 100%** | 6.6→9.35 | 128.6 ms/s | 72→76.4 ℃ |
| 恢复封顶 | 6.7→4.8 | 68.6 ms/s | 47–50 ℃ |

满载时**有没有帽，stall 速率一模一样**（129 vs 129 ms/s）——`some` 只看"有没有任务在等 CPU"，
八颗核都被 `yes` 塞满时它不看频率。而静置就有 4~5 个 `avg10`。
所以按绝对阈值写，开机几秒就会被判成"卡了"，一路放宽到 100% 停在那儿，**模块把自己关掉**。
判据因此改成"相对这台机自己的基线"，并且借出量有硬上限。

### 禁止 GPU Boost（默认开）

`GPU_BOOST_OFF=1` 不是再压一道上限，而是把厂商抬频的源头关掉：

- 高通：`dcvs_boost`（DCVS 抬频）、`touch_wake`（触摸唤醒抬频）、
  `force_no_nap`、`devfreq_boost` 模块的输入 / 唤醒 boost 时长；
  KGSL `idle_timer` 从默认 80ms 收到 48ms（只降不升，原值本来就短就不动）。
  48ms 高于 30fps 的单帧间隔（33.3ms），连续渲染不会被误判为空闲，
  间歇渲染（刷信息流、聊天）能砍掉一截停止渲染后的尾部空转。
- 天玑：`/sys/kernel/ged/hal/custom_boost_gpu_freq`。这个节点是 **OPP 索引**，
  不是频率；0 通常是最高频档，写 0 反而会把 boost 锁到最高。模块从
  `stack_working_opp_table`（或 `gpufreq_opp_dump`）里按频率找最低频那一档的真实索引，
  再写进去；表读不到就不动，不猜。
  只动 boost 目标，不改 `custom_upbound_gpu_freq`（上限）、不关 `fpsgo` / `gpu_dvfs_enable`。

节点存在才写，原值记进账本：游戏、满血、熄屏交还时自动还原；
关掉开关或在页面上取消，也会立刻还原。不需要重启。
这个开关同时做两层：先关"因"（不再产生抬频请求），再把"果"压回最低档
（`scaling_min_freq`/devfreq 下限）。旧键 `GPU_MIN_LOCK` 已并入，不再单独控制。
某些内核上没有这些节点，开关会静默空转，不报错。

### CPU 下限锁到底（`CPU_MIN_LOCK`，默认关）

常态每拍只读各簇 `scaling_min_freq`，高于 `cpuinfo_min_freq` 才写；全局 30 秒最多写一次，
避免和 perfd 抢节点拖慢唤醒。

**写完隔一拍（约 1 秒）再复核**：插电或 boost 期间，MTK PPM / 厂商 powerhint 会把
`scaling_min_freq` 的硬下限抬到 1.8~2.2GHz，这时写入是成功的（`store` 返回写入长度），
但 `policy->min` 停在平台值，回读得到的是**平台此刻的下限**，不是内核拒绝写入。
这种“夹回”会随插拔电、温控漂移，所以：

- 只记“该簇被平台钉在 X”，按簇退避 60→180→300→600 秒（封顶 10 分钟）重探，
  不再“连续 3 次就停 10 分钟”、也不再“本启动不再尝试”；
- 一个簇被钉住不影响其他簇；
- 插拔电、亮屏、改配置、切换智能档位会立刻清零退避重探；
- 日志里会写清充电态、第几次夹回、多久后重探；同一个钉住值只报一次。

游戏/满血/熄屏解除时按账本还原。它压的是**下限**，和 `CPU_PCT_*` 的**上限**不冲突；
轻载时 CPU 不再长期贴着厂商地板跑。

### 下限为什么会"让路"（`MIN_WINDOW_STEPS`，默认 3）

`scaling_min_freq == scaling_max_freq` 时，governor 没有任何下降空间：**空载也只能跑在
那个频点上**，这就是用户能感觉到的"CPU 空转"。更麻烦的是这时封顶也失效了——温控、
PSI、电量偏移想把天花板压下来，内核会因为 `min > max` 直接拒掉 `scaling_max_freq`
的写入，或者被下面这段旧逻辑顶回去：

```c
long floor = read_num(".../scaling_min_freq");
if (floor > 0 && want < floor) want = floor;   /* 封顶被下限抬回去 */
```

所以现在按"封顶是硬约束、下限是偏好"处理：

1. 封顶目标低于当前下限时，**先把下限让到「封顶往下 N 个频点」**，再写封顶
   （顺序不能反：`min > max` 时内核会拒掉 `max` 写入）；
2. 让不下去（平台硬下限）才退回"按平台值抬封顶"，并在日志里写明；
3. 封顶离硬件最低不足 N 档时，下限直接落硬件最低——这时"落最低"和"落几档"
   是同一件事，不把频率锁在半空中；
4. `MIN_WINDOW_STEPS=0` 关掉守护，回到旧行为（下限可以顶住封顶）。

落最低还是落几档？**默认落几档**：直接落最低（300MHz 左右）在重载毛刺时会让整簇
掉到地板、主频上不来，卡顿比省下的电更明显；留 N 档既保住了下降空间，也不至于
一发请求就打到最低档。

### 平台帽：厂商把上限压住时会自动学（不是算错）

日志里出现这行：

```
policy6 平台帽 1401600（目标 1958400 写不上去），5 秒后重探
```

说明这一簇此刻被平台压在 1401：厂商 perf HAL / `msm_performance` / 系统温控会在策略层
限制 `scaling_max_freq`，模块写下去会被夹回来。以前每拍都硬写，只会刷「写入未生效」；
现在：

- 学到帽值后，目标高于它时先按帽值生效，按 **5 → 15 → 60 → 180 秒** 退避重探；
- 帽放开（写到更高成功）补一行 `平台帽 … 已放开`；
- **亮屏、插拔电、改配置、切智能档位**都会清零重探，不把旧帽带到新状态；
- `CAP_BACKEND=auto` 在高通上只写 sysfs（不会自动接管 msm 节点），日志会提示节点存在；
  想越过这道帽，可手动设 `CAP_BACKEND=msm`，由模块接管
  `/sys/module/msm_performance/parameters/cpu_max_freq`（厂商再覆盖时模块会自己回退）；
- 帽值是"平台此刻"的，不是模块算错。厂商把下限钉在 1401 时，任何低于 1401 的封顶都写不进去。

### GPU 的封顶为什么可能比滑杆百分比低

GPU 的目标是「滑杆百分比 + 实时偏移（温控 / 电量；PSI 不参与）」，再向下吸附到真实频点。
偏移到 -25 档时，50% 先变成 25%；如果目标低于 GPU 的最低频点，会落到最低档
（例如 282 MHz），和 CPU 的封顶语义一致。配置页现在会在 SoC 标题下写出当前
偏移量；不想要这层让路，就在「功能」页把温控 / PSI 护栏关掉。
**适配页「封顶后」一列只算设定值的吸附**（100% 就是 1200MHz），不叠加实时偏移；
实际生效值（偏移、厂商上限都算进去）在「GPU 封顶」卡片和状态里看，两处不混。

## 配置页顶部的 SoC 与频率表

SoC 型号依次读 `ro.soc.model` → `ro.board.platform` → `ro.chipname` →
`ro.product.model`，取**最后一个空格/逗号分隔的词**并转小写
（属性值常是 `Qualcomm Technologies, Inc SM8750` 这种带前缀的）。
四个都取不到才显示"未知"。

顶上还会列出每个核心与 GPU 的「原生最高频率 → 封顶后」：

```
CPU0  68%     1901 MHz  →  1292 MHz
CPU3  66%     3187 MHz  →  2103 MHz
GPU KGSL 45%   900 MHz  →   405 MHz
```

原生最高频率是硬件标称值，四舍五入显示；**封顶那一列一律向下取整**——
真实封顶 1292.544 MHz 就显示 1292，不显示 1293。往上凑的话，拿显示值反算
百分比会发现比设定值还大，"绝不超过设定百分比"这个卖点就成了空话。

拖动百分比滑杆时封顶值实时重算。标 `≈` 的表示**还没保存**（守护此刻
还不知道这个值），同样向下取整，和守护的吸附策略一致。
这一列显示的是**设定值**对应哪个频点，不叠加实时偏移；偏移后的实际值看
「GPU 封顶」卡片（硬件上限 / 当前封顶）和首页状态。

机上手动确认（两条都要看）：

```sh
$MODDIR/socfreqd export | grep '^soc='      # 期望 soc=sm8750
$MODDIR/socfreqd export | grep -E 'gpu_(max|unit)'   # 期望 gpu_unit=Hz
```
