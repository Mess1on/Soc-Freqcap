# 配置

（返回 [README](../README.md)）

## 配置

全在 `/data/adb/soc_freqcap/socfreq.conf` 里，每项都有注释。常用的几项：

| 项 | 默认 | 说明 |
|---|---|---|
| `CPU_PCT_BIG` | 65 | 最强核的封顶百分比 |
| `CPU_PCT_MID2` | 64 | 次强核（只有 4 簇以上机型用得上） |
| `CPU_PCT_MID` | 66 | 中间档 |
| `CPU_PCT_LITTLE` | 65 | 最弱核 |
| `GPU_PCT` | 45 | GPU 封顶百分比 |
| `STRATEGY` | cap | `cap` 固定百分比封顶；`smart` 四档智能调度，`CPU_PCT_*` 只当天花板 |
| `GPU_BOOST_OFF` | 1 | 1 = 禁止 GPU Boost：同时把下限压回最低档、关掉抬频源头（`dcvs_boost` / `touch_wake` / `devfreq_boost` / 天玑 OPP boost 档）；交权态自动还原。旧键 `GPU_MIN_LOCK` 已并入本开关 |
| `BIG_MIN` | 0 | 1 = 超大核压到最低可用频点（不关核）；游戏/满血/熄屏交还仍放开 |
| `CPU_MIN_LOCK` | 0 | 1 = 常态把各簇下限压到 `cpuinfo_min`；30s 节流、连续 3 次被夹回停 10 分钟 |
| `INTERVAL` | 5 | 巡检间隔（秒） |
| `GAME_GRACE_SEC` | 10 | 退出游戏后继续保持解锁的秒数 |
| `SCREEN_POLICY` | cap（新装）/ 升级按旧键迁移 | 熄屏策略：`uncap` 交还系统、`cap` 保持封顶+轻巡检、`keep` 保持封顶+全量巡检；缺键时 `SCREEN_UNCAP=0` 补 cap、其余补 uncap |
| `SOFF_INTERVAL` | 15 | 熄屏轻巡检周期（秒，5~300） |
| `SCREEN_STATE_PATH` | 空 | 亮屏信号文件；空 = 自动挑选 |
| `SCREEN_UNCAP` | 0 | 旧键兼容：没有 `SCREEN_POLICY` 时 1 映射成 uncap |
| `IDLE_CURRENT_MA` / `IDLE_HOLD_CYCLE` | 250 / 2 | 熄屏电流低于多少 mA、连续几轮后进深度空闲 |
| `IDLE_INTERVAL` / `WAKE_DELTA_MA` | 30 / 150 | 深度空闲周期；电流比熄屏基线高多少 mA 才触发一次亮屏复核 |
| `BATT_CURRENT_PATH` / `BATT_CURRENT_UNIT` | battery/current_now / ma | 电流节点与单位；ua 会先 /1000，符号统一取绝对值 |
| `BOOT_FULL_S` | 60 | 开机后满血窗口秒数（0 = 关掉这个功能） |
| `CPU_GOVERNOR` | 空（不干预） | 留空 = 不碰调速器；荣耀 / 华为机型一律不改写（切 conservative 会硬重启） |
| `CHG_UNCAP` / `CHG_PCT` | 1 / 100 | 插电时把常态 CPU/GPU 封顶至少抬到多少（专属 GPU 档不抬） |
| `TH_CAP` / `TH_HIGH` / `TH_LOW` | 0 / 75 / 68 | 温控闭环默认**关**（发热交给内核热管理）；打开后超 TH_HIGH 逐档压、回 TH_LOW 逐档还 |
| `TH_STEP` / `TH_MAX` / `TH_BACK` | 5 / 25 / 20 | 每档压多少个百分点、最多压多少、每多少秒还一档 |
| `PSI_ADAPT` / `PSI_GAIN` / `PSI_STEP` | 1 / 5 / 5 | PSI 护栏开关与最多借出（默认最多一档 +5）、每档多少个百分点 |
| `PSI_HOLD` / `PSI_BACK` | 30 / 15 | 判到卡后额度至少借住多久、不卡了每多少秒收回一档 |
| `ADAPT_UP_MAX` / `ADAPT_DOWN_MAX` | 15 / 30 | 合计偏移的总闸（百分点）；0 = 那一侧封死 |
| `BATT_STEP` | 0 | 电量阶梯开关（默认关）；打开后低电量才额外收紧 |
| `BATT_LOW` / `BATT_LOW_CUT` | 20 / 5 | 低于多少电量（%）压第一刀、压几个点 |
| `BATT_CRIT` / `BATT_CRIT_CUT` | 10 / 10 | 更低的第二档与第二刀（必须低于 BATT_LOW） |

改错了不会生效 —— 数值会被夹回合法范围，调速器名只认白名单里的词。

> 旧版本的 `govs.saved` 可能把模块最后写入的调速器当成原值。升级后如果选「不干预」仍是老调速器，
> 说明原厂值已被旧快照覆盖：按机型手动选一次原厂 governor，再切「不干预」即可。
> 修复后的版本启动时会先按快照恢复、再取基准，不会再覆盖。

### 按芯片套的预设

芯片默认值只有一份来源：`adapt/sm8750.conf`、`sm8850.conf`、`sm8845.conf`、`sm8975.conf`、
`sm8650.conf`、`sm8550.conf`、`sm8475.conf`、`mt6991.conf`、`mt6993.conf`、`mt6995.conf`
里的 `default_*`。装机时读 `ro.soc.model`（拿不到再退到 `ro.board.platform`），命中文件后：

| 芯片代号 | 机型 | 超大核（BIG） | 中核（MID） | 小核（LITTLE） | GPU | 温控/PSI |
|---|---|---|---|---|---|---|
| `SM8750` | 骁龙 8 Elite | 46% | — | 51% | 45% | 75/68℃、PSI_GAIN 5 |
| `SM8850` | 骁龙 8 Elite Gen 5 | 46% | — | 52% | 42% | 75/68℃、PSI_GAIN 5 |
| `SM8845` | 骁龙 8 Gen 5 | 51% | — | 53% | 41% | 75/68℃、PSI_GAIN 5 |
| `SM8975` | 骁龙 8 Elite Extreme Gen 6 | 40% | 47% | 51% | 41% | 75/68℃、PSI_GAIN 5 |
| `SM8650` | 骁龙 8 Gen 3 | 74%（≈2438MHz） | 66%（≈2074MHz，两个中簇） | 68%（≈1536MHz） | 56%（≈500MHz） | 75/68℃、PSI_GAIN 5 |
| `SM8550` | 骁龙 8 Gen 2 | 70%（≈2227MHz） | 69%（≈1920MHz） | 73%（≈1459MHz） | 59%（≈401MHz） | 75/68℃、PSI_GAIN 5 |
| `SM8475` | 骁龙 8+ Gen 1 | 69%（≈2208MHz） | 66%（≈1805MHz） | 73%（≈1459MHz） | 47%（≈421MHz） | 75/68℃、PSI_GAIN 5 |
| `MT6989` | 天玑 9300 / 9300+ | 80%（≈2600MHz） | 78%（≈2200MHz，X4×3） | 90%（≈1800MHz） | 39%（≈500MHz） | 75/68℃、PSI_GAIN 5 |
| `MT6991` | 天玑 9400 / 9400+ | 80%（≈2900MHz） | 67%（≈2200MHz） | 75%（≈1800MHz） | 35%（≈550MHz） | 75/68℃、PSI_GAIN 5 |
| `MT6993` | 天玑 9500 | 72%（≈3000MHz） | 63%（≈2200MHz） | 71%（≈1900MHz） | 35%（≈600MHz） | 75/68℃、PSI_GAIN 5 |
| `MT6995` | 天玑 9600 Pro | 73%（≈3300MHz） | 56%（≈2400MHz） | 65%（≈2000MHz） | 37%（≈650MHz） | 75/68℃、PSI_GAIN 5 |
| 其它 | — | 不动，保持通用默认 | | | | |

**只对全新安装生效**。升级安装一律不碰用户配置——用户刻意填的 65 可能刚好等于
旧默认值，用"值等于默认就覆盖"的启发式会把它改掉。
覆盖安装的人想用新预设，去「CPU / GPU 封顶」页点**推荐**或**偏流畅**：后端按当前 SoC
重新匹配 `adapt/*.conf`，把这台的推荐值填进控件；没有匹配的芯片时显示「无」，两个按钮都置灰。
两种预设都只填入控件，点「保存并生效」才写盘。

**推荐预设**会同时落四条策略（写进控件，随保存生效）：
插电不封顶（`CHG_UNCAP=1` / `CHG_PCT=100`）、发热不主动降（`TH_CAP=0`，发热交给
内核热管理）、PSI 不放宽（`PSI_ADAPT=0`，连默认的少借一档也不借）、
调度回限频（`STRATEGY=cap`；智能模式仍可在页面手动切）。

**偏流畅**只做一件事：在推荐预设的 CPU 每个簇上 **+10 个百分点**
（例如推荐 46/51 → 56/61，最高 100），GPU、温控、PSI、充电、调度全部不动。
适合觉得推荐值偏保守、想要更跟手的场景；连点两次结果不变。
芯片默认值和你打开配置看到的值是同一份，不存在守护 fallback 里的第二套。

8E / 8E5 / 8G5 都是 m=2 双簇，`CPU_PCT_MID` / `MID2` 在这类机器上不生效，适配文件只给
BIG/LITTLE；SM8975 是 m=3 三簇，中间簇映射到 `CPU_PCT_MID`，`MID2` 不生效。
天玑 9400（1+3+4）、9500（1+3+4）、9600 Pro（2+3+3）也是三簇，同样用 BIG/MID/LITTLE。
SM8650 是四个频率域（两个 A720 簇峰值相同），`CPU_PCT_MID` 与 `CPU_PCT_MID2` 都写 66%；
如果内核把两个同频簇去重成一档，MID2 不生效，结果仍然是 66%。
天玑那三套的百分比是按"向下吸附后仍能落在目标 MHz 上"取的，不是纯算术占比：
例如 9500 的 Ultra 3000MHz 若写 71%，71%×4210=2989 会吸到 3000 以下一档；
写 72% 算出 3031，才能吸住 3000。GPU 同理（9400 写 34% 只有 548，写 35% 才够 550）。
百分比最终会向下吸附到频点表；换机型先用
`cat /sys/devices/system/cpu/cpufreq/policy6/cpuinfo_max_freq` 确认硬件顶点，
再看吸到的实际频率。候选值发布前仍按真机温度/续航曲线复测。

**升级时怎么处理**：一个 `default_*` 都不套，用户配置逐字节保留。
不靠"值等于默认就覆盖"的启发式——用户刻意填的 65 可能刚好等于旧默认值，
那样会被静默改掉。升级只追加配置里不存在的新键；`SCREEN_POLICY` 单独迁移：
缺这个键且旧 `SCREEN_UNCAP=0`（会落进 keep 全量巡检）时补成 `cap`，
`SCREEN_UNCAP=1` 或两个键都没有时补成 `uncap`，显式写了的配置不改。

### 这台机上没有的那一档，不摆控件

骁龙 8 Elite 这类两档/三档芯片，`MID2`、`MID` 可能天生落空。
守护把这种情况报成 `coretier_CPU_PCT_MID2=`（空），页面对应的行**只留名字和
（未检测到）**：滑杆摘掉、百分比不显示、保存时也不写进 conf。
摆一个"调了也没用"的滑杆在那里，只会让人以为是自己设了没生效、保存出了问题。

反过来，**"检测失败"（守护版本旧或读不到）时滑杆照旧保留** ——
那种情况下我们并不知道这台机有没有这一档，不该替用户把控件藏掉。

## 智能调度（STRATEGY）

`STRATEGY=cap` 是原来的固定百分比封顶；`STRATEGY=smart` 打开四档状态机：

| 负载状态 | 目标 |
|---|---|
| 空闲 | 天花板 ×45% |
| 轻载 | 天花板 ×65% |
| 中载 | 天花板 ×85% |
| 重载 | 天花板 ×100% |

每 5 秒读一次 `/proc/stat`，按 policy 分簇算平均占用，取**最忙的一簇**作信号
（单核满载不会被 8 核求和稀释）；升档 1 拍（5s）、降档 2 拍（10s）。
每簇按自己的 `CPU_PCT_*` 当天花板，m=3/4 机型的中间档也一样；重载就是天花板。
智能模式不叠 PSI 向上借额度（温控/电量收紧保留）；插电时充电地板仍会抬高目标，省电对比请拔电。

游戏、满血、熄屏交还三条路径两种策略完全一样，仍然按原逻辑交还系统；
交还时只撤模块自己写的上限——厂商游戏助手/热控已经把上限压得更低时保留它，
不会在进游戏的一瞬间把帽抬回硬件最高。
交权时连**调速器**一起还原成模块接管前的名字（账本保留），回常态再按你的选择写回去——
不然选过 powersave / conservative 的机器，游戏里仍跑着模块那个调速器，"官方调度"其实没恢复全。
## 分应用档位（app_modes.conf）

`/data/adb/soc_freqcap/app_modes.conf`，一行一条 `包名=值`：

| 值 | 含义 |
|---|---|
| `full` | 这个应用在**前台时**整个交还系统（CPU 和 GPU 都不封顶） |
| `1~100` | CPU 四簇统一按这个百分比封顶；**GPU 仍按全局的 `GPU_PCT`**（老写法，语义不变） |
| `80:40` | CPU 80%、GPU 40%，两段各自吸附到实际频点 |
| `80:` / `:40` | 只设一边，另一边跟随全局 |
| `70/50` | 大核 70%、小核 50%；中间档跟随全局（2 簇机型就是大小核两档） |
| `70/50:40` | 在大/小核之外再给 GPU 单独设 40% |
| `keep` | 熄屏那一刻在这个应用前台时不交还系统，继续按全局百分比巡检 |
| `soff` | 熄屏那一刻在这个应用前台时交还系统，亮屏仍按全局百分比；熄屏轻巡检不查前台，后台下载/后台音乐/闹钟不在前台时仍吃全局 `cap` |

优先级：**游戏名单 > 满血窗口（开机 / 熄屏解除）> 应用专属 > 全局百分比**。
应用专属排在满血窗口之后是有意的——熄屏解除是用户主动开的全局开关，
屏幕都灭了还守着某个相机的 80% 没有意义。`soff` 只影响熄屏那一拍：
要看"熄屏瞬间的前台包"，不是整晚盯着进程，所以它不能替代"后台任务别被限频"
这类全局放行。

典型用法是把相机、录像、地图设成 `full`：这些应用要吃完整性能，
而它们本来也不在"日常待机节流"的目标场景里。想反过来压住某个应用的 GPU 发热
（比如录像、长时间导航），用 `70:40` 给 GPU 单独设一道比全局更低的帽；
GPU 段吃温控、电量阶梯和插电地板，不吃 PSI 借出。

守护按 mtime 热重载，改完就生效，不用重启手机。写的一侧（`api.sh` / WebUI）
有校验：坏包名、越界数字直接被拒；读的一侧（守护）对坏行是**整条忽略**，
不是当成 0%——手改文件写错不该让手机突然变成砖。

WebUI 的入口在「应用 → 分应用档位」（和名单、候选栏在同一页，都是按应用定的事）：
先选一个 CPU 档位（满血 / 90 / 80 / … / 50 / 40 / 30 / 分核 / 自定义）和 GPU 档位（跟随全局 / 90 / … / 自定义），
选「分核」时填大核和小核两个百分比（1~100），例如 `70/50`；
按「＋ 添加应用」展开**已安装应用列表**：默认是第三方应用 + 系统里有桌面入口的那些
（相机、设置、相册、信息…）。列表下面有**「显示系统应用」**开关：勾上连 provider / 服务 /
组件一起列，给"要选某个系统包、但默认列表里没有"的机器用。部分 ROM 把
`cmd package query-activities` 裁掉了，后端会自动回退到全部系统包，不会只剩第三方。
点一下就写入；已经设过的行有两个下拉，CPU 和 GPU 可以分开改，× 删除。

系统应用在 APK 里的名字常是英文（OPPO 相机叫 `Camera`、设置叫 `Settings`），
所以搜索框做了中文别名：搜「相机 / 设置 / 时钟 / 相册 / 文件 / 联系人…」都能找到。
**别名只影响搜索，不改显示名**——名字仍以 APK 里的 `android:label` 为准，不替厂商翻译。
APK label 解析不出来（引用型 label / 资源被裁）的包，用 `scripts/builtin_labels.txt` 的
中文名兜底；只填空白，不覆盖已有英文名。列表先画 80 行，滚到底点「显示更多」再追加；
滑动时暂停批量取图标/名字，停手后再发 root 调用，避免在管理器里滑起来一卡一卡。
深睡页的「永久豁免」默认也只列第三方；同一个「显示系统应用」开关打开后可以选系统包，
厂商短信 / 电话这类不在 `-3` 里的包就能手动加。

**相机类默认满血。** 装机时按 `scripts/builtin_modes.txt` 里各家相机的包名
（`com.android.camera`、`com.oplus.camera`、`com.sec.android.app.camera`、`com.vivo.camera` 等），
只给**本机已安装**的那些追加 `pkg=full  #builtin`。取景、快门、连拍、4K 录像都吃瞬时响应，
相机在前台本来也不在"日常待机节流"的目标里。这份清单**不覆盖你的选择**：

- 已经给这个包设过任何值（哪怕手写 80）→ 不动；
- 删掉那一行 → 以后升级不会塞回来（基准 `builtin_modes.base.txt` 记着上一版清单，
  只有**新版清单里新增**的包才会补）；
- 想换回百分比或 `keep`，直接在「分应用档位」里改即可。

这里不能做"把**当前前台**应用设为满血"：这一页是在管理器里打开的，
那一刻守护抓到的前台**永远是管理器自己**，那个按钮唯一能设的对象就是管理器。
现在首页连"当前前台是哪个"都不显示了（上一段说了原因），
要设档位就在应用列表里自己挑。

命令行同理（走的是同一个 `api.sh`，所以校验也一样）：

```sh
A=/data/adb/modules/soc_freqcap/webroot/api.sh
sh $A modes_list                          # 看现在设了哪些
sh $A modes_set com.android.camera full   # 相机满血
sh $A modes_set com.autonavi.minimap 80   # 地图按 80% 封
sh $A modes_set com.android.camera 70:40  # CPU 70%、GPU 40%
sh $A modes_del com.android.camera        # 删掉
```

直接编辑 `/data/adb/soc_freqcap/app_modes.conf` 也行，但坏行会被守护整条忽略
（不是当成 0%）——手改写错不该让手机突然不动。

**配置为什么不在模块目录里。** 管理器升级模块是「先删 `/data/adb/modules/<id>`
再解包」，配置放模块目录里就会被新包的默认值盖掉，用户调过的东西一次升级就没。
所以装在 `/data/adb/soc_freqcap/`（`customize.sh` 首次安装时搬过去，
`api.sh` 里还有一道兜底）。也没放 `/sdcard`：那里是 FUSE + `media_rw` +
MediaProvider 的一套权限，root 写进去的文件应用侧未必读得到。

**开机满血窗口**（`BOOT_FULL_S`）：`service.sh` 在等到 `boot_completed` 之后、
正式接管之前，往 `/data/adb/soc_freqcap/run/boot_boost_until` 写一个截止秒数
（读 `/proc/uptime`，不用墙钟——开机阶段时间会被 NTP 往前跳）。
守护在主循环里看到没过期就整个交还系统，到期后自己压回常态封顶。
开机动画、首屏加载、桌面重建挤在那几十秒里，封顶会让它明显变慢。

**熄屏轻巡检**（`SCREEN_POLICY`）：三个值，新装默认 `cap`。升级用户缺这个键时，
旧 `SCREEN_UNCAP=0` 补成 `cap`（否则会落进 keep 的 5 秒全量巡检），
`SCREEN_UNCAP=1` 或两个键都没有时补成 `uncap`；显式已有的值不改。

| 值 | 熄屏后 | 周期 |
|---|---|---|
| `uncap` | 解除封顶、交还系统 | `SOFF_INTERVAL`，只读亮屏信号 |
| `cap` | **保持封顶**，只压回被厂商顶高的上限；下限压到硬件最低、不吃充电地板；温控每 4 拍采一次 | `SOFF_INTERVAL` |
| `keep` | 保持封顶，但走亮屏全量路径（读温度/PSI/前台） | `INTERVAL` |

`uncap`/`cap` 共用轻路径：不再 fork `dumpsys window`、不跑 PSI/前台识别，只读一个亮屏信号。
亮屏后立刻恢复常态巡检（`cap` 会把下限还原、充电地板重新生效）；
游戏/满血应用熄屏时保留原交权状态，不会先压一拍再解锁。
`cap` 是"待机也要省电"的推荐档：夜里插电不会因为 `CHG_PCT` 被抬到 100%。

亮屏信号的选择：启动时自动挑 `fb0/blank`（0=亮），没有就挑任意
`backlight/*/brightness`（>0=亮）。实测在一加 13 / Android 17 上 `fb0/blank`
不存在，且锁屏亮屏时 `dumpsys window` 仍是 `mSleeping=true`（keyguard token），
所以不拿 `mSleeping` 当判据；亮度节点 0/1127 与 `mWakefulness` 完全一致。
节点读不到时退 `dumpsys power` 兜底；任何判据都失败时按「亮屏」处理——
探测失败的后果是维持封顶，不是悄悄放开。

`SOFF_INTERVAL` 只影响熄屏态的亮屏检测延迟（新装默认 30s）。想回到旧行为
（熄屏照样封顶、5s 巡检）就把 `SCREEN_POLICY=keep`；这个回退不依赖改代码或降级。

**深度空闲（P0b）：** 熄屏后电流持续低于 `IDLE_CURRENT_MA`（默认 250mA）达到
`IDLE_HOLD_CYCLE` 轮，巡检周期从 30s 拉到 `IDLE_INTERVAL`（新装默认 60s）。亮屏信号仍每轮读，
电流只做辅助：比熄屏 EMA 基线高出 `WAKE_DELTA_MA`（默认 150mA）时才多问一次
`dumpsys power`，不拿绝对阈值。电流读不到就停在 SCREEN_OFF，永不进深睡。
电流单位在 `BATT_CURRENT_UNIT` 里显式写 `ua`/`ma`——一加 13 实测是 mA 且充电为负，
代码统一取绝对值；换 ROM 先按 `_tools/measure_screen_state.sh` 复测再改这一项。

**分应用 `keep`：** `app_modes.conf` 里写 `包名=keep`，这个包在熄屏那一刻是前台时
**不交还系统**，继续按全局百分比做轻巡检（只读频率节点、被顶回就压回），适合 Termux
编译、挂机下载。它只影响熄屏，亮屏时仍按全局分档。

## 动态封顶（默认关，一个开关 = 完整压制）

开关在「Boost 与压制」页。参考能效曲线哲学：推荐值是最优解，压制不压低它，
只管"不许无谓地越过它"。打开后下面这组一起生效——全部节点存在才写、值记进
账本，进游戏/满血/熄屏交还时自动还原，卸载按账本恢复：

1. **动态天花板（三档）**：亮屏常态把巡检切成 1s 快拍，天花板在最优解、中间档、风格地板之间收放——无贴顶且占用低，先降到中间档，再连续低载才到地板；调度器顶着当前档要更高（cur_freq 贴顶），**连续 2 拍贴顶才放一档，仍贴顶下一拍才回最优解**，避免单次滑动/切屏把天花板拉回满频。不拿占用率当升档依据：压低 cap 会推高占用率，拿它判需求会自激振荡；
2. **静置压下限**：到地板且无贴顶持续 5 拍，把各簇 `scaling_min_freq`
   压到硬件最低，活动立即还原。开启期间「CPU 下限锁到底」的亮屏巡检自动
   让位（两条路都写 min 会互相还原）；熄屏的 `cpu_min_to_floor` 不受影响；
   在 SM8750 / SM8850 上，压制期间最高频簇（超大核）直接落到硬件最低，
   大核按阶梯走；其他芯片保持统一百分比，不套这个拓扑假设；
3. **walt 拉频源中和**（高通）：`input_boost_ms` / `sched_per_task_boost` /
   `sched_boost` 写 0——触摸瞬间顶频率的源头（`input_boost_freq` 是频点表，
   数值账本无法原样还原，暂不写）；压制期间每个 1s 快拍补写，防止系统在切前台/
   亮屏时把 `input_boost_ms` 恢复成 100；
   其他 SoC 没有这些节点自动跳过；写入一次不对抗厂商后续行为；
4. **调度下限 uclamp.min**：`/dev/cpuctl/{top-app,system,cpu,foreground,background}/cpu.uclamp.min`
   存在时压到 0，降低前台/系统任务的“最低性能请求”；cgroup 布局不同的机型
   没有这些节点就跳过，不猜路径；
5. **升/降频限速**：各簇调速器 `up/down_rate_limit_us` 按 `GOV_UP_US` /
   `GOV_DOWN_US`（µs，默认 1000）写入，削平升频尖峰；walt / interactive /
   schedutil（含 MTK sugov_ext）通用，按各簇实际调速器名找节点；
   厂商自有调度器（hmbird/scx）不碰；
6. **uclamp.max**：0/1/2 档分别把 `top-app / foreground / dex2oat` 的
   `cpu.uclamp.max` 压到 85/65/45、70/50/30、60/40/20。节点回读
   `max` / 小数 / ≤100 时按百分比写，>100 时按 0–1024 换算；
   其他回读值不猜刻度，直接跳过（避免把 60 当成 5.8%）。原值
   （可能是 `max` 或 `50.00`）单独记在 `uclamp.saved`，还原时原样写回；
7. **cpuset 前后台分区 + 分级 hispeed**：有适配数据的芯片（SM8550、
   SM8650、SM8750、SM8850、MT6989；P 后缀回落基础型号）在 0/1/2 档
   按 `adapt/<soc>.conf` 的 `cpuset_*_lv0/lv1/lv2` 写
   `/dev/cpuset/{top-app,foreground,background,system-background}/cpus`，
   并在中间/地板档按 `gov_lv1/lv2_cl<N>_hispeed_ratio / hispeed_load`
   写各簇调速器（0 档不额外改）。`hispeed_ratio` 是千分比
   （对位 JSON 的 `hispeed_freq / 该模式上限`），按我们当前档的封顶
   换算，不会因为绝对值高于我们的百分比封顶而被整簇跳过。`clN` 按
   policy 号升序；SM8650 的两个同频簇用 `clN` 写法，不会被 tier
   去重吃掉。只写 `cpus` 掩码，不搬任务；没有数据的芯片完全不碰。

`core_ctl` / `migt` / `metis` 这类核心拓扑和厂商调度参数没有跨芯片通用值，
本版不写；`cpuset` 也只在有适配数据的芯片上写 `cpus` 掩码，不移动
`tasks`/`cgroup.procs`。节点不存在或语义不一致时直接跳过，避免把别的
机型的参数套到本机。

**与其它功能的边界**（避免互相拉锯的规则）：

- **插电暂停**：插电时压制自动暂停并交还——"插电不封顶"是既定策略，
  压制的相对阶梯此时会把满频按 80% 压住，与策略矛盾；拔电下一拍恢复。
- **CPU 下限锁到底**：压制开启期间，亮屏的下限巡检由压制的"低载静置
  压下限"接管（`cpu_min_patrol` 让位），两条路都写 min 会互相还原；
  熄屏的 `cpu_min_to_floor` 不受影响。
- **实时偏移（PSI/温控/电量）**：同向叠加、无对抗——偏移改的是生效
  封顶，压制的阶梯以"当前生效封顶"为 100% 跟随；PSI 借出/温控收紧后
  压制地板随之浮动。插电时压制本身暂停，充电地板不与阶梯叠加。
- **内核钳制退避**：目标低于某簇实际下限（如 BIG_MIN 或小封顶机型）
  时记住回读值并退避 600s，不做每秒一次的无效写入。

**压制风格**（`SUP_STYLE`，开关下方可切）：

| 风格 | 中间档 | 地板 | 低载降档 | 贴顶回升 |
|---|---|---|---|---|
| `bal` 均衡 | 90% | 80% | 连续 3 拍 <20% 逐级降 | 先到中间，仍贴顶回 100% |
| `sav` 省电 | 85% | 70% | 连续 2 拍 <20% 逐级降 | 先到中间，仍贴顶回 100% |

`sav` 的 0 档附加层也按均衡组走（uclamp 70/50/30、cpuset fg 0-5 / bg 0-3），
1/2 档按省电组；`bal` 的 0 档才用性能组。这样选省电风格时，活跃的 0 档不会仍挂着
性能组的 85/65/45 和 fg 0-6。

附加层与档位对应（0/1/2 档 = 性能/均衡/省电，换档/关闭/交权全部还原）：

| 档位 | uclamp.max（top / fg / dex2oat） | cpuset（有数据芯片） | hispeed（有数据芯片） |
|---|---|---|---|
| 最优解 0 | 85 / 65 / 45 | 后台 0-5、前台 0-6、top 0-7 | 不改（最优解） |
| 中间档 1 | 70 / 50 / 30 | 后台 0-3、前台 0-5、top 0-7 | 均衡档参数 |
| 地板档 2 | 60 / 40 / 20 | 后台 0-2、前台 0-5、top 0-7 | 省电档参数 |

SM8750 的 hispeed：中间档超大核 1958MHz/大核 1786MHz（load 80），
地板档超大核 1402MHz/大核 1363MHz（load 90）；SM8850 对应
1978/1786MHz（load 80）和 1382/1114MHz（load 90）。0 档不改调速器
（性能档 hispeed 高于日常封顶，写了也是无效工作点）。SM8750 / SM8850
压制时超大核本来就被放到硬件最低，所以超大核那组 hispeed 会被跳过，
实际生效的是大核那组。数值写在 `adapt/<soc>.conf`，还没有数据的机型
不写这三层。

压制叠加在 cap/smart 与分应用档位之上（以各自算出的生效封顶为 100%）。
开启后若卡顿明显，把封顶放回推荐值或关掉压制。

## 实时偏移（PSI / 温控 / 充电态）

这一节管的是**这一刻该不该让路**。三条各自独立记账，
合成一个偏移加在生效值上：

```
CPU 生效封顶 = 设定值（插电时先抬到 CHG_PCT）+ PSI 借出 − 温控压回 − 电量阶梯
GPU 生效封顶 = 设定值（全局 GPU_PCT 或应用 GPU 档）− 温控压回 − 电量阶梯
```

合计偏移还有一对总闸（`ADAPT_UP_MAX` / `ADAPT_DOWN_MAX`，默认 +15 / −30），
防止每个来源都不越界、叠起来却把 65% 压成 5%。

**只改生效值，从不写配置文件。** 滑杆上显示的就是你设的那个数，背后没有第二个东西在偷偷改它。

**功能页不摆术语。** 三张卡各自只有一个下拉框：「插着电的时候」「机身发热的时候」「CPU 排队偏高的时候」，
选项写的是行为（不封顶 / 早点降 / 少借一点），不是参数名。具体数值收在每张卡的
「自己定」里，**范围一个都没缩** —— 手动改过之后下拉框会自己变成「自己定的值」，
不会继续谎称你还在某一档。页面顶上还有一句按当前值现算的话：
「插电　插着电时不封顶，拔电自动恢复 / 发热　到 75℃ 开始一档档降，最多比设定低 25%…」。
首页那一行同样先给人看的那句（`现在比设定值低 10%　机器发热，正在降速保护`），
`stall / ms/s / 几档` 这些原始读数放在后面一小段淡色文字里，截图反馈问题时用的就是它。

### 充电态（默认开）

`/sys/class/power_supply/battery/status` 是 Charging/Full 时，把常态封顶至少抬到 `CHG_PCT`（默认 100），
拔电自动回落 —— 插着电发热由充电器承担，压它没有意义。三条边界：

- **温控优先**：本拍有收紧（温控/电量）时不抬地板——65% 设定 + 温控 −25 = 40%，
  不会变成 100−25=75%。
- **分应用档位不吃这块地板**：那是你对某个应用的明确选择，插电不该替你改掉。
- **GPU 吃这块地板**：只抬 CPU 不抬 GPU，插电打游戏仍会被 GPU 上限卡在 60 帧；
  例外是分应用里单独设的 GPU 档，那是你给这个应用明确设的上限。

**充电速度不归这个模块管。** 模块不写任何 `power_supply` / 充电器 / 充电电流节点，
只写 CPU/GPU 的频率上限；熄屏充电时不再维持模块的帽（`state=full`，交还系统），
厂商在充电时压低 CPU 上限时模块也跟随（日志写"厂商已压更低"）。
真正影响充电速度的是：电池温度（烫了厂商会主动降功率）、当前电量（80% 以后必然慢）、
充电器/线材、电池老化，以及**边充边玩**——游戏/相机的满血模式会让机身更热，厂商随之降充电功率。

怀疑是模块时做一次 A/B：关于页 →「暂停」（会恢复频率并停掉守护），
用同一个充电器、同样的电量区间、屏幕熄灭各充 10 分钟，比较
`/sys/class/power_supply/battery/current_now` 和电池温度；再「恢复」重复一次。
两组数一样就与模块无关。深睡也不会在充电时压 Doze：除了 `online` 节点，
还会看 `battery/status`（有些 ROM 只有后者）。

### 温控闭环（默认关）

扫 `/sys/class/thermal/thermal_zone*/`，只取 `type` 里带 cpu / gpu / soc 的，拿**最热**那个读数。
超 `TH_HIGH` 每个巡检周期压一档（`TH_STEP`），最多压到 `TH_MAX`；回到 `TH_LOW` 以下每隔 `TH_BACK` 秒还一档；
两者之间是迟滞带，**保持不动**——不然温度在阈值附近晃，封顶就跟着抖。

- 内核的 `temp` 是**毫摄氏度**（43600 = 43.6℃），阈值填℃，代码里换算。这条有断言钉着：
  第一版按 0.1℃ 比较，结果静置 43℃ 就被判成超阈值、白压一档。
- 同一棵目录树下还躺着 `vbat`（4091 其实是 4.091V）、`ibat`、`bcl` 这些**不是温度**的 zone，
  按数值筛会把电压当温度、把恒 0 的当"很凉快"，所以只按 `type` 认。
- 有些内核把 **trip point（阈值）** 也放进 thermal_zone，`type` 叫 `cpu-hw-trip-0/1`，
  `temp` 恒等于阈值（实测 95000 = 95℃）。它不是温度计；混进最大值会让整机永远被判成 95℃，
  温控压满、实时偏移一直不为 0。现在 `type` 里带 `trip` 的一律不收，
  测试里用假 zone（正常 42℃ + trip 95℃）钉住了"最热仍是 42℃、th_steps=0"。
- **zone 路径启动时扫一次并缓存**：PJZ110 上 87 个 thermal_zone 里只有 29 个命中
  cpu/gpu/soc，缓存后每轮只读这 29 个 `temp`，不再每 5 秒 opendir 整棵目录；
  某个缓存路径读失败（驱动重建/热插拔）会自动重扫一次。
- 温控偏移同时作用于 CPU 和 GPU。最热的传感器常常就是 GPU，只压 CPU 等于闭环只做了一半。
- **温度读不到时按"低于恢复线"处理**：thermal zone 热插拔、驱动重建、部分机型熄屏后目录消失，
  这时不能把上一次热到的档位冻住（会变成永久 −25）。已压下的档位按 `TH_BACK` 逐档还回去，
  这段时间温控不再挡 PSI，所以可能出现"温控还在还档、PSI 已经允许借额度"并存，
  最长持续 `TH_BACK × 当前档数` 秒（默认 20×5 = 100 秒）。这是有意的取舍：
  传感器坏了不该同时锁死发热保护和卡顿放宽。
- 默认 `TH_HIGH=75` 是通用值。8 Elite 这类 SoC 到 75℃ 时内核往往已经开始砍频，主动闭环就晚了；
  觉得"热了没效果"时先把 `TH_HIGH` 试到 68~70（`TH_LOW` 要跟着留至少 5℃ 的迟滞带）。
  不同机型散热差异太大，这一项需要按真机温度曲线调，所以默认值没有替所有人拍板。
- 这是主动闭环，比等内核热管控直接砍频平滑。厂商那边同时在压时日志会写"厂商已压更低"，两边不互相盖。

### 电量阶梯（默认关）

出厂不压：低电量时先只管「封到设定值」，不再额外收紧，免得用户觉得"没电就更卡"。
在功能页「电量低的时候」打开后：不充电且容量低于 `BATT_LOW`（默认 20%）时，
再收紧 `BATT_LOW_CUT`（默认 5 个点）；低于 `BATT_CRIT`（默认 10%）
再叠 `BATT_CRIT_CUT`（默认 10 个点）。
它和 PSI/温控共用 `ADAPT_DOWN_MAX` 总闸，不会把 65% 压到 5%：

- **插电时不生效**：低电量正在充电时不该再压，充电态本来就在放宽。
- **分应用档位不吃这一刀**：CPU/GPU 的应用专属档是用户明确设的值，和"专属档不吃充电地板"同一个口径。
- 读不到容量（`capacity` 缺失/越界）就不收紧，不猜。
- 功能页「电量低的时候」有总开关和四档数值；关着（默认）时电量再低也不额外收紧。

### PSI 护栏（默认开，只借不拿）

读 `/proc/pressure/cpu` 的 `total`（累计 stall 微秒），按墙钟差分算出**速率**（ms/s），
和这台机自己最近 10 分钟的基线比：**超出 2 倍、且绝对值再高 30 ms/s** 才借，
一档一档往外借（`PSI_STEP`），总量不超过 `PSI_GAIN`；不卡了先等 `PSI_HOLD` 秒，
之后每隔 `PSI_BACK` 秒收回一档。**它只能往上放宽，永远不低于你设的值**。
基线只在**常态且当前没在借额度**时更新：借出期间 stall 高是放宽本身的结果，
拿它去抬高基线会让护栏在持续高载约 7 分钟后自己失效。游戏/满血/熄屏不更新，
也不推进档位、不攒额度。阈值附近来回抖动导致长期借出、基线长期不学时，
`status` 里 `psifrz` 会给出这一轮连续冻结的秒数。

**它测的是 CPU 排队，不是帧**：看不到 GPU、存储 IO、内存和帧时间；作为
"负载尖峰时别把 CPU 帽压太死"的护栏合理，不能当成"用户真的卡了"的判据。
**温控优先**：只要这一拍还有降温档在生效、而且温度确实读得到，PSI 一档都不借，旧额度清零；
`down_max` 已被电量阶梯占用的部分也不能再借出去。GPU 不吃 PSI（只吃温控/电量），
避免 CPU 排队信号把 GPU 功耗抬上去。
**无效样本只冻结、不学习**：PSI 读不到、熄屏很久回来、内核计数器被清，这一拍不算"不卡了"，
也不会拿 0 去洗基线；`status` 里的 `stall` 这时报 `-1`，页面不显示这一项。
`PSI_GAIN` / `TH_MAX` 填 0 = 整条环路关；非 0 时必须至少能凑出一整档
（`PSI_GAIN >= PSI_STEP`、`TH_MAX >= TH_STEP`），否则后端/守护会按"关"处理。

为什么不用 `avg10` 的绝对值判（"`<1%` 收紧、`>5%` 放宽"那种写法）：一加 13 上量过一轮，

| 状态（各 25 秒） | `some avg10` | stall 速率 | 最热 cpu/gpu |
|---|---|---|---|
| 静置·封顶 62/64/66/68 | 3.6–5.7 | 61.6 ms/s | 42–46 ℃ |
| 8 路满载·有帽 | 4.7→8.5 | 129.0 ms/s | 67→74.5 ℃ |
| 8 路满载·**没帽 100%** | 6.6→9.35 | 128.6 ms/s | 72→76.4 ℃ |
| 恢复封顶 | 6.7→4.8 | 68.6 ms/s | 47–50 ℃ |

满载时**有没有帽，stall 速率一模一样**（129 vs 129 ms/s）——`some` 只看"有没有任务在等 CPU"，
八颗核都被 `yes` 塞满时它不看频率。而静置就有 4~5 个 `avg10`。
所以按绝对阈值写，开机几秒就会被判成"卡了"，一路放宽到 100% 停在那儿，**模块把自己关掉**。
判据因此改成"相对这台机自己的基线"，并且借出量有硬上限。

### 禁止 GPU Boost（默认开）

`GPU_BOOST_OFF=1` 不是再压一道上限，而是把厂商抬频的源头关掉：

- 高通：`dcvs_boost`（DCVS 抬频）、`touch_wake`（触摸唤醒抬频）、
  `devfreq_boost` 模块的输入 / 唤醒 boost 时长
- 天玑：`/sys/kernel/ged/hal/custom_boost_gpu_freq`。这个节点是 **OPP 索引**，
  不是频率；0 通常是最高频档，写 0 反而会把 boost 锁到最高。模块从
  `stack_working_opp_table`（或 `gpufreq_opp_dump`）里按频率找最低频那一档的真实索引，
  再写进去；表读不到就不动，不猜。
  只动 boost 目标，不改 `custom_upbound_gpu_freq`（上限）、不关 `fpsgo` / `gpu_dvfs_enable`。

节点存在才写，原值记进账本：游戏、满血、熄屏交还时自动还原；
关掉开关或在页面上取消，也会立刻还原。不需要重启。
这个开关同时做两层：先关"因"（不再产生抬频请求），再把"果"压回最低档
（`scaling_min_freq`/devfreq 下限）。旧键 `GPU_MIN_LOCK` 已并入，不再单独控制。
某些内核上没有这些节点，开关会静默空转，不报错。

### CPU 下限锁到底（`CPU_MIN_LOCK`，默认关）

常态每拍只读各簇 `scaling_min_freq`，高于 `cpuinfo_min_freq` 才写；全局 30 秒最多写一次，
避免和 perfd 抢节点拖慢唤醒。连续 3 次写完被内核夹回（例如某些 ROM 把下限锁在 556800），
会自动停 10 分钟并在日志里说明；游戏/满血/熄屏解除时按账本还原。
它压的是**下限**，和 `CPU_PCT_*` 的**上限**不冲突；轻载时 CPU 不再长期贴着厂商地板跑。

### GPU 的封顶为什么可能比滑杆百分比低

GPU 的目标是「滑杆百分比 + 实时偏移（温控 / 电量；PSI 不参与）」，再向下吸附到真实频点。
偏移到 -25 档时，50% 先变成 25%；如果目标低于 GPU 的最低频点，会落到最低档
（例如 282 MHz），和 CPU 的封顶语义一致。配置页现在会在 SoC 标题下写出当前
偏移量；不想要这层让路，就在「功能」页把温控 / PSI 护栏关掉。
**适配页「封顶后」一列只算设定值的吸附**（100% 就是 1200MHz），不叠加实时偏移；
实际生效值（偏移、厂商上限都算进去）在「GPU 封顶」卡片和状态里看，两处不混。

## 配置页顶部的 SoC 与频率表

SoC 型号依次读 `ro.soc.model` → `ro.board.platform` → `ro.chipname` →
`ro.product.model`，取**最后一个空格/逗号分隔的词**并转小写
（属性值常是 `Qualcomm Technologies, Inc SM8750` 这种带前缀的）。
四个都取不到才显示"未知"。

顶上还会列出每个核心与 GPU 的「原生最高频率 → 封顶后」：

```
CPU0  68%     1901 MHz  →  1292 MHz
CPU3  66%     3187 MHz  →  2103 MHz
GPU KGSL 45%   900 MHz  →   405 MHz
```

原生最高频率是硬件标称值，四舍五入显示；**封顶那一列一律向下取整**——
真实封顶 1292.544 MHz 就显示 1292，不显示 1293。往上凑的话，拿显示值反算
百分比会发现比设定值还大，"绝不超过设定百分比"这个卖点就成了空话。

拖动百分比滑杆时封顶值实时重算。标 `≈` 的表示**还没保存**（守护此刻
还不知道这个值），同样向下取整，和守护的吸附策略一致。
这一列显示的是**设定值**对应哪个频点，不叠加实时偏移；偏移后的实际值看
「GPU 封顶」卡片（硬件上限 / 当前封顶）和首页状态。

机上手动确认（两条都要看）：

```sh
$MODDIR/socfreqd export | grep '^soc='      # 期望 soc=sm8750
$MODDIR/socfreqd export | grep -E 'gpu_(max|unit)'   # 期望 gpu_unit=Hz
```
