# Soc智能限频

CPU / GPU 频率封顶模块。常态按百分比压住性能上限，进游戏自动放开并把
控制权交回系统。

- 装在 KernelSU / Magisk / APatch 下
- 任意 SoC，按簇自动分档，不写死 CPU 编号
- 高通 KGSL 与 MTK Mali 都支持
- 附带 WebUI 与深度睡眠（熄屏 20 秒冻结后台、7:30 进 Doze，可配豁免名单与唤醒榜）

作者：梦笙Mess1on　　版本：V1.6

---

## 它做什么

**平时** —— 把每个 CPU 簇和 GPU 的最高频率限制在设定百分比以内。
默认 CPU 64~66%（超大核与小核均 65%）、GPU 45%，可调。守护每 5 秒查一次，系统把它顶回去了就压回来。

**打游戏时** —— 认出当前前台是游戏（认的是包名，名单在 `games.txt`），
立刻解除封顶，并把相关节点的写权限交给系统，让系统自己的调度器接管。
不在游戏里就恢复正常封顶。进入游戏的那一刻，首页顶部的状态徽标
会从「常态限频中」变成「游戏中 · 已解锁」。徽标旁边不再摆「前台 / 档位」那一格：
徽标已经说明现在处于哪一种档，具体是哪个应用、封到多少，
在「应用」页那一列里看得更全，小格子里塞一串折行的包名只是添乱。

**用一阵子之后** —— 守护记住"帽真的扣在身上时，各簇实际跑到哪一档"，
首页的「智能建议」按这份记录说这一簇该放宽还是该收紧（见下面「智能学习与建议」）。
默认档位是给一整批机器定的，建议是给手上这一台定的。

这样做的用意是：模块平时只当"节流阀"，该发挥的时候不跟系统抢。

## 为什么这样设计

### 按簇分档，不按 CPU 编号

不同 SoC 的簇数、编号都不一样，policy0 未必是最强核。
本模块读每个 policy 的 `cpuinfo_max_freq`，排序去重得出频率阶梯，
再按位置分配百分比。所以换机型不用改配置。

### 封顶值向下吸附

内核只认自己频点表里的值。算出百分比后取**不超过该值的最高可用频点**。
这保证实际生效的频率一定不超过你设的百分比，不会因为向上取整而超。
如果某些设备的频点表很稀疏，可能比设定值低一档。

### 和系统调度相处

直接跟厂商框架对着改上限会互相拉扯，一方压回一方抬上去，来回抖。
所以分两种情况：

- **常态**：巡检压回，够用了
- **游戏态**：不硬顶，而是把写权限（666）交给系统，让它爱怎么调怎么调

系统调度器不在白名单里就不碰 —— `hmbird`、`scx` 这类一律不改。

### KernelSU 热安装：装完不用重启

`customize.sh` 里按 KernelSU 的约定申请热安装（`MODULE_HOT_INSTALL_REQUEST`），
并指定 `scripts/hotinstall.sh` 作为安装后脚本。支持这个约定的管理器会在安装完成后：

1. 用新版本替换 `/data/adb/modules/soc_freqcap`（模块文件、**WebUI**、`action.sh`、
   `module.prop` 立即生效，管理器不再提示重启）；
2. 执行 `scripts/hotinstall.sh`：先让旧的深睡守护退出（它会解冻、unforce 并撤掉临时白名单），
   再用新二进制 `restart` 主守护（等旧实例恢复完频率再接手），深睡开关开着就重新拉起。

模块处于「暂停」状态时保持停住，不替用户恢复；配置、名单、学习样本都在
`/data/adb/soc_freqcap`，不受热安装影响。

不支持这个约定的管理器会忽略这两个变量，自动回到"重启后生效"，不会更糟。
本模块不写 `system/`、也不依赖 `service.sh` 才启动，所以适合热安装；
热安装时 `service.sh` 不会执行，守护由 `hotinstall.sh` 负责拉起。

版本边界：**SukiSU Ultra 从 v4.2.1-r2 起支持**（hot install 在 2026-10-15 合入）；
4.1.3 及更早的 ksud 没有这段实现，安装界面会提示"当前管理器不支持热安装"，
并照常走重启后生效。KernelSU 官方管理器按官方文档实现该约定。安装脚本会用
`KSU_HAS_HOT_INSTALL` 判断并如实提示，不会把"仍需重启"说成"已热安装"。

### WebUI 的 root 桥：确认状态

本模块按顺序探测四个接口。**下面的"验证状态"如实写，不替没验证过的打包票：**

| 接口 | 注入者 | 返回形态 | 验证状态 |
|---|---|---|---|
| `kernelsu` | 新版 KernelSU Manager | Promise，`string` 或 `{code,stdout,stderr}` | 已验证（在模拟环境逐形态喂桩） |
| `ksu` | 旧版 KernelSU / APatch | 回调 `(errno, stdout, stderr)` | 已验证（同上） |
| `mm` | MM 管理器 | 假设为 Promise\<string\> | **未验证**，返回契约是照文档推测的 |
| `magisk` | Magisk Manager | 假设为 Promise\<string\> | **未验证**，多半不对 |

Magisk Manager 很可能不注入 `magisk.exec`（它那套是 `requestRoot` + WebView 授权），
所以 **Magisk 的 WebUI 很可能用不了**，只有命令行能用。
这一条没有可验证的依据，所以不写成"支持"。

打开 WebUI 首页，状态卡底部会显示「桥接 ksu」——那是本机实际命中的接口名。
显示"管理器不支持"就是四条都没探到，此时命令行仍然可用：

> 这一栏**只认接口本身**（`window.kernelsu.exec` 之类的真接口），
> 没探到就显示「无」。它**不会**去 `window` 里按名字正则搜索——
> 那会命中浏览器自带的 `oncommand`（里面含 "mm"，被 `/mm/` 匹配上），
> 于是显示成 `oncommand(无exec)`。报一个假的名字比报"无"更糟：
> 用户会以为走通了 MM 那条路，实际上一条都没探到。

```sh
D=/data/adb/modules/soc_freqcap   # APatch 则是 /data/adb/ap/modules/soc_freqcap
sh $D/socfreqd status
sh $D/socfreqd probe
```

## 出问题能自己恢复

每次写 sysfs 之前，先把"原来的值是多少、原来什么权限"记进 journal。
正常退出时按 journal 还原；被强杀（kill -9）来不及还原也没关系，
下次启动会先按 journal 还原再取新的基准值。

所以强杀守护不会让手机一直卡在低频上。

### 卸载后频率没回原厂 / 出现“限制性能的组件”弹窗

模块只写 CPU/GPU 的 `scaling_max_freq` 等节点，**重启后内核会把这些节点重置**。
如果重启后频率仍然偏低，先确认模块真的不在了：

```sh
ls /data/adb/modules /data/adb/modules_update 2>/dev/null | grep soc_freqcap
pidof socfreqd
ps -A | grep deep_sleep
```

再看当前上限和硬件最高：

```sh
for p in /sys/devices/system/cpu/cpufreq/policy*; do
  echo "$p max=$(cat $p/scaling_max_freq) hw=$(cat $p/cpuinfo_max_freq)"
done
```

- 两个目录都没有 `soc_freqcap`、也没有进程 → 本模块已经清干净；此时上限仍低，是**别的性能工具 /
  厂商省电 / 游戏助手**在写节点或禁用了性能组件，不是本模块的残留。
- **`/data/adb/modules_update/soc_freqcap` 还在**：这是一次没应用完的更新，重启后会被装回去。
  在管理器里再卸载一次，或删掉这个待更新目录后再重启。这就是"卸载了又自己回来"的常见原因。
- **Scene 的弹窗**（“检测到系统中可能限制性能的组件”）是 Scene 看到有人在改 CPU/性能节点；
  Scene 自己也有 CPU 频率 / 开机情景模式。检查 Scene 的「开机应用 / 情景模式 / 性能模式」
  是否设了上限，并看它弹窗里要禁用的那个“组件”到底是系统组件还是 `soc_freqcap`。
  本模块没有任何对话框，也不会在卸载后保留进程。
- 临时把上限放回硬件最高（重启也会重置，先应急用）：
  ```sh
  for p in /sys/devices/system/cpu/cpufreq/policy*; do
    cat $p/cpuinfo_max_freq > $p/scaling_max_freq 2>/dev/null
  done
  dumpsys deviceidle unforce
  settings delete global device_idle_constants
  ```
- **截图里“检测到系统中可能限制性能的组件，是否将其禁用(重启手机后还原)?”不是本模块的 UI**：
  本模块没有任何对话框。点「取消」后看它属于哪个 App（常见是 Scene、爱玩机、游戏助手一类的性能工具），
  把那个 App 的名字/版本发过来才能继续定位。
- 本模块的卸载流程：停守护 → 按 journal 还原 → 没有 journal 时把 CPU 上限放回硬件最高 →
  停深睡并解冻、撤临时白名单、退出强制空闲 → 删数据目录。卸载脚本在 `uninstall.sh`，可直接读。

## 配置

全在 `/data/adb/soc_freqcap/socfreq.conf` 里，每项都有注释。常用的几项：

| 项 | 默认 | 说明 |
|---|---|---|
| `CPU_PCT_BIG` | 65 | 最强核的封顶百分比 |
| `CPU_PCT_MID2` | 64 | 次强核（只有 4 簇以上机型用得上） |
| `CPU_PCT_MID` | 66 | 中间档 |
| `CPU_PCT_LITTLE` | 65 | 最弱核 |
| `GPU_PCT` | 45 | GPU 封顶百分比 |
| `GPU_MIN_LOCK` | 1 | 是否把 GPU 下限钉在最低档，抵消 Boost 越界 |
| `INTERVAL` | 5 | 巡检间隔（秒） |
| `GAME_GRACE_SEC` | 10 | 退出游戏后继续保持解锁的秒数 |
| `SCREEN_POLICY` | uncap（新装）/ keep（升级） | 熄屏策略：交还系统并轻巡检，或保持旧行为 |
| `SOFF_INTERVAL` | 15 | 熄屏轻巡检周期（秒，5~300） |
| `SCREEN_STATE_PATH` | 空 | 亮屏信号文件；空 = 自动挑选 |
| `SCREEN_UNCAP` | 0 | 旧键兼容：没有 `SCREEN_POLICY` 时 1 映射成 uncap |
| `IDLE_CURRENT_MA` / `IDLE_HOLD_CYCLE` | 250 / 2 | 熄屏电流低于多少 mA、连续几轮后进深度空闲 |
| `IDLE_INTERVAL` / `WAKE_DELTA_MA` | 30 / 150 | 深度空闲周期；电流比熄屏基线高多少 mA 才触发一次亮屏复核 |
| `BATT_CURRENT_PATH` / `BATT_CURRENT_UNIT` | battery/current_now / ma | 电流节点与单位；ua 会先 /1000，符号统一取绝对值 |
| `BOOT_FULL_S` | 60 | 开机后满血窗口秒数（0 = 关掉这个功能） |
| `CPU_GOVERNOR` | 空（默认不干预） | 留空 = 一个 `scaling_governor` 节点都不写 |
| `LEARN` | 1 | 智能学习采样（0 = 停采并清空已采样本） |
| `LEARN_APP` | 0 | 按应用学习（默认关，见「按应用学习」） |
| `LEARN_APP_MIN` / `LEARN_APP_DAY` | 30 / 2 | 一个应用要自己攒够多少分钟、跨几天才敢给建议 |
| `LEARN_MODE` | balanced | 学习偏好：`eco` 省电（允许下调大核）/ `balanced` 均衡（大核只升不降）/ `performance` 性能（只升不降、上升更积极） |
| `CHG_UNCAP` / `CHG_PCT` | 1 / 100 | 插电时把常态封顶至少抬到多少（见「实时偏移」） |
| `TH_CAP` / `TH_HIGH` / `TH_LOW` | 1 / 75 / 68 | 温控闭环开关与触发、恢复温度（℃，中间是迟滞带） |
| `TH_STEP` / `TH_MAX` / `TH_BACK` | 5 / 25 / 20 | 每档压多少个百分点、最多压多少、每多少秒还一档 |
| `PSI_ADAPT` / `PSI_GAIN` / `PSI_STEP` | 1 / 10 / 5 | PSI 护栏开关与最多借出、每档多少个百分点 |
| `PSI_HOLD` / `PSI_BACK` | 30 / 15 | 判到卡后额度至少借住多久、不卡了每多少秒收回一档 |
| `ADAPT_UP_MAX` / `ADAPT_DOWN_MAX` | 15 / 30 | 合计偏移的总闸（百分点）；0 = 那一侧封死 |
| `BATT_STEP` | 0 | 电量阶梯开关（默认关）；打开后低电量才额外收紧 |
| `BATT_LOW` / `BATT_LOW_CUT` | 20 / 5 | 低于多少电量（%）压第一刀、压几个点 |
| `BATT_CRIT` / `BATT_CRIT_CUT` | 10 / 10 | 更低的第二档与第二刀（必须低于 BATT_LOW） |

改错了不会生效 —— 数值会被夹回合法范围，调速器名只认白名单里的词。

### 按芯片套的预设

芯片默认值只有一份来源：`adapt/sm8750.conf` / `adapt/sm8850.conf` 里的 `default_*`。
装机时读 `ro.soc.model`（拿不到再退到 `ro.board.platform`），命中文件后：

| 芯片代号 | 机型 | 超大核 | 小核 | GPU | 温控/PSI |
|---|---|---|---|---|---|
| `SM8750` | 骁龙 8 Elite | 66% | 68% | 50% | 75/68℃、PSI_GAIN 10 |
| `SM8850` | 骁龙 8 Elite Gen 5 | 64% | 69% | 50% | 75/68℃、PSI_GAIN 10 |
| 其它 | — | 不动，保持通用默认 | | | |

**只对全新安装生效**。升级安装一律不碰用户配置——用户刻意填的 65 可能刚好等于
旧默认值，用"值等于默认就覆盖"的启发式会把它改掉。芯片默认值和你打开配置看到的值
是同一份，不存在守护 fallback 里的第二套。

8E/8E5 都是 m=2 双簇，`CPU_PCT_MID` / `MID2` 在这类机器上不生效，适配文件只给
BIG/LITTLE。百分比最终会向下吸附到频点表；换机型先用
`cat /sys/devices/system/cpu/cpufreq/policy6/cpuinfo_max_freq` 确认硬件顶点，
再看吸到的实际频率。候选值发布前仍按真机温度/续航曲线复测。

**升级时怎么处理**：一个 `default_*` 都不套，用户配置逐字节保留。
不靠"值等于默认就覆盖"的启发式——用户刻意填的 65 可能刚好等于旧默认值，
那样会被静默改掉。升级只追加配置里不存在的新键（`SCREEN_POLICY` 除外）。

### 这台机上没有的那一档，不摆控件

骁龙 8 Elite 这类两档/三档芯片，`MID2`、`MID` 可能天生落空。
守护把这种情况报成 `coretier_CPU_PCT_MID2=`（空），页面对应的行**只留名字和
（未检测到）**：滑杆摘掉、百分比不显示、保存时也不写进 conf。
摆一个"调了也没用"的滑杆在那里，只会让人以为是自己设了没生效、保存出了问题。

反过来，**"检测失败"（守护版本旧或读不到）时滑杆照旧保留** ——
那种情况下我们并不知道这台机有没有这一档，不该替用户把控件藏掉。

## 分应用档位（app_modes.conf）

`/data/adb/soc_freqcap/app_modes.conf`，一行一条 `包名=值`：

| 值 | 含义 |
|---|---|
| `full` | 这个应用在**前台时**整个交还系统（CPU 和 GPU 都不封顶） |
| `1~100` | CPU 四簇统一按这个百分比封顶；**GPU 仍按全局的 `GPU_PCT`**（老写法，语义不变） |
| `80:40` | CPU 80%、GPU 40%，两段各自吸附到实际频点 |
| `80:` / `:40` | 只设一边，另一边跟随全局 |
| `keep` | 熄屏那一刻在这个应用前台时不交还系统，继续按全局百分比巡检 |

优先级：**游戏名单 > 满血窗口（开机 / 熄屏解除）> 应用专属 > 全局百分比**。
应用专属排在满血窗口之后是有意的——熄屏解除是用户主动开的全局开关，
屏幕都灭了还守着某个相机的 80% 没有意义。

典型用法是把相机、录像、地图设成 `full`：这些应用要吃完整性能，
而它们本来也不在"日常待机节流"的目标场景里。想反过来压住某个应用的 GPU 发热
（比如录像、长时间导航），用 `70:40` 给 GPU 单独设一道比全局更低的帽；
GPU 段同样吃温控和 PSI 偏移，但不吃"插电地板"。

守护按 mtime 热重载，改完就生效，不用重启手机。写的一侧（`api.sh` / WebUI）
有校验：坏包名、越界数字直接被拒；读的一侧（守护）对坏行是**整条忽略**，
不是当成 0%——手改文件写错不该让手机突然变成砖。

WebUI 的入口在「应用 → 分应用档位」（和名单、候选栏在同一页，都是按应用定的事）：
先选一个 CPU 档位（满血 / 90 / 80 / … / 自定义）和 GPU 档位（跟随全局 / 90 / … / 自定义），
按「＋ 添加应用」展开**已安装应用列表**：默认是第三方应用 + 系统里有桌面入口的那些
（相机、设置、相册、信息…）。列表下面有**「显示系统应用」**开关：勾上连 provider / 服务 /
组件一起列，给"要选某个系统包、但默认列表里没有"的机器用。部分 ROM 把
`cmd package query-activities` 裁掉了，后端会自动回退到全部系统包，不会只剩第三方。
点一下就写入；已经设过的行有两个下拉，CPU 和 GPU 可以分开改，× 删除。

系统应用在 APK 里的名字常是英文（OPPO 相机叫 `Camera`、设置叫 `Settings`），
所以搜索框做了中文别名：搜「相机 / 设置 / 时钟 / 相册 / 文件 / 联系人…」都能找到。
**别名只影响搜索，不改显示名**——名字仍以 APK 里的 `android:label` 为准，不替厂商翻译。
APK label 解析不出来（引用型 label / 资源被裁）的包，用 `scripts/builtin_labels.txt` 的
中文名兜底；只填空白，不覆盖已有英文名。列表先画 80 行，滚到底点「显示更多」再追加；
滑动时暂停批量取图标/名字，停手后再发 root 调用，避免在管理器里滑起来一卡一卡。
深睡页的「永久豁免」默认也只列第三方；同一个「显示系统应用」开关打开后可以选系统包，
厂商短信 / 电话这类不在 `-3` 里的包就能手动加。

**相机类默认满血。** 装机时按 `scripts/builtin_modes.txt` 里各家相机的包名
（`com.android.camera`、`com.oplus.camera`、`com.sec.android.app.camera`、`com.vivo.camera` 等），
只给**本机已安装**的那些追加 `pkg=full  #builtin`。取景、快门、连拍、4K 录像都吃瞬时响应，
相机在前台本来也不在"日常待机节流"的目标里。这份清单**不覆盖你的选择**：

- 已经给这个包设过任何值（哪怕手写 80）→ 不动；
- 删掉那一行 → 以后升级不会塞回来（基准 `builtin_modes.base.txt` 记着上一版清单，
  只有**新版清单里新增**的包才会补）；
- 想换回百分比或 `keep`，直接在「分应用档位」里改即可。

这里不能做"把**当前前台**应用设为满血"：这一页是在管理器里打开的，
那一刻守护抓到的前台**永远是管理器自己**，那个按钮唯一能设的对象就是管理器。
现在首页连"当前前台是哪个"都不显示了（上一段说了原因），
要设档位就在应用列表里自己挑。

命令行同理（走的是同一个 `api.sh`，所以校验也一样）：

```sh
A=/data/adb/modules/soc_freqcap/webroot/api.sh
sh $A modes_list                          # 看现在设了哪些
sh $A modes_set com.android.camera full   # 相机满血
sh $A modes_set com.autonavi.minimap 80   # 地图按 80% 封
sh $A modes_set com.android.camera 70:40  # CPU 70%、GPU 40%
sh $A modes_del com.android.camera        # 删掉
```

直接编辑 `/data/adb/soc_freqcap/app_modes.conf` 也行，但坏行会被守护整条忽略
（不是当成 0%）——手改写错不该让手机突然不动。

开了「按应用学习」之后，这份文件里可能出现带来源标记的行：

```
com.miHoYo.Yuanshen=70  #learn     ← 学习写回的，会被学习继续更新
com.android.camera=full            ← 你填的，学习一个字都不改
```

标记在值后面，守护读值时先截掉注释（截不掉就是整行被当坏值丢掉，
页面上列着档位、核心上却没戴帽）。想收回自己管：把标记删掉，或在页面上
点那条「学出来」的标、或直接改一次值。

**配置为什么不在模块目录里。** 管理器升级模块是「先删 `/data/adb/modules/<id>`
再解包」，配置放模块目录里就会被新包的默认值盖掉，用户调过的东西一次升级就没。
所以装在 `/data/adb/soc_freqcap/`（`customize.sh` 首次安装时搬过去，
`api.sh` 里还有一道兜底）。也没放 `/sdcard`：那里是 FUSE + `media_rw` +
MediaProvider 的一套权限，root 写进去的文件应用侧未必读得到。

**开机满血窗口**（`BOOT_FULL_S`）：`service.sh` 在等到 `boot_completed` 之后、
正式接管之前，往 `/data/adb/soc_freqcap/run/boot_boost_until` 写一个截止秒数
（读 `/proc/uptime`，不用墙钟——开机阶段时间会被 NTP 往前跳）。
守护在主循环里看到没过期就整个交还系统，到期后自己压回常态封顶。
开机动画、首屏加载、桌面重建挤在那几十秒里，封顶会让它明显变慢。

**熄屏轻巡检**（`SCREEN_POLICY`）：新装默认 `uncap`，升级用户没有这个键时保持
`keep`（旧行为）。`uncap` 下熄屏后不再 fork `dumpsys window`、不跑 PSI/温控/学习，
只解除封顶并把节点权限交还系统；每 `SOFF_INTERVAL`（默认 15s）只读一个亮屏信号。
亮屏后立刻恢复常态巡检，游戏/满血应用熄屏时保留原交权状态，不会先压一拍再解锁。

亮屏信号的选择：启动时自动挑 `fb0/blank`（0=亮），没有就挑任意
`backlight/*/brightness`（>0=亮）。实测在一加 13 / Android 17 上 `fb0/blank`
不存在，且锁屏亮屏时 `dumpsys window` 仍是 `mSleeping=true`（keyguard token），
所以不拿 `mSleeping` 当判据；亮度节点 0/1127 与 `mWakefulness` 完全一致。
节点读不到时退 `dumpsys power` 兜底；任何判据都失败时按「亮屏」处理——
探测失败的后果是维持封顶，不是悄悄放开。

`SOFF_INTERVAL` 只影响熄屏态的亮屏检测延迟（默认 15s）。想回到旧行为
（熄屏照样封顶、5s 巡检）就把 `SCREEN_POLICY=keep`；这个回退不依赖改代码或降级。

**深度空闲（P0b）：** 熄屏后电流持续低于 `IDLE_CURRENT_MA`（默认 250mA）达到
`IDLE_HOLD_CYCLE` 轮，巡检周期从 15s 拉到 `IDLE_INTERVAL`（默认 30s）。亮屏信号仍每轮读，
电流只做辅助：比熄屏 EMA 基线高出 `WAKE_DELTA_MA`（默认 150mA）时才多问一次
`dumpsys power`，不拿绝对阈值。电流读不到就停在 SCREEN_OFF，永不进深睡。
电流单位在 `BATT_CURRENT_UNIT` 里显式写 `ua`/`ma`——一加 13 实测是 mA 且充电为负，
代码统一取绝对值；换 ROM 先按 `_tools/measure_screen_state.sh` 复测再改这一项。

**分应用 `keep`：** `app_modes.conf` 里写 `包名=keep`，这个包在熄屏那一刻是前台时
**不交还系统**，继续按全局百分比做轻巡检（只读频率节点、被顶回就压回），适合 Termux
编译、挂机下载。它只影响熄屏，亮屏时仍按全局分档；学习不会把它改写成数字档位。

## 智能学习与建议

默认档位是按骁龙 8 Elite 的功耗曲线给的一组通用值。你这台机器上**真跑出来的频率分布**
才是该用的值，但没人会自己盯一整天频率去算——所以让守护自己记。

**采样**在守护里（`src/learn.c`），只在**封顶真的生效**的那段累计：亮屏、不在开机满血窗口、
不在游戏或分应用满血、没暂停。熄屏和解锁时段没有帽，采进来的分布回答不了
"这道帽扣得紧不紧"，只会把建议往高了带。

每 5 分钟落一次盘，写 `/data/adb/soc_freqcap/learn.tsv`，一个采样对象一行：
这簇的**频率驻留分布**（按"占硬件最高频的百分比"切成 24 个等宽桶，每桶 4.17%）、
**顶帽时长**（跑在上限 97% 以上的驻留）、**被压时长**、墙钟采样时长、
28 天的"这天采到过"位图，以及**这一行是在哪道配置帽下攒的**（百分比）。
最后一项是判据的凭据：改了百分比，旧帽下的分布就不参与新建议。
凭据记的是**你设的百分比**，不是这一拍生效值——插电地板、PSI 借还、温控降档
都不会改写它，所以插拔电源、温度抖一档不会把已经攒了几小时的样本清零。
戴着应用专属档位的那一拍只记应用行，全局行原样不动（哪怕应用的百分比不同）。

**GPU 也算一档**（第 5 档，键名 `GPU_PCT`）：驻留取自 KGSL 的 `gpu_clock_stats`
—— 一行 N 个数，和 `gpu_available_frequencies` 按位置一一对应。
不用 devfreq 自带的 `trans_stat`：KGSL 走厂商 governor，那张表最后一列 `time(ms)`
在真机上 5 秒纹丝不动，采了等于没采；也不用 `cur_freq` 凑数 —— 它空闲时趴在最低档，
会把分布做成"GPU 永远用不满"的假结论。机器上没有 `gpu_clock_stats` 这个节点时，
就干脆不出 GPU 那一行，CPU 那几档照采。

单位一律不换算：`time_in_state` 在不同内核里可能是 jiffies 也可能是毫秒，
所以判据只用**比值**（顶帽占比）、**分布里的位置**（p90 / p99，按桶内线性插值）
和**贴帽两桶**（当前帽所在的那一桶 + 下面一桶，约帽下 8 个点）的占比，
需要"多少分钟"时取真实流逝的墙钟时间。

- **p99** 回答"最忙的那一小段跑到多高"：贴帽说明这道帽真的在拦。
- **贴帽两桶** 回答"平时是不是也经常贴着这道帽跑"：占 25% 以上就算爆发压力，
  这时即使顶帽占比不高（顶帽只数 97% 以上那一小段），也不该再往下收。
  这里**不能取绝对频率最高的两个桶（22/23）**：帽通常只有 60~70%，
  那两桶永远是空的，这个信号会一直是 0，建议又只剩"往下收"。
- **顶帽占比** 仍然用来防止"看着有余量、其实经常撞帽"的误判。

**判据**写在 `webroot/api.sh` 的 `advice` 子命令里（awk），不在二进制里：
改阈值不用重编，也能在 PC 上喂一份造出来的样本直接把每条分支验一遍。

| 方向 | 条件 |
|---|---|
| 放宽一档（+5%） | p99 距当前帽 ≤ 4.17 个点（贴帽），且（顶帽占比 ≥ 10% 或 贴帽两桶 ≥ 25%），且采满 60 分钟、跨 2 天（省电 3 天 / 性能 1 天） |
| 收紧一档（−5%） | 顶帽占比 ≤ 10%、p99 ≤ 当前帽 − 15 个点，且 2 天 / 120 分钟；只作用于非大核，性能模式不收紧 |
| 大核收紧（−5%） | 只在省电模式：p99 ≤ 当前帽 − 25 个点，且 7 天 / 180 分钟；均衡和性能下大核只升不降 |
| 维持 | 其余情况，并把"p99 离帽几个点、顶帽多少、贴帽两桶多少"照实写出来 |

**大核（超大核）为什么不再自动往下收：** 它是爆发型负载，p99 低不代表不需要——
一次冷启动、一次相机对焦就要那几毫秒的高频，平时分布再低也不该把上限削掉。
所以均衡/性能模式下大核只升不降；省电模式才允许在"7 天、180 分钟、
p99 离帽 25 个点"这种强证据下收一档。觉得大核该降的人，切到省电模式就行。

**学习偏好**（配置页「功能 · 学习偏好」）只改建议的方向，不改实时封顶：

| 偏好 | 行为 |
|---|---|
| 省电 `eco` | 允许下调大核；放宽要 3 天样本 |
| 均衡 `balanced`（默认） | 大核只升不降；其余档可升可降；放宽要 2 天样本 |
| 性能 `performance` | 所有档位只升不降（不自动收紧）；放宽只要 1 天样本 |

**反向冷却 7 天：** 刚往一个方向调过 5%，7 天内不建议反着改，
避免"升一档→过两天又降回去"来回拉锯。记录在 `learn_meta.tsv`，手改配置也会被识别。

升和降的门槛故意不对称：放宽只决定"能跑多快"，收紧决定"该快的时候够不够快"。
样本不够就不动——模块把机器弄得发卡顿，比少省一点电严重得多。
建议值只加/减一档（5%），不会一步跳到某个算出来的数；
每次应用都要用户点一下，页面不会自己改配置。

**不需要"学满几天才给东西看"**：打开首页就有卡片，每行下面都带证据
（顶帽、贴帽两桶、p99、采样分钟/天数），采到多少显示多少；只是没到门槛时
建议写"样本不够（现在 1 天 5 分钟，要 2 天 60 分钟）"，而不是空白。
**一分钟都没采到时**（页面显示"已学到 0 天"）卡片会点名当前被哪道门挡着：
熄屏、插电不封顶、实时偏移（借频/降温）、游戏满血或模块暂停，并给出怎么开始累计。
文案里那句**「建议学习 3 天以上效果更好」**是因为：
一天的样本只代表你那一刻的使用（比如刚打完游戏），
跨到第三天，早上后台、白天刷视频、晚上打游戏这三段才会都被记进同一个分布。

**旧版样本会清空一次：** v1 的行只有 12 个桶、没有"当时是哪道帽"，
和新判据的帽有效性对不上。升级后守护把两份样本一起删掉，留一个
`learn.tsv.v2reset` 标记，页面提示"学习算法已升级，重新积累 2~3 天"。
不清的话，旧帽下的分布会继续推着建议往一个方向走，比从零开始更糟。

**天数怎么算：** 从第一次真正采样起，每满 24 小时算一天，不按本地零点、更不按 UTC 零点切。
起点存在 `learn.tsv.since`，守护重启不会重置；`learn.tsv.since` 和学习样本一起被「清零重学」删掉。
所以装完 9 小时仍显示 1 天，满 24 小时才会变成 2 天。
v1 升级时会整份换新（见上一段）；如果只是起点文件单独丢了、样本还在，
第一次会按"今天用过"补一天，从当前时刻重新起算。

页面上三个动作：

- **应用建议** —— 只把判成升/降的那几档写成新封顶（走的就是滑杆那条 `conf_set`，
  校验和原子写只有一份实现），维持的那几档一个字不动。按应用那几条一起点：
  它们走 `modes_learn` 写进 `app_modes.conf`，手填过的不会被改。
- **重新读取** —— 重算一次；建议不进 5 秒轮询，样本本来就 5 分钟才落一次盘。
- **清零重学** —— 删掉 `learn.tsv`、`learn_app.tsv` 和计时起点 `learn.tsv.since`，
  并撤掉学习写回的那批应用档位。
  守护每轮巡检都查一次文件在不在，
  删了就把内存里的累计归零（退出时那一次落盘也先查这一条，
  免得"显示已清零、数据一条没少"），不用重启手机。删之前要连点两次确认。

`LEARN=0`（配置页那个开关，或 conf 里那一行）就是**停采并丢掉样本**：
下次打开是从零开始，不拿半年前的分布给现在的使用习惯出建议。
配置里没有这一行时按"开"处理——升级装机不会重写用户已有的 `socfreq.conf`。

命令行有同样一条：音量键菜单第 9 项（`sh webroot/api.sh advice`），
读的是同一个子命令、同一份判据。

### 按应用学习（`LEARN_APP`，默认关）

全局那份记录回答的是"这台机平时该定多少"。可软件之间的差别大到一份分布盖不住：
同一个包贴着帽跑的时候，另一个可能连一半都没用到。打开之后，同一份驻留分布会
**另记一份到前台应用头上**，建议就能细到"这个应用可以放宽一档 / 收紧一档"。

- **每个前台应用都学。** 已经设了数字档位的按那道帽算；没设的按全局四簇的
  平均当基准（记录里标着 `base=global`，页面挂「全局」标），点应用会新建一条
  专属档位。`full` 的包整条跳过——满血是把整个系统交还回去，没有帽可判。
  游戏名单里的包在前台时同样解锁，学不到东西。
- **专属帽只记应用，不进全局。** 某个应用戴着它自己的 75% 时，这一段分布不记进
  全局样本；否则就是拿应用帽下的表现去建议全局值，两层会互相把对方带偏。
  只设了 GPU 的档位（`:40`）也算应用上下文——那段 GPU 驻留是在应用帽下采的。
  反过来，全局帽生效的那一段两层都记：它既是全局样本，也是这个包在全局帽下的表现。
- **换帽就从零重攒。** 改了某个包的数字档位、或者改了全局百分比，这个包的
  应用行会清空重来。顶帽率是按"离当时那道帽多近"记的，两道帽的分布混在一起，
  建议会沿着旧帽一路加码（70→75→80），哪怕应用早就碰不到新帽了。
- **门槛按这个包自己算。** 默认要它自己攒够 30 分钟前台、跨 2 天（`LEARN_APP_MIN`
  / `LEARN_APP_DAY`，配置页「按应用学习 → 自己定门槛」）。全局那份是整机共享一份，
  这一层是各攒各的，攒得慢是设计的一部分。没设档位的包只在学出 up/down 时
  才出现在列表里，"样本还不够"的条目不会把真正要改的那几条埋掉。
- **手填的永远压过学出来的。** 学习写回 `app_modes.conf` 的行末尾带 `#learn` 标记；
  你自己填的那条没有标记，学习一个字都不改它。建议照样给（页面上标着「手填」），
  要不要改由你点。点那条「学出来」的标记就是把这条收回自己管。
- **带 GPU 段的档位不参与自动建议。** `70:40` 这种是你精细调过的；学习只懂 CPU，
  重写会吞掉 GPU 段，所以这类条目连建议都不出。
- **只写数字，不写满血。** 满血是整个交还系统，学错了等于完全不限频，这个动作只留给人来点。
- 判据和全局那套同形：p99 贴帽且（顶帽 ≥ 10% 或贴帽两桶 ≥ 25%）→ 放宽一档，
  固定要 3 天 + `LEARN_APP_MIN`；p99 离帽 15 个点以上且顶帽 ≤ 10% →
  收紧一档（`LEARN_APP_DAY` / `LEARN_APP_MIN`；性能模式不收紧）。
  被厂商热限频压在下面的那段一律不给建议（量的是它的帽）。
  数字是四簇合并成一个分布算的——应用档位本来就是四簇统一一个百分比，GPU 不参与；
  应用这一层不做大核特判，四簇一视同仁。
- 「清零重学」会把两层样本一起清，并顺手撤掉学习写回的那批档位（手填的一条不动）。

## 实时偏移（PSI / 温控 / 充电态）

智能学习管的是**长期该定多少**，这一节管的是**这一刻该不该让路**。三条各自独立记账，
合成一个偏移加在生效值上：

```
CPU 生效封顶 = 设定值（插电时先抬到 CHG_PCT）+ PSI 借出 − 温控压回 − 电量阶梯
GPU 生效封顶 = 设定值（全局 GPU_PCT 或应用 GPU 档）+ PSI 借出 − 温控压回 − 电量阶梯
```

合计偏移还有一对总闸（`ADAPT_UP_MAX` / `ADAPT_DOWN_MAX`，默认 +15 / −30），
防止每个来源都不越界、叠起来却把 65% 压成 5%。

**只改生效值，从不写配置文件。** 滑杆上显示的就是你设的那个数，背后没有第二个东西在偷偷改它。

**功能页不摆术语。** 三张卡各自只有一个下拉框：「插着电的时候」「机身发热的时候」「真的卡的时候」，
选项写的是行为（不封顶 / 早点降 / 少借一点），不是参数名。具体数值收在每张卡的
「自己定」里，**范围一个都没缩** —— 手动改过之后下拉框会自己变成「自己定的值」，
不会继续谎称你还在某一档。页面顶上还有一句按当前值现算的话：
「插电　插着电时不封顶，拔电自动恢复 / 发热　到 75℃ 开始一档档降，最多比设定低 25%…」。
首页那一行同样先给人看的那句（`现在比设定值低 10%　机器发热，正在降速保护`），
`stall / ms/s / 几档` 这些原始读数放在后面一小段淡色文字里，截图反馈问题时用的就是它。

### 充电态（默认开）

`/sys/class/power_supply/battery/status` 是 Charging/Full 时，把常态封顶至少抬到 `CHG_PCT`（默认 100），
拔电自动回落 —— 插着电发热由充电器承担，压它没有意义。三条边界：

- **温控优先**：热的时候插着电照样降（地板先抬，压档叠在上面）。
- **分应用档位不吃这块地板**：那是你对某个应用的明确选择，插电不该替你改掉。
- **GPU 也不吃这块地板**：`GPU_PCT` 和应用 GPU 档都是明确上限，插电不抬高。

**充电速度不归这个模块管。** 模块不写任何 `power_supply` / 充电器 / 充电电流节点，
只写 CPU/GPU 的频率上限；熄屏充电时不再维持模块的帽（`state=full`，交还系统），
厂商在充电时压低 CPU 上限时模块也跟随（日志写"厂商已压更低"）。
真正影响充电速度的是：电池温度（烫了厂商会主动降功率）、当前电量（80% 以后必然慢）、
充电器/线材、电池老化，以及**边充边玩**——游戏/相机的满血模式会让机身更热，厂商随之降充电功率。

怀疑是模块时做一次 A/B：关于页 →「暂停」（会恢复频率并停掉守护），
用同一个充电器、同样的电量区间、屏幕熄灭各充 10 分钟，比较
`/sys/class/power_supply/battery/current_now` 和电池温度；再「恢复」重复一次。
两组数一样就与模块无关。深睡也不会在充电时压 Doze：除了 `online` 节点，
还会看 `battery/status`（有些 ROM 只有后者）。

### 温控闭环（默认开）

扫 `/sys/class/thermal/thermal_zone*/`，只取 `type` 里带 cpu / gpu / soc 的，拿**最热**那个读数。
超 `TH_HIGH` 每个巡检周期压一档（`TH_STEP`），最多压到 `TH_MAX`；回到 `TH_LOW` 以下每隔 `TH_BACK` 秒还一档；
两者之间是迟滞带，**保持不动**——不然温度在阈值附近晃，封顶就跟着抖。

- 内核的 `temp` 是**毫摄氏度**（43600 = 43.6℃），阈值填℃，代码里换算。这条有断言钉着：
  第一版按 0.1℃ 比较，结果静置 43℃ 就被判成超阈值、白压一档。
- 同一棵目录树下还躺着 `vbat`（4091 其实是 4.091V）、`ibat`、`bcl` 这些**不是温度**的 zone，
  按数值筛会把电压当温度、把恒 0 的当"很凉快"，所以只按 `type` 认。
- 有些内核把 **trip point（阈值）** 也放进 thermal_zone，`type` 叫 `cpu-hw-trip-0/1`，
  `temp` 恒等于阈值（实测 95000 = 95℃）。它不是温度计；混进最大值会让整机永远被判成 95℃，
  温控压满、智能学习因为 `dlt != 0` 永远不采样。现在 `type` 里带 `trip` 的一律不收，
  测试里用假 zone（正常 42℃ + trip 95℃）钉住了"最热仍是 42℃、th_steps=0"。
- **zone 路径启动时扫一次并缓存**：PJZ110 上 87 个 thermal_zone 里只有 29 个命中
  cpu/gpu/soc，缓存后每轮只读这 29 个 `temp`，不再每 5 秒 opendir 整棵目录；
  某个缓存路径读失败（驱动重建/热插拔）会自动重扫一次。
- 温控偏移同时作用于 CPU 和 GPU。最热的传感器常常就是 GPU，只压 CPU 等于闭环只做了一半。
- 默认 `TH_HIGH=75` 是通用值。8 Elite 这类 SoC 到 75℃ 时内核往往已经开始砍频，主动闭环就晚了；
  觉得"热了没效果"时先把 `TH_HIGH` 试到 68~70（`TH_LOW` 要跟着留至少 5℃ 的迟滞带）。
  不同机型散热差异太大，这一项需要按真机温度曲线调，所以默认值没有替所有人拍板。
- 这是主动闭环，比等内核热管控直接砍频平滑。厂商那边同时在压时日志会写"厂商已压更低"，两边不互相盖。

### 电量阶梯（默认关）

出厂不压：低电量时先只管「封到设定值」，不再额外收紧，免得用户觉得"没电就更卡"。
在功能页「电量低的时候」打开后：不充电且容量低于 `BATT_LOW`（默认 20%）时，
再收紧 `BATT_LOW_CUT`（默认 5 个点）；低于 `BATT_CRIT`（默认 10%）
再叠 `BATT_CRIT_CUT`（默认 10 个点）。
它和 PSI/温控共用 `ADAPT_DOWN_MAX` 总闸，不会把 65% 压到 5%：

- **插电时不生效**：低电量正在充电时不该再压，充电态本来就在放宽。
- **分应用档位不吃这一刀**：CPU/GPU 的应用专属档是用户明确设的值，和"专属档不吃充电地板"同一个口径。
- 读不到容量（`capacity` 缺失/越界）就不收紧，不猜。
- 功能页「电量低的时候」有总开关和四档数值；关着（默认）时电量再低也不额外收紧。

### PSI 护栏（默认开，只借不拿）

读 `/proc/pressure/cpu` 的 `total`（累计 stall 微秒），按墙钟差分算出**速率**（ms/s），
和这台机自己最近 10 分钟的基线比：**超出 2 倍、且绝对值再高 30 ms/s** 才算"卡"，
一档一档往外借（`PSI_STEP`），总量不超过 `PSI_GAIN`；不卡了先等 `PSI_HOLD` 秒，
之后每隔 `PSI_BACK` 秒收回一档。**它只能往上放宽，永远不低于你设的值**——收紧是智能学习的活。
基线只在**常态、且没有偏移生效**时更新：游戏/满血/熄屏那段帽是解开的、负载又高，让它进基线
会把门槛抬高，回到日常后护栏就变钝了。

为什么不用 `avg10` 的绝对值判（"`<1%` 收紧、`>5%` 放宽"那种写法）：一加 13 上量过一轮，

| 状态（各 25 秒） | `some avg10` | stall 速率 | 最热 cpu/gpu |
|---|---|---|---|
| 静置·封顶 62/64/66/68 | 3.6–5.7 | 61.6 ms/s | 42–46 ℃ |
| 8 路满载·有帽 | 4.7→8.5 | 129.0 ms/s | 67→74.5 ℃ |
| 8 路满载·**没帽 100%** | 6.6→9.35 | 128.6 ms/s | 72→76.4 ℃ |
| 恢复封顶 | 6.7→4.8 | 68.6 ms/s | 47–50 ℃ |

满载时**有没有帽，stall 速率一模一样**（129 vs 129 ms/s）——`some` 只看"有没有任务在等 CPU"，
八颗核都被 `yes` 塞满时它不看频率。而静置就有 4~5 个 `avg10`。
所以按绝对阈值写，开机几秒就会被判成"卡了"，一路放宽到 100% 停在那儿，**模块把自己关掉**。
判据因此改成"相对这台机自己的基线"，并且借出量有硬上限。

### GPU 的封顶为什么可能比滑杆百分比低

GPU 的目标是「滑杆百分比 + 实时偏移（温控 / PSI）」，再向下吸附到真实频点。
偏移到 -25 档时，50% 先变成 25%；如果目标低于 GPU 的最低频点，会落到最低档
（例如 282 MHz），和 CPU 的封顶语义一致。配置页现在会在 SoC 标题下写出当前
偏移量；不想要这层让路，就在「功能」页把温控 / PSI 护栏关掉。
**适配页「封顶后」一列只算设定值的吸附**（100% 就是 1200MHz），不叠加实时偏移；
实际生效值（偏移、厂商上限都算进去）在「GPU 封顶」卡片和状态里看，两处不混。

### 与智能学习的相互影响

**偏移生效期间不攒学习样本**（`dlt != 0` 或插电抬着地板的那一轮）。
那时核心身上的是别的封顶，采进来的分布回答不了"设定值这道帽紧不紧"，混进去会把建议带偏。
代价说清楚：默认 `CHG_UNCAP=1` 时，插着电的整段时间**完全不攒样本**——不是变慢，是停住；
关掉充电放宽之后才会继续攒。这是有意的，宁可慢也不要偏。

## 深度睡眠（V1.6）

熄屏、没在充电、满 20 秒后开始冻结第三方后台进程；满 7 分 30 秒再让系统进入 Doze 深度空闲
（`force-idle deep`）。亮屏或插上电立刻解冻、撤临时白名单、退出强制空闲。它关的是"系统空闲时
还在后台折腾"，和上面那条「熄屏交还系统」不冲突：一个管 CPU 上限，一个管系统睡眠。

**默认是关的。** 打开入口在「睡眠」页顶部的总开关；关闭时脚本不会冻结任何应用。
打开后由 `service.sh` 拉起独立守护，暂停模块会先让它退出并还原。

页面上的三块：

- **总开关 / 状态**：未启用、监测中（熄屏 20 秒后开始压制后台）、深度睡眠中、守护没在跑。
- **永久豁免**：名单里的应用不会被冻结，深睡时也能被正常唤醒（等同系统电量设置里的「无限制」）。
  深睡期间正在播放音乐的应用会自动临时解冻，退出深睡后重新冻上；新加进豁免名单的应用
  在当次深睡里也会立即生效。
  **系统默认短信应用即使不在名单里，进入时也会临时加白、退出时撤销**：否则 Doze 会把
  短信广播压到出 Doze 才发，表现就是"解锁后一下收到半小时前的短信"。默认应用优先用
  `cmd role get-role-holders android.app.role.SMS` 取，取不到再退回旧 setting 和常见包名。
  **通讯 / 音乐 / 运动健康 / 系统关键应用默认加入**：微信、QQ/TIM、企业微信、钉钉；
  网易云、QQ音乐、汽水、酷狗、酷我、咪咕、喜马拉雅和各厂商自带音乐；
  小米/华为/荣耀/OPPO/vivo/三星健康、Zepp、Garmin、Fitbit；
  以及时钟、电话/通话、信息、联系人、日历（含荣耀/华为/OPPO/ColorOS/小米/vivo 的厂商包）。
  飞书 / Lark / WhatsApp / Telegram / Signal / LINE 不在内置清单里。
  装机时只给**本机已安装**的包写 `white=包名`（清单在 `scripts/builtin_white.txt`），
  不覆盖你的名单；删掉的行升级不会塞回来，上游移除的项会从白名单撤下
  （基准 `builtin_white.base.txt`）。
- **闹钟守卫**：时钟类应用有 30 分钟内要响的闹钟时，**不进入深睡**；7:30 收口那一刻也会
  再查一次，在闹钟窗口里就先不收口，5 分钟后重试。每天设闹钟也不会整晚不深睡——只让路
  闹钟前半小时。**第三方闹钟应用请加进永久豁免**：冻结会连它的响铃一起停住。
- 系统应用没有全量加白：Doze 的豁免是按包生效，把 400 多个系统包全塞进去等于把深睡
  关掉。内置的是会影响你感知的那批（时钟/电话/信息/联系人/日历/健康）。
- **唤醒榜**：本次深睡榜 + 累计榜（拔电或重启后清零）。页面 2 秒刷新一次；
  两个榜本身是**每分钟**从 `dumpsys alarm` 读一次增量（计数器是累计量，读得慢不丢数），
  所以刚醒来的那一两分钟看到的还是上一次的数。

冻结是这套方案的主力，Doze 只是最后的收口：

- 熄屏满 20 秒开始分批冻结第三方后台：每轮最多 8 个，3 分钟内完成；队列空了每分钟
  补扫一次，接住这几分钟里刚退到后台的进程。只认 `pm list packages -3` 且
  `oom_score_adj >= 200` 的进程；前台、可见应用、输入法、桌面、无障碍、VPN、当前前台、
  `full` / `keep` 档位、正在放媒体的应用、本模块和管理器、Scene 都不冻。
  厂商自带应用（`com.coloros.` / `com.oplus.` / `com.hihonor.` / `com.google.` 等前缀）
  整片不冻：ColorOS 的时钟/健康/天气在 `-3` 清单里，冻了就是闹钟不响。
- 后端按 `/dev/freezer`（cgroup v1）→ `cgroup.freeze`（v2）→ `SIGSTOP` 依次降级。
  冻结账本 `run/freeze.saved` 每批落盘；亮屏、关开关、守护启动、卸载都按账本解冻。
  解冻用 `cgroup.procs` 把整个进程搬回根组再删自己的组——`tasks` 只搬主线程，
  别的线程会留在冻结点上。
- **不再改 `device_idle_constants`**：进入不再靠调低全局门槛，而是冻结 + 延迟收口。
  升级前旧版留下的快照仍会按原值把常量还原/删除。
- 7:30 的 Doze 是**一次性**：`cmd deviceidle force-idle deep` 优先，失败补发
  `dumpsys` 兼容命令，仍失败就不重试。系统把你弹出（来电、闹钟等）之后不再每 15 分钟
  压回去。

开关背后的实现约束：

- **熄屏巡检不拿 system_server 当轮询接口**：亮屏判定先读背光/blank 节点（一次 `cat`），
  节点说灭时最多每 60 秒让 `dumpsys power` 复核一次；媒体保护 30 秒、唤醒数 60 秒才读一次。
  以前每 2 秒跑 `dumpsys power`＋`dumpsys display`＋`media_session`＋`alarm`，守护自己
  就是熄屏后的常驻唤醒源；`display` 那份 dump 一旦卡住，整轮巡检就不返回，亮屏了也没人
  解冻（应用一直停在冻结组里）。
- 每个 `dumpsys` 都套 `timeout`，卡住最多丢一轮，不会挂死守护。
- **游戏在前台时不进深睡**：主守护状态里 `game_pkg` 和 `fg` 是同一个包时（典型是熄屏挂机），
  只记一行日志、不冻结也不收口。Doze 会把游戏挂住，系统也会把这段功耗记进空闲/待机。
- 个别 ROM 的亮度节点在亮屏时也报 0：连续 3 次和 `dumpsys power` 对不上就停用节点，
  改成直接问系统（日志里会写一行）。
- 进入时写 `ds_snap.conf`（本次临时加的白名单）；正常退出删除它。启动时发现它还在 =
  上次被杀，按存档还原。
- 白名单只撤销"本次临时加的"；用户名单里的应用永久保留。
- 唤醒统计来自 `dumpsys alarm` 的 Top Alarms 段，按增量入账；负增量（计数器重置）丢弃。

**待机耗电怎么排查**（先分清是不是模块自己）：

- **冻结范围是第三方后台**：被冻的应用在解锁前收不到推送、也跑不了后台任务，
  要随时收消息的（微信、飞书、Telegram 等）、息屏还要用的（导航、第三方闹钟）
  请加进永久豁免。豁免越多，能冻的越少，待机也会更费电——先只留通讯 / 闹钟 / 短信，
  过一晚再按需加。
- **深睡守护每 2 秒仍会醒一次**（为了亮屏后立刻解冻）。如果关掉深睡后待机
  明显下降，这段巡检就是主因——先关深睡做一晚 A/B，再决定要不要继续用。
- **「功能 · 熄屏交还系统」开着时**，熄屏会解除 CPU/GPU 封顶，system 可以满频跑后台
  任务。想压待机可以关掉它（熄屏也封顶），代价是熄屏后台任务变慢。
- 导出的适配包现在带「深度睡眠现场」：`dsleep.conf`、`ds_state`、最近 40 行深睡日志、
  `deviceidle` 的白名单行数和关键状态。待机异常时直接导一份发作者。

需要 root（KernelSU / Magisk / APatch）。冻结优先用系统的 cgroup freezer
（ColorOS 上是 `/dev/freezer`），没有就退到 `cgroup.freeze`，再没有就用 `SIGSTOP`；
7:30 的收口依赖 Android 12+ 的 DeviceIdleController shell 接口。极个别深度定制 ROM
两者都裁掉时，开关能开、状态也会动，但既冻不住也进不了强制空闲——日志里会出现
「已进入」，功耗却不变，遇到这种情况请回报机型。

## 芯片适配包（自动探测扑空的机器）

有些机器的节点名和目录结构跟常规不一样：一个 `policy*` 目录都读不到，
或者找不到可写的 GPU 上限节点。这种机器装上就表现为
「看不到核心表」「GPU 那一档是灰的」——不是配置错了，是这台机的 sysfs 长得不在预期的那几条路径上。
只能人工适配，而适配得先知道他手上那台机到底有什么。**用户侧只有一个动作：导出**。
改好的节点表由作者写进下一个模块版本，他到时候更新模块就生效，不用自己动任何文件。

**导出**（关于页「导出适配包」，或 `sh webroot/api.sh pkg`）把现场打成一个 txt，落在

```
/storage/emulated/0/Download/Soc智能限频/socpkg-<品牌>-<型号>-<芯片>-<时间>.txt
```

选公共 Download 是因为 QQ / 微信 的发送框能直接翻到它，不用装 root 文件管理器。
写不进去回执是 `E/PKG_DIR`（目录建不出来）或 `E/PKG_WRITE`（文件是空的）。

包里有机种属性、这台机上**当前能用的节点表**（就是下面那几行 `#ovr`）、
守护自己的 `probe` 和 `export` 原样、逐个 policy 的频率表与调速器、GPU 节点普查
（把 KGSL / devfreq / mali 几条常见形态挨个点一遍，在的连值一起列出来）、
守护要用的那几个接口（`dumpsys` / `ps` / `packages.list`）读不读得到、
当前配置全文、当前建议结论、最近 40 行日志，最后一段是**这份包缺什么**的自动结论
（policy 目录数、几个 policy 没有驻留表、有没有可写的 GPU 上限节点）——作者先看这段就知道要补什么。

`#ovr` 只有四种键，和数据目录里那份 `override.conf` 的行一一对应：

```
#ovr cpu-dir <policy 目录> <这一档的硬件最高频>
#ovr gpu-max <可写的上限节点>
#ovr gpu-min <对应的下限节点>
#ovr gpu-freqs <空格分隔的频点表>
```

守护侧的生效顺序是**兜底，不是覆盖**：自动探测拿到东西时一个字都不看这份文件；
`detect_policies_raw()` 一条都没返回才按 `cpu-dir` 逐条造行（目录此刻已不存在的直接跳过），
GPU 的频率表和上限节点也是各自探不到才回落到 `gpu-freqs` / `gpu-max`。
覆盖只在守护启动时读一次，所以适配表要重启后才生效。

**这张表怎么发到用户机上**：作者把改好的表存成包里的 `adapt/<机型>.conf`，装机脚本按 `#match` 认机器，
命中才写进数据目录当 `override.conf`，并在第一行留下 `#from adapt/<文件名>` 标记。用户只要更新模块。

```
adapt/PJZ110.conf:
  #match brand=OnePlus        # 三种键都要命中才算命中
  #match model=PJZ110
  #match soc=SM8750           # 比对 ro.soc.model，取不到时退回 ro.board.platform，按包含匹配
  cpu-dir /sys/devices/system/cpu/cpufreq/policy0 3532800
  gpu-max /sys/class/devfreq/1a00000.qcom,kgsl-3d0/max_freq
```

三条规矩都有台架盯着（`src/test_install_merge.sh` 场景 8）：

- **没有 `#match` 的文件一律不装** —— 没条件就等于对所有机器适用，太危险。
- **只带进那四种键开头的行**：作者把 `cpu-dir` 打成 `CPU-DIR` 时不会被静默装上。
- **撤表只撤带 `#from adapt/` 标记的那份**：某台机器的适配下架后，用户升级就回到自动探测；
  而用户（或作者远程指导时）用命令行自己导进去的表没有这个标记，装机不会替他删。

包里的 `adapt/_TEMPLATE.conf` 是格式说明，`#match model=__NO_SUCH_MODEL__` 命中不了任何机器，
节点行也全是注释状态 —— 它存在的意义就是让那个目录随包发布。

从收到的包里取现成的一行不用手抄：

```sh
grep '^#ovr ' 收到的包.txt | sed 's/^#ovr //'   # 直接就是 adapt 文件正文那四种键
```

导出端的 GPU 候选现在按**名字白名单**（mali/kgsl/gpufreq/gpu/3d0）挑，并排掉
ufshci / dvfsrc / busmon / bwmon / memlat。以前通配 `/sys/class/devfreq/*/max_freq`
会把 UFS 控制器（如荣耀 MT6993 的 `16810000.ufshci`）写成 `gpu-max`，导入后限的是闪存，
页面还显示"GPU 已接上"。没有 GPU devfreq 的 MTK 新平台现在由守护直接走 gpufreqv2：
读 `stack_working_opp_table` 当频点表、写 `limit_table` 的 ceiling；包里的「GPU 节点普查」
仍会带上 `limit_table`、`stack_working_opp_table`、GED 参数等现场，方便核对不同内核。
不要拿 ufshci 的频点当 GPU 频点表。

**为什么页面上没有"导入适配包"这个按钮**：那份表是给某一台机子手搓的，
让用户自己点一下就能装进机器，等于给他一个把手机钉死在别人节点表上的入口——
导错一次，他的机器此后就一直按着那台机子的拓扑跑，而他自己看不出所以然。
所以导入和撤回只留在命令行（作者在自己机器上验一份刚改好的表要用）：

```sh
sh webroot/api.sh pkg_import [文件]   # 不传路径取 Download 那个目录里最新的一份
sh webroot/api.sh ovr_clear           # 删掉 override.conf 并重启，回到全自动探测
```

导入端先验首行是 `#SOCPKG 1`，再把 `#ovr` 行逐条校验：键不认、路径不是绝对路径、
频率不是纯数字，整份拒绝（`E/PKG_OVR`），不会留下半截没人知道缺了什么的覆盖；
包里一条 `#ovr` 都没有是 `E/PKG_NOOVR`（那份包什么也没适配）。
回执会打印**用的是哪个文件**、芯片名，再逐条对照"这个节点在这台机上到底存不存在"——
「导入成功」但路径全是别人机器上的，等于什么都没适配，这一段就是为了让这种情况当场露出来。

关于页那张卡片是**只读**的：它显示这台机当前的探测结果，
以及在用哪一份适配表（没在用时明说"全靠自动探测"），用户看得到自己的机被适配成了什么样，但改不了。

探测正常的机器整节都用不到，放着不用就行。

发之前自己看一眼：包里有配置全文和最近 40 行日志，日志里可能出现你加进名单的应用包名。

**改完一份表，先在真机上验一遍兜底路径**：`tools/sandbox_probe.sh`（要 root）
在 `/data/local/tmp/fakeroot` 造一台"假机器"——有 `cpu0/cpufreq`、`cpu4/cpufreq` 两个逐核目录，
但没有 `/sys/devices/system/cpu/cpufreq/policy*`，所以自动探测必然扑空，正是适配包要救的那种机器。
它把沙箱里的守护真跑 8 秒，验四件事：没表时探测不到、有表时两个簇和 GPU 都按表列出来
（名字取的是能分清簇的那一段，不是一排重名的 `cpufreq`）、封顶真写进了节点（50% 的 3532800 落成 1766400）、
退出时按 journal 恢复。全程只在沙箱里读写，碰不到真 sysfs，跑完自己清掉：

```sh
adb push tools/sandbox_probe.sh /data/local/tmp/
adb shell su -c 'sh /data/local/tmp/sandbox_probe.sh'   # 末行报 N/N 通过
```

## WebUI

KernelSU 管理器里点开模块就能用。不用浏览器、不联网、不加载任何外部资源。

六个页面：**首页**看状态、各簇实际频率和智能建议、**配置**调所有参数、**功能**放会跟着现场改行为的功能开关
（充电态 / 温控闭环 / PSI 护栏，见「实时偏移」）、**应用**增删名单、
**睡眠**配深度睡眠与唤醒榜、**关于**看信息、芯片适配包、重启守护。

### 浅色 / 深色主题

页面右上角是太阳 / 月亮开关：浅色和深色各一套新拟物配色，卡片仍然和背景同色，
只换阴影的亮档 / 暗档和文字颜色。第一次打开时跟随系统的深浅色偏好，手动点过之后
存在本地（`localStorage`），下次优先用你选的；管理器的 WebView 禁用存储时，
读不到就退回系统偏好，再退回浅色。

切换主题不会改任何配置。赞赏码卡片始终保持白底（二维码需要），说明字用固定深灰；
滑杆已走过的部分会染成主色，凹槽里能直接看出当前值。底部标签栏是浮起的药丸形，
页面底部留白和 toast 都带 `env(safe-area-inset-bottom)`，不会被手势条压住。

### 点起来不卡

管理器的 root 调用是同步的：一次调用没回来，页面这一帧就画不出去。所以：

- 切标签页先换页、让出一帧，再读这一页的数据；
- **首屏先发 `status`**：状态徽标只等一次桥往返 —— 探模块根（含 APatch 的第二个根）
  和取状态合在同一条手机 shell 里，徽标不用先等一次单独的 ping。管理器在页面刚打开时的
  第一条 exec 偶尔会空回执，会按 300/900/2000ms 退避重试；首屏第一次状态失败先保持
  「连接中」、400ms 后自试，不会出现"先报无法连接、过 5 秒自己好"。
  徽标还会把**上次的状态淡着先画出来**（7 天内有效），新状态一到就恢复不透明；
  所以除首次打开外，不会再先看到黑的「连接中」等那一次 root 往返。
  内置应用名、日志、建议排在后面（名字晚到也不会再被 APK 的英文标签盖回去）。以前是
  名字先 `await`，徽标要等 ping → 应用名 → 状态三次往返，进页面就多两秒「连接中」；
- 应用图标攒 40ms 合成一次 `icons` 批量请求（每批 8 个；调用失败或回包缺行会重试，
  不会误记成"这个包没有图"），取过的图标在一次会话里不再重取；
- 应用名同样一次只发一批；后端临时文件按进程分开，同一页三块同时点名不会互相覆盖；
- 关于页信息、芯片适配状态各只问一次；
- `conf_get` 用一趟 awk 读完（旧写法逐键起 sed，四十多个键实测 0.72 秒）；
- **保存一次只发一个 `conf_set_many`**（值没变的键后端直接跳过）：以前三十多个键是
  三十多次同步 root 调用，手机上要十几秒，用户以为没点上就会反复按；保存期间按钮
  锁住并显示"保存中…"，重复点击不会排队再存一遍；
- **输入框有焦点、或最近 0.8 秒有触摸/拖动时，1 秒一次的 cores 和 5 秒一次的 status 暂停**，
  打字和拖滑杆不会被同步 root 调用卡住；滑杆松手后主动失焦，曲线马上恢复；
- 两个搜索框 150ms 防抖再重画（不再每敲一个键重建最多 400 行）；
- 拖滑杆时 `paintHw` 合并到 80ms 一次，不按每个像素重排；
- 深睡总开关先按你点的方向画开关和状态条，再等守护起停的回执，
  旧轮询回来的过期状态不会把开关弹回去。

**管理器没给 root 接口时**，页面顶部会常驻一条
「当前管理器不支持 WebUI，请用 action.sh 命令行操作」，同时把标签页藏掉、
停掉每 5 秒一次的轮询 —— 这种情况底下所有卡片都是死的，
一闪而过的提示会让人以为"加载失败了，刷新试试"，然后一直刷新。

这条提示和另一种失败必须分开：**桥接是通的、但两个模块根下都找不到 api.sh**
时说的是"模块装在哪"（提示里会把试过的两个根都列出来），
处置方式是回报路径，不是换管理器。合成一句话会把人往完全反的方向支。

「游戏」页**只列这台手机上装了、并且在名单里的应用**。
预设名单有四百多条，绝大多数人的手机上只装了其中几个，
把没装的也列出来既没意义，四百行空图标也把页面撑得没法看。
`games_list all` 仍然可以拿到全量名单，命令行下有用。

### 恢复全部默认

关于页「维护」→「恢复全部默认」，连点两次确认。会重置：性能百分比、GPU、熄屏策略、
实时偏移、深睡开关与豁免名单、分应用档位、适配覆盖、学习样本；<b>保留</b>游戏名单、
发行商词典、主题。装机时会把出厂配置留一份在 `/data/adb/soc_freqcap/defaults/`，
恢复用的是这份原件，不依赖模块目录里可能已被移走的 `socfreq.conf`。

### 名单覆盖不到的新游戏：发行商词典

`/data/adb/soc_freqcap/vendors.txt`。「游戏」页顶部多出一栏
**「可能是游戏、还没进名单」**：扫一遍这台机上的第三方包，
包名里带词典中的发行商段、又不在名单里的就列出来，旁边标着命中的是哪个词，
点 ＋ 才加进 `games.txt`。

**词典不参与前台匹配** —— 守护读的只有 `games.txt` 的整串包名。
这条边界是刻意的：让包名含 `tencent` 就算游戏，微信一封前台就把限频解除掉了，
模块的核心承诺就废了。所以词典里：

- 只收**游戏专用的段**（`com.tencent.tmgp` 前缀、`mihoyo`、`hypergryph`、
  `kurogames`、`aligames` 这类），通用公司名（`tencent`/`netease`/`bilibili`）
  一个都不当命中项；
- 判据是**整段相等**（带点的词才按前缀），所以 `com.some.gameshop`
  不会被 `game` 命中；
- 命中之后还要过一遍**排除表**（`cloudmusic`/`bbs`/`community`/`gamecenter`
  /`launcher`/`emulator` 等同公司的非游戏）；
- 一次最多列 80 条，避免首屏被噪音占满。

自己加词：一行一条，`+词` 命中、`-词` 排除，改完立刻生效（每次点「重新扫描」重读）。
漏了某个游戏不是问题——直接在输入框写包名加就行；误收才是要避免的，
所以宁缺毋滥。

每一行左边是应用图标，右边两句话：**第一行应用名，第二行包名**。
只给包名的话，`com.tencent.tmgp.osgame` 这一串摆在十几行列表里没人看得出是哪个应用，
而名单是靠"眼熟"来管的。名字取不到（老包、解析不了）时
第一行仍然显示包名、第二行整条不出现，表现就是退回以前的一行样式，
不会留空行、也不会两行写同一个东西。

图标和名字都是从设备上已安装的 APK 里直接读出来的；
没装这个应用、或者 APK 里解不出位图时就显示首字母色块。
图标只在滚动进可视区域时才去取，列表再长也不会一次性把管理器卡住；
名字反过来，是**一次调用点一批**（`api.sh labels`），
因为读一个名字要把那个包的 manifest 和 `resources.arsc` 都解一遍，
一行一次请求在几百个应用的选择器里会当场把页面拖死。

名字为什么没有便宜的外壳来源：这台机上实测 `pm list packages` 没有
`--show-app-label`，`dumpsys package` 里也不带标签 ——
标签只存在于 APK 里（`AndroidManifest.xml` 的 `android:label`，
而且通常是 `@string/app_name` 这样的引用，文本还要再去 `resources.arsc`
的字符串池里查一次）。所以这份解析在守护里做（`src/appinfo.c`）。
同一套解析顺带把**声明的那张桌面图标**也定了：
`android:icon` 指向的条目在 arsc 里就是文件路径，取到了就直接按那条取图，
不再靠猜 —— 只有它给的是 `.xml`（自适应图标）或者整条读不出来时，
才退回下面那两轮打分。

解包由守护自己读 zip 的中央目录完成（`src/icon.c`），静态链了 zlib。
主路不依赖任何外部命令，所以不挑 ROM。守护失败时另有一条兜底：
系统里恰好有 `unzip` 就用它取条目字节（`unzip -p`），挑图仍然由守护打分。

早先这里写的是"Android 的 toybox 里没有 unzip，所以必须自己解析"。
**这条前提是错的**：部分 ROM 自带 unzip。
它现在只是"不能当唯一路径"的理由——unzip 的列格式各家不一样、
版本有差异，整条链路挂在它一条命上不稳。

两条路的能力**不互相包含**，是互补的：

| | 主路（守护解析） | 兜底（unzip 取字节） |
|---|---|---|
| 按名字挑（`mipmap-xxhdpi/ic_launcher.png`） | 有 | 有 |
| 按图片尺寸猜（资源名被 AGP 缩短过的包） | 有 | **没有** |
| 中央目录 >4MB / 条目 >65535（ZIP64）/ 包 >512MB | 4GB 以内有 | 有（不受这个上限约束） |

所以：缩短过的包只有主路能出图（实测一个 111MB 的缩短包，喂给兜底的
候选数是 0 条）；超大/ZIP64 包兜底更稳。谁都不许把另一条当冗余删掉。

关于页那一行会显示这张图是谁给的：`守护解析 APK` / `unzip 兜底`。
后者出现得越多，说明主路越需要修——那是留给自己看的线索，不是装饰。

### 图标可能不是桌面图标（这是设计上的已知边界）

准确的取法有，而且已经做了：`src/appinfo.c` 解 `AndroidManifest.xml`（AXML）
找到桌面入口那个 activity 的 `android:icon`，再去 `resources.arsc`
的条目表里把它翻成**文件路径**——这条路径就是桌面真正在用的那张图。
拿到之后按这条路径直接取字节，不经过下面那两轮猜。

但**声明的常常是一张 `.xml`**（Android 8 之后几乎全是自适应图标，
`mipmap-anydpi-v26/ic_launcher.xml`），而 WebView 解不了矢量图。
这一步会再钻进那张 xml 取 `foreground` 引用的资源，
仍然只认它是位图的情况；层里还是矢量、或者整条链读不通时，
才退回去找**同名的位图版本**（`ic_launcher.png` 在某个 `mipmap-<密度>/` 里）。

再往下就真的只能猜了。正式发布包多数过了 AGP 的资源路径缩短，
`res/mipmap-xxhdpi/ic_launcher.png` 会变成 `res/aK.png` 这种名字，
mipmap / drawable / launcher 三个关键词一个都搜不到，按名字挑必然一张都挑不出来。
这时**不看名字、改看图片自身**：只认 `res/` 下的图，要求正方形、边长 48~512，
再按"最接近槽位"打分（PNG 读 IHDR 的宽高，WebP 读 VP8/VP8L/VP8X 头的宽高，都不解压）。

所以走到底的那一档给的是「`res/` 下一张尺寸像图标的方图」，**不保证是桌面图标**——
它同样可能是游戏内素材（`com.tencent.tmgp.osgame` 就是这么被取成一张 128 灰度方块的，
那条包的 manifest 声明是矢量层，位图版本根本同名不回来）。
选图时不看 `assets/`，是因为那里的东西多数是动画帧和纹理
（实测一个 33 MB 的游戏包里有 661 张），挑中就是错的图，那比留色块更糟。

取图失败时关于页那一行会写明卡在哪一档，长按色块也有同样的说明；
"取到了"和"取对了"是两件事，这两句话在界面上是分开的。

选图的几条细则：

- **密度按"离槽位多近"排，中间那档最高**。
  图标槽位是 CSS `38px`，3168×1440 的屏在 WebView 里 `dpr` 约 3~3.5，
  实际要填的是 **114~133 物理像素**。所以顺序是
  `xxhdpi(144) > xhdpi(96) > hdpi(72) > xxxhdpi(192) > mdpi(48)`。
  mdpi 的 48px 塞进 114px 要放大 2.4 倍，糊；xxxhdpi 的 192px 虽然画得清，
  但 base64 之后一张能有几十 KB，几百条清单会把 WebView 拖垮。
  xxhdpi 的 144px 不用放大也不用过度缩小，是唯一合适的一档。
  （CSS px 和位图 px 差一个 `dpr`，拿 `38` 去比 `48/144/192` 会得出
  "小图够用"的相反结论——这条判错过一次。）
- **单张不超过 24KB，超了就换下一张**。`score_name` 只看名字、拿不到体积，
  按密度挑会顺带选中 `res/` 里几十 KB 的游戏美术图。所以择优分两趟：
  先在预算内挑，一个都没有才放开预算——放开是为了"整包都超"时仍有图标，
  而不是一超就留空。
- **名字带 `round` 的不进第一轮**。`ic_launcher_round.png` 是很多包自带的
  圆形版本，体积通常比方形图标小，在"同分取小"这条规则下会稳定地赢过
  真图标，列表里出现一圈空白圆环。这里用**直接不收**而不是扣分：
  档位最小间距是 1，扣 2 就跨档（round 一档跟方形高一档同分，
  再靠"同分取小"赢回来，等于没惩罚），扣 1 也只是本档垫底。
  只剩 round 的包不会丢图——第二轮会按图片尺寸把它收下。
  匹配必须按**整词**：`background` 里含 `round`（back-g-roun-d），
  用子串匹配的话每个自适应图标都被这条否掉，
  下一条兜底等于永远不生效。
- **自适应图标退到 `background`**。现代包常常只剩
  `mipmap-anydpi-v26/ic_launcher.xml`（自适应图标，本模块不解析 XML）
  加两张光栅图。这种情况下 background 那张能当图标底色收下，
  至少不是空块。它的分数压在所有 mipmap 之下。

保存配置后守护会自动重算并生效，不用重启手机。

## 命令行

```sh
D=/data/adb/modules/soc_freqcap   # 模块目录（只放解包出来的东西）
V=/data/adb/soc_freqcap           # 可变状态（配置、名单、日志、journal）

$D/socfreqd status      # 当前状态
$D/socfreqd probe       # 会封到多少（只读，不改任何东西）
$D/socfreqd restart     # 重启守护
$D/socfreqd stop        # 停掉并恢复频率
$D/socfreqd uninstall   # 清理还原（卸载时自动执行）

tail -f $V/socfreqd.log # 看日志
```

`restart` 会**立刻返回**，守护由它 fork 出来的子进程（setsid 后脱离调用者的进程组）接着跑：
守护循环是前台常驻的，如果 restart 在调用者这个进程里 exec 成守护，这条命令就永远不返回，
WebUI 的「重启守护」、音量键第 6 项、适配包的导入回执全被吊在那儿，管理器那头只看到超时。
`start` 才是前台实现，所以看门狗那条用 `nohup "$DAEMON" start >/dev/null 2>&1 </dev/null &` 拉起。

临时想停：建个 `$V/pause` 文件，看门狗就不再拉起守护；删掉文件自动恢复。

看门狗以**心跳**为准：守护每轮（亮屏 5s / 熄屏 15s / 深睡 30s）写一次
`$V/run/heartbeat`，`service.sh` 每 60s 只 `stat` 它的 mtime；超过 90s 没更新就认为
卡死——如果旧进程还在，先 `kill -9` 再拉起，避免清掉锁文件后跑出两个实例。

### 模块里那个「执行」按钮（音量键操作）

管理器点「执行」跑的是 `action.sh`。这时候 stdin 不是终端，键盘输入进不来，
所以整个界面用**音量键**操作：

| 按键 | 作用 |
|---|---|
| 音量＋ | 切换选择项；在确认界面是「取消」 |
| 音量－ | 执行选中项；在确认界面是「确认」 |

菜单九项：查看运行状态、封顶预览（只读）、最近 30 行日志、
CPU 封顶 ±5%（四簇同步）、重启守护、暂停/恢复、停掉并还原、智能建议（只读）。
只读的那四项（1 / 2 / 3 / 9）按下去直接执行；会改东西的五项都要再确认一次，
**20 秒不按键按「取消」处理**。菜单 **90 秒**无按键才自动退出，什么都不会改。

等待窗口 30 秒 / 10 秒实测太紧：只让音量键重置计时，
所以先按电源键亮屏、或者误按了别的键，那一下被丢掉、时钟照走，
人慢慢看完八行菜单就"超时退出"——反馈回来就是"我明明按了，它说没检测到操作"。
现在**任何实体键都算活动**（`EV_KEY` 但不是音量键 → 重新计时继续等），
窗口也拉到 90 / 20 秒。触摸屏事件**不算**活动：口袋误触会持续出事件，
拿它续时这个界面就永远不退出，白占一个 root shell。

**完整菜单只打一次，之后每按一次只补一行 `→ 4 CPU 封顶 +5%`。**
管理器那块「执行」输出是只能往下追加的文本区，不是终端 —— 没有"刷新"这个动作。
每次按键重打一遍八项菜单的话，按八下就是八屏重复，
"现在选到哪一行"反而要往下翻着找。真终端（`adb shell` 里手跑，`[ -t 1 ]` 为真）
才走 ANSI 整屏重画。

`getevent` 的读数节奏是**窗口 0.1 秒 + 隔 0.05 秒再看**，
不是一秒一次的阻塞读。这么定的直接理由不是手感，是"这一版在管理器的执行界面里
十几秒就没声了，而参考那份同样的菜单没有这个毛病"——两个脚本之间只剩这一处实质差别。

代价写在这儿，别当没有：evdev 每次 `open` 是一个新客户端，**只在进程活着那段时间里收事件**，
两次调用之间按下的键整个丢掉。窗口 1 秒时空档约 1~2%，0.1 秒 + 0.05 秒时空档能到两三成，
表现就是**有时要按两下才动**。参考那份本来就是这个行为，
所以宁可慢半拍，也不要一个会中途没声的界面。

判"读不到输入设备"用的是**用时对不对得上读数次数**（一秒里读上百次 = 每次都立刻返回空），
不是退出码：读数一旦写成管道，`$?` 取到的是管道最后一个命令的状态，永远是 0，
"124 = 被 timeout 杀掉"这个区分根本不存在。

真机实测（一加 PJZ110）：音量＋ 来自 `/dev/input/event2`、音量－ 来自 `/dev/input/event0`，
**两个不同的节点** —— 所以读数必须不带设备参数、让 getevent 自己监听全部节点，
"先挑一个键盘节点再只读它"会做成"只有一边能用"。
另外这台机上 `sendevent` 注入的事件 getevent 收不到（ROM 侧独占），
`input keyevent` 走 InputManager 也不经 `/dev/input` —— **这条链路只能真人按键验**。

所有操作都转给 `webroot/api.sh`，不在命令行里自己写配置文件 ——
区间校验和键名白名单只有那一份实现，两处各写一份迟早会有一个是松的。

`getevent` 读不到音量键、机器上没有 `timeout`、或者 api.sh 不可读时，
不进按键循环，改为打印等价的命令行清单后退出。
这个分支必须有：少了它，"点执行"就变成等一个永远不来的按键，
看起来像模块把手机卡住了。

## 卸载

管理器里卸载会在模块目录下执行 `uninstall.sh`：先让守护自己还原，再按 journal
兜底还原一遍（数值、节点权限、调速器名三本账都读），最后把数据目录
`/data/adb/soc_freqcap` 整个删掉。两道都做完，sysfs 上不留东西，
手机上也不留 root 私有的孤儿目录。

即使守护被强杀、来不及自己还原，journal 里存着原始值，卸载时照样能还原回来。
从老版本直升的机器上账本可能还在模块目录里（`<模块>/run/`），
两处都会读——只兜一处等于留一半。

**名单怎么跟着版本升级。** 上面那句"升级不动数据目录"会带来一个副作用：
包里精选名单新增的游戏，升级时进不了用户机器——数据目录里那份是装机那天的旧版，
新条目一个都盖不进去。所以装机脚本做的是三方合并，基准就是 `games.base.txt`：

| 情况 | 结果 |
|---|---|
| 包里有、基准里没有 | 补进用户名单（这就是升级通道） |
| 基准里有、包里没有 | 从用户名单删掉（上游下架的条目） |
| 用户自己加的 | 基准和包里都没有它 → 两个差集都不含，不动 |
| 用户自己删的 | 包和基准都还有 → 不属于"新增"，不会被塞回去 |

从没有基准的老版本直升时只做"补新增"、不做删除：那种情况下分不清
"用户自己加的"和"上游删掉的"，宁可多留几条，也不能把人自己加进去的包删掉。

## 关于管理器里看到的输出

三个坑都在安装/执行脚本里，都表现成"看起来是管理器的问题"：

**「执行」按钮点下去一片空白。** `ui_print` 是管理器提供的函数，装机时有，
但点「执行」的运行环境里不一定有。脚本里每一行都调它 →
每一行都变成 `ui_print: command not found` 打到 stderr → 界面整页空白。
两个脚本开头都做了兜底（`command -v ui_print` 不通过就用 `echo` 顶上）。

**输出前面多一个 `v` 或 `x`。** 部分管理器会自己给 `ui_print` 的输出加一套
行首标记，脚本里再加一遍就成了 `v 未检测到冲突`。
所以脚本自己**不加**这类前缀。

**刷机日志最上方出现方框/竖线。** 标题夹在横杠中间（`━━ 标题 ━━`）时，
部分管理器会把横杠两端的文字当行首标记解析。现在标题独占一行，
所有分隔线宽度统一 20 字。

**关于页一直弹「about 输出里没有 ---PROP--- 标记」。** 这是 WebUI 与
`api.sh` 版本混装，或个别 ROM 的 `sh` 把 `printf -- '---PROP---'` 的 `--`
当成了格式串（只吐出两个减号）。V1.4 已把标记改成 `printf '%s\n'`，
前端在标记丢失时也会从 `module.prop` 的 `id=/version=` 行恢复；
更新时请刷完整 zip（或同时热推 `webroot/index.html` 与 `webroot/api.sh`），
不要只换其中一个。

`test_install_merge.sh` 是把 `customize.sh` 里那段**抠出来**在临时目录里跑的，
不是照抄一份逻辑到测试里：装机脚本只在刷机的时侯跑一次，
PC 上其余自检碰不到它，抄一份就会和原脚本各自漂移。

`tools/test_appinfo.js` 解决的是另一类问题：`src/appinfo.c` 那份 AXML /
`resources.arsc` 的读法，在这台 Windows 上**根本执行不了**
（NDK 只产 arm64 的安卓二进制，本机没有 host gcc、也没装 WSL），
所以"偏移抄对没有"没法靠跑一遍确认。做法是先有一份能跑的参照实现
（`tools/apklabel.js`，同一套算法的 JS 版），拿本机 SDK 的
`aapt2 dump badging` 当权威答案比：两边的 `application: label=` 和 `icon=`
必须一致，C 那份才是照着已经验过的偏移抄的。
本地没有可测的 APK 或没有 aapt2 时这组会整组跳过并明说"没验"，不会假绿。
代价也要写在这儿：**参照实现和 C 是两份**，改了格式判定要两边一起改——
所以两边的注释里都标了同一个出处（实测的包：gnirehtet / 酷安 / Kin / WakeUp）。

`test_contract.js` 要**七个**参数，顺序固定：

```sh
node src/test_contract.js src/socfreqd.c webroot/index.html \
     socfreq.conf webroot/api.sh README.md games.txt src/icon.c \
     [比对基准脚本]
```

少传这七个里的任何一个都会在开头就报"参数不对"并打印用法（`exit 2`），
不会跑到一半才崩在某个 `readFileSync(undefined)` 上。

末尾还有一个**可选**参数：另一个模块的 `api.sh`，用来做相似度对比。
它不随本包发布，所以没传就跳过那两条，其余检查照跑：

```sh
node src/test_contract.js ... src/icon.c src/ref_api_ktwo.sh
```

> 这一条当初是必填的，结果外部用户照着 README 跑，第一步就卡在
> "参数不对"——要一个他手上根本没有的文件。别人的模块怎么装、
> 叫什么名字，只有作者知道。这种参数不该挡在自检的门口。

最后一个参数是**任意一份同类限频模块的接口脚本**，只用来跑一条断言：
本模块的 `api.sh` 和它不能雷同到让人觉得是同一个东西。
判据是剔除 `fi`/`done`/`}` 这类 shell 语法糖之后，双方还剩几行逐字相同
（上限 3 行），以及最长公共连续片段（上限 20 字符）。

**这一份基准文件需要你自己准备，不会随包分发**——
把别人的代码再分发一次和抄它是一回事。随便找个同类限频模块的
`api.sh` 传进去即可（第八个参数），找不到就不传，
那两条相似度断言会打印 `skip` 后跳过，其余检查照常跑完。

各项的具体条数以脚本最后一行打印的 `全部通过 (N)` 为准——
这里不写死数字：每加一批断言它就会烂一次，写在文档里的数必然比代码旧。

> 这条当初是必填的。当时的想法是"少一个输入还假装全绿，比报错更糟"，
> 但它挡住的不是自己的自检，而是别人的：外部用户手上根本没有
> 别人的 `api.sh`，照着 README 敲第一步就 `exit 2`，后面一条都跑不到。
> 缺输入该跳过还是该报错，取决于那个输入是不是只有作者才有——
> 前七个是本仓库自己的文件，必须齐全；第八个不是。

接口约定：成功输出数据到 stdout，失败输出 `E/<原因码>` 到 stderr 并返回非零。
原因码（`BAD_PKG` / `RANGE` / `VERIFY` / `NO_CONF` / `WRITE` …）是给程序看的，
不混进 stdout，因为 WebUI 拿 stdout 当数据解析，错误信息混进去整段就废了。

### 名单必须是 LF 结尾

`games.txt` 存成 CRLF 的话，游戏一个都列不出来，页面显示「本机已装 0 个」，
也不报错。原因：`grep -x` 要求整行相等，而 CRLF 的行尾多一个 `\r`，
和来自 `pm` 的包名永远对不上。安装时会自动去掉一次 `\r`，
但**平时用 Windows 编辑器改名单记得存成 LF**（VS Code 右下角点一下编码换）。

顺带说明为什么这类问题能在测试全绿的情况下溜到手机上：
开发机上跑的是 MSYS，它读文件时会翻译行尾、把 `\r` 吃掉，
于是「CRLF 匹配不上」在 PC 上根本不会发生。同类的还有 `mktemp`——
它在 PC 上有 `/tmp` 可写，在设备的 root shell 里没有。

```sh
# 装完在手机上查一遍（PC 上的测试替不掉这一步）
adb push tools/smoke_ondevice.sh /data/local/tmp/
su -c 'sh /data/local/tmp/smoke_ondevice.sh'
```

**前面那个 `sh` 不能省。** `adb push` 推过去的文件是 0644，没有执行位；
直接 `su -c '/data/local/tmp/smoke_ondevice.sh'` 会被内核拒绝，报
`Permission denied`。而这行报错出现在自检脚本的第一条命令之前，
看起来像是脚本本身坏了——实际上一条检查都还没跑到。
交给 `sh` 解释执行不需要执行位。（想直接跑也行，
`adb push` 之后补一句 `adb shell chmod 755 /data/local/tmp/smoke_ondevice.sh`。）

目录名取自 `module.prop` 里的 `id`（**不是**模块显示名 `Soc智能限频`）：
APatch 装在 `/data/adb/ap/modules/soc_freqcap`，就作为参数传进去。

```sh
su -c 'sh /data/local/tmp/smoke_ondevice.sh /data/adb/ap/modules/soc_freqcap'
```

> 目录写错时脚本会立刻退出并打出上面的用法。早退是有意的：
> 硬跑下去，`api.sh` 不存在 → `sh: cannot open` → `2>/dev/null` 吞掉 →
> 最后只剩一句"名单匹配不上"，把人往完全错的方向带。

**脚本内部调 `socfreqd` 时不能写成 `sh "$D/socfreqd"`。** shell 对"脚本操作数"
是读进来当命令解析、不是 `execve`，把 ELF 当脚本解析只会得到
`cannot execute binary file`，stdout 一行都没有——于是上面第 3 到 6 项
全都变成恒空判断，**代码全对也报 FAIL**。
`api.sh` 是真脚本，那几处 `sh "$API"` 保留才对。

只查八件事：游戏列表有没有内容、名单条数对不对、守护认不认得 SoC、
逐核频率表读没读到（`ncores` / `coremax_0` / `corepol_*`）、
新键接上了没有 + 守护读的是不是搬家后的配置、守护活着没有、
**这台机上的真 APK 读不读得出应用名和声明的图标**（前六项 PC 上都能验，
只有这一项必须上真机——酷安那种资源名被缩短过的包，
在临时目录里造不出第二个来），
以及**智能学习的样本文件和 advice 判据接上了没有**（列数对不对、有没有落盘）。
任何一项不合格就非零退出，并把接口的原样输出打出来。

算法与前台包名解析的自检要跑 aarch64 二进制，在设备上执行：

```sh
# 构建自检版（与守护同一批源文件，SF_TEST 下不编 main）
aarch64-linux-android21-clang -DSF_TEST -static -s -O1 \
     -Wall -Wno-unused-function -Wl,-z,max-page-size=16384 -o test_real \
     src/socfreqd.c src/icon.c src/appinfo.c src/learn.c src/adapt.c -lz
# 必须过一遍 TLS 对齐，否则推上手机直接 Abort：
#   executable's TLS segment is underaligned: alignment is 8, needs 64
node tools/fix_tls_align.js test_real
adb push test_real /data/local/tmp/
adb shell su -c /data/local/tmp/test_real
```

**这一份要在真机上跑，不能只 `-fsyntax-only`。** 构建脚本里那步只编译不执行，
所以曾经有一条断言（`snap_from_list` 低于最低频点时该返回什么）和实现各说各话了很久：
实现返回原值（写 0 会被内核拒、整档不封顶），用例却写着 0 —— 只有真跑一次才会红出来。

`icon.c`、`appinfo.c` 和 `-lz` 都不能省：图标和名字都是从 APK 的 zip 条目里读的，
需要 `inflate`；少了 `src/icon.c` 会报 `undefined symbol: icon_from_apk`，
少了 `src/appinfo.c` 会报 `undefined symbol: appinfo_label`，
少了 `-lz` 会报 `undefined symbol: inflateInit2_`。

这里测试直接 include 守护源码，跑的就是线上那份代码——
刻意不把逻辑抄一份到测试里：两份实现会各自漂移，
抄的那份全绿而线上那份早已失效的情况很难被发现。

## 从源码编译

用随包分发的构建脚本，它比手敲编译命令多做了加载期的检查：

```sh
powershell -File tools/build_daemon.ps1
powershell -File tools/build_daemon.ps1 -dynamic   # 动态链接，省 700KB
```

**Windows PowerShell 5.1 和 PowerShell 7 都能跑**，不必特意装新的——
5.1 是系统自带的，上面这条命令直接可用。

（5.1 读 `.ps1` 时若文件没有 BOM 会按系统 ANSI 编码解码，
中文机器上是 GBK，中文注释和字符串全成乱码、报 ParserError，
而且退出码是 1，看着像"检查没过"。所以 `tools/` 下的脚本一律存成
UTF-8 with BOM，`pack.ps1` 会在打包前断言这一点。）

脚本会自己找 NDK（PATH / `ANDROID_NDK_HOME` / 标准 SDK 路径都试），
路径全部按脚本自身位置推导，放在任何目录下都能跑。

等价的手工命令（**四个参数都不能省**）：

```sh
aarch64-linux-android21-clang -O2 -static -s -Wall -Wextra \
     -Wl,-z,max-page-size=16384 -o socfreqd \
     src/socfreqd.c src/icon.c src/appinfo.c -lz
node tools/fix_tls_align.js socfreqd
llvm-readelf -lW socfreqd | awk '$1=="TLS"{print "TLS = "$NF}'
llvm-readelf -lW socfreqd | awk '$1=="LOAD"{print "LOAD = "$NF}'
```

| 缺了 | 结果 |
|---|---|
| `src/icon.c` | `undefined symbol: icon_from_apk` |
| `src/appinfo.c` | `undefined symbol: appinfo_label`（名单只剩包名，图标也回不到"按声明取"那一条） |
| `-lz` | `undefined symbol: inflateInit2_`（图标取自 APK 的 zip 条目，要 inflate） |
| `-Wl,-z,max-page-size=16384` | `PT_LOAD` 对齐停在 4KB，Android 15+ 的 16KB 页设备拒载 |
| `fix_tls_align.js` | `PT_TLS` 对齐是 8，Bionic 直接拒载 |

最后两条 `awk` 是**加载期自检**：TLS 段的 align 必须 ≥ `0x40`，
每个 LOAD 段的 align 必须 ≥ `0x4000`。这两项不对的话守护在 `exec` 之前就被
linker 拒绝，用户看到的只是「无法连接守护」，没有 logcat、没有 stderr、
没有 rc，只能把 `socfreqd` 捞出来跑 readelf 才能定位——
所以必须在构建阶段挡住，不能指望用户来报。

动态链接的产物用另一套判据：**不应有 `PT_TLS`**（`.tdata` 交给 libc.so）
且**必须有 `PT_INTERP`**。`tools/check_loadable.ps1` 会按产物实际的链接方式
自动选判据，两种都不合格都 `exit 1`。

`-s` 是去掉调试信息，包体积从 3.3 MB 降到 745 KB。
剩下的体积主要是静态链接的 libc，换来的是不依赖任何系统 .so。

### 两条只有真机才会暴露的加载期地雷

这两条都在 `exec` 之前被 Bionic 的 linker 拒绝，
守护一个字都没跑起来，页面上只显示「无法连接守护」，完全看不出真正原因。

**一、`PT_TLS` 的 `p_align` 是 8，而 Android 要求 >= 64。**

报错原文：

```
executable's TLS segment is underaligned:
alignment is 8, needs to be at least 64 for ARM64 Bionic
```

来源是 **NDK r25c 静态 libc 自带的 `.tdata`，不是本模块的代码**——
实测连 `int main(void){return 0;}` 编出来也一样是 `0x8`。
这个段是 `errno` 之类的东西，全静态链接的 C 程序都有。

r25c 的链接器没有 TLS 对齐的入口（`-z tlsalign=64` 被忽略，
`--tls-align=64` 直接报 unknown argument），所以只能在产物上补：

```sh
node tools/fix_tls_align.js socfreqd
```

只改 `p_align` 这 8 个字节，文件大小不变。
脚本改之前会核对 `p_offset % p_align == p_vaddr % p_align`
（loader 也会核对这一条，改完不自洽照样拒载），不自洽就报错退出。

**二、`PT_LOAD` 的 `p_align` 是 `0x1000`（4 KB），16 KB 页设备会拒载。**

Android 15+ 开始有 16 KB 页的机型。这个用链接器参数解决，
`-Wl,-z,max-page-size=16384` 实测在 r25c 上有效
（`p_align` 变成 `0x4000`，各段的 offset 和 vaddr 会一起重排，保持自洽）。

**两条都要在产物上核对，别信构建脚本自己说的"通过"：**

```sh
# 静态产物：TLS 对齐 >= 64，所有 LOAD 对齐 >= 0x4000
llvm-readelf -lW socfreqd | awk '$1=="TLS"{print "TLS align = "$NF}'
llvm-readelf -lW socfreqd | awk '$1=="LOAD"{print "LOAD align = "$NF}'
# 期望 TLS 那行 >= 0x40，所有 LOAD 那些 >= 0x4000
```

这两条不对的话，守护在 `exec` 之前就被 linker 拒绝，
用户看到的只是「无法连接守护」，没有 logcat、没有 stderr、没有 rc，
只能把 `socfreqd` 捞出来跑 readelf 才能定位。**这类问题要在构建阶段挡住，
不能指望用户来报。**

（`tools/build_daemon.ps1` 会自动跑上面那套 `awk` 断言，不合格时 `exit 1`；
`tools/check_loadable.ps1` 可以单独对任意 ELF 跑同一套判据。）

### 为什么保留静态链接

动态链接（去掉 `-static`）确实没有 `PT_TLS`，体积还能从 745 KB 降到 37 KB
（`tools/build_daemon.ps1 -dynamic`，实测）。但本模块的 C 代码只用 libc
和系统调用，没有 pthread / dl / NSS，不存在必须运行时解析的符号。
为省 700 KB 换来"linker64 与 libc.so 版本对不上"这种失败模式，
对一个开机脚本不值得。只有想在 recovery 或极早期启动里跑才需要考虑。

## 已知的边界

- 和其他改频率/调度器的模块（Scene、Scene5 等）不要同时用，
  两个都想当"节流阀"会互相打架。安装时会检测并提示，但不阻止。
- 部分新 SoC 的 GPU 没有暴露频率表节点，这时只限 CPU，日志里会告警。
- 读写范围只有两处：`/data/adb/soc_freqcap` 这一份数据目录，和自己封顶的那几个
  cpufreq / devfreq 节点；不需要网络权限，也不碰别人的文件。
- 图标：manifest 里那条声明路径读不出来的包（自适应图标只指向矢量 drawable、
  或资源名被缩短到认不出），那一行退回首字母色块 —— 这是设计上的降级，不是失败。
- 智能学习只在封顶真的生效时累计：被厂商热限频压着的那一段不算你的帽，
  那一档的建议会直接写成"被厂商压着，先不给建议"。这台机只有两档时就只有两行。
- **第三方耗电统计把游戏时段记成"待机"**：这类应用靠自己的常驻采样进程算账。进程在游戏时
  被 ColorOS `o-kill`（`dumpsys activity exit-info` 里是 `reason=13` 的 `o-kill(4013)`）后，
  采样会断几十分钟；恢复时它把断档按"待机"结算，断档期间掉的电量就全成了"待机功耗"。
  系统侧 `dumpsys batterystats --history` 同期仍是 `+screen`，本模块的深睡日志也没有
  "已进入"（亮屏不压 Doze）。把统计应用在最近任务里锁定、允许后台活动，能减少被系统回收；
  这段账不是模块能替它补的。

## 配置页顶部的 SoC 与频率表

SoC 型号依次读 `ro.soc.model` → `ro.board.platform` → `ro.chipname` →
`ro.product.model`，取**最后一个空格/逗号分隔的词**并转小写
（属性值常是 `Qualcomm Technologies, Inc SM8750` 这种带前缀的）。
四个都取不到才显示"未知"。

顶上还会列出每个核心与 GPU 的「原生最高频率 → 封顶后」：

```
CPU0  68%     1901 MHz  →  1292 MHz
CPU3  66%     3187 MHz  →  2103 MHz
GPU KGSL 45%   900 MHz  →   405 MHz
```

原生最高频率是硬件标称值，四舍五入显示；**封顶那一列一律向下取整**——
真实封顶 1292.544 MHz 就显示 1292，不显示 1293。往上凑的话，拿显示值反算
百分比会发现比设定值还大，"绝不超过设定百分比"这个卖点就成了空话。

拖动百分比滑杆时封顶值实时重算。标 `≈` 的表示**还没保存**（守护此刻
还不知道这个值），同样向下取整，和守护的吸附策略一致。
这一列显示的是**设定值**对应哪个频点，不叠加实时偏移；偏移后的实际值看
「GPU 封顶」卡片（硬件上限 / 当前封顶）和首页状态。

机上手动确认（两条都要看）：

```sh
sh $MODDIR/socfreqd export | grep '^soc='      # 期望 soc=sm8750
sh $MODDIR/socfreqd export | grep -E 'gpu_(max|unit)'   # 期望 gpu_unit=Hz
```
